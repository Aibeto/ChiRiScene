用户原话：「每天8～24点每2小时获取一次 https://raw.githubusercontent.com/Aibeto/ChiRiScene/refs/heads/
main/updateInformation/remindPush.json ，连接失败不重试，留一条info级别日志，然后尝试
https://raw.giteeusercontent.com/Aibeto/ChiRiScene/raw/main/updateInformation/remindPush.json
连接失败也是只留info不重试… 需要查找versionCode字段，找有没有和当前版本相同的JSON数组，
如果没有则静默，有则把titile和content作为通知标题和正文发送，渠道是ChiRi-Remote」

### 新增

- `src/remote_push.rs`（新模块，含 8 个单测 + 1 个 `#[ignore]` 网络冒烟）。
- `src/main.rs`：`mod remote_push;` + 启动路径 `remote_push::spawn(root.clone())`（独立线程，不 join）。
- `Cargo.toml`：`ureq = { version = "3", default-features = false, features = ["rustls"] }` + `serde_json`。
  ureq 3 默认特性是 `[rustls, gzip]`，关 gzip 省掉 flate2——目标接口是未压缩 JSON。
- i18n：新增 6 个 key（`remote-push-started/primary-failed/fallback-failed/notified/no-match/thread-failed`），
  zh/en 各 364 键、差集为空。注意通知**标题/正文来自远程 JSON**，不是 i18n 文案。

### 关键设计点

1. **槽位口径**：`SLOT_HOURS = [8,10,12,14,16,18,20,22]`。「8～24 点每 2 小时」里 24 点即次日零点、
   不在偶数槽位内，故最后一个槽是 22:00。按**墙钟**排（用户说的是「每天几点」），60s 轮询比对小时，
   同槽位只拉一次；进程在槽位中途启动会**补拉一次**（是补上本槽，不是重试）。
2. **versionCode 归一化是必须的**：示例文件用的是 `"00000"` 这种补零字符串，而真机 module.prop 是
   不补零的 `30210`，直接 `==` 永远不命中。`normalize_code` 去空白 + 去前导零，两侧都归一后再比。
   versionCode 允许是字符串或数字（`entry_code` 都认）。
3. **当前版本以磁盘 module.prop 为准**，读不到才回退 `include_str!` 内嵌值——用户看到的「当前版本」
   就是磁盘那份。
4. **未命中静默**：只留 debug（`log_enabled!` 门控），不进 info——没命中是常态，不该占日志。
5. **失败不重试**：主源失败 info 一条 → 备用源 → 失败再 info 一条，本轮收工；下一个槽位自然再拉。
6. **超时与体积上限**：10s + 64KB，后台线程不能卡死。`ueq` 的 `http_status_as_error` 默认 true，
   故 404 也走 Err（会被记成 info），正合「连接失败留 info」的口径。
7. **TLS**：rustls + ring + `webpki-roots`（内嵌根证书）。刻意不用 `platform-verifier`：daemon 以
   root 跑，但 Android 系统 CA 目录不保证可读，内嵌根证书更稳且行为确定。

## 修正：versionCode 改为数字 + 恒等 + 只认内嵌（同日，用户四次修正）

用户原话：「示例修正：versionCode 30000/30001 …两个versionCode需要恒等，现在不用去0了。
始终使用内嵌versionCode，不要看磁盘，因为磁盘是可以被篡改的」

### 三处改动（`src/remote_push.rs`）

1. **删掉 `normalize_code`**，`find_entry` 改成 `code.trim() != want` 的**恒等比较**。
   只保留 trim 级清洗，不做任何数值归一——归一会让 `"030001"` 命中 `30001`、`"00000"` 命中 `0`，
   正是用户明确排除的模糊匹配。
2. **`current_version_code()` 去掉 `root` 参数，只返回 `include_str!("../module/module.prop")`
   里的 versionCode**，不再读磁盘。理由（用户点明）：模块目录对其它进程可写，改 `module.prop`
   的 versionCode 就能让 daemon 去匹配远程列表里任意一条、收到伪造提醒；内嵌值随二进制一起更新，
   语义上本就是「这个二进制的版本」。这也与本仓库 `rules.yaml` / `special_tuned.yaml` 的
   「编译期嵌入为唯一来源、磁盘副本仅展示」口径一致。
3. 连带简化：`run_once()` / `spawn()` 都不再需要 `root` 参数；`use std::path::Path` 移除。
   `main.rs` 改为 `remote_push::spawn()`。

安全细节：内嵌 versionCode 取不到时返回**空串**，`find_entry` 遇空值直接 `None`（静默）——
**空值绝不当通配符**，否则缺 versionCode 的构建会把远程列表第一条当成本机提醒发出去。

## 修复：日志超限通知四条（用户「123都修」+ 渠道改 ChiRi-Logs）

### 真机证据（用户提供，2026-10-18 12:20:41）

```
[notify] [Notify] 投递成功（tag=ChiRi-Status title=ChiRi日志事件 strategy=- verify=posted）
[logger] [Logger] devimp/ 已达到 128MB，立即重启调度以打包日志
```

`verify=posted` 证明 AOSP 回查**确实看到了这条通知**——所以不是「没发出去」，而是**发出去后被覆盖了**。
`strategy=-` 则暴露另一个 bug（见第 ④ 条）。

### 根因：同 tag 覆盖

启动通知与日志超限通知**共用 tag `ChiRi-Status`**，而 AOSP 侧同 tag 即同一条通知（`NOTIFICATION_ID` 固定 2020）。
本通知发出后 daemon 立刻 `exit(0)`、看门狗 3s 后拉起新进程，新进程又发一条 `ChiRi-Status` 的启动通知，
**几秒内把日志事件顶掉**。用户回看通知栏只剩「ChiRi已启动」，自然认为没发。
→ 用户决定：日志超限改用 **`ChiRi-Logs`** 渠道/tag，两者互不覆盖。

### 四条修改

1. **`src/logger.rs` tag `ChiRi-Status` → `ChiRi-Logs`**（含 `[tag-separate]` 注释说明为何不能共用）。
2. **通知提到 `watchdog_pid()` 判定之前**：日志满了必须告知用户，与能否自愈重启无关；无看门狗时用户更需要知道（要手动处理）。
   新增 `LOG_OVER_NOTIFYING: AtomicBool` 串行化投递（门限达到后每次写日志都会进来，脚本 su 链最坏十几秒，不挡会并发投递）。
   两条相关日志都加 `notify={ $notify }`（`ok`/`failed`），避免只看「立即重启调度」把投递失败误当成功。
3. **`log_overrun_allowed(None)` 由 `false` 改 `true`**：原实现把「读不到 `current_mode.chr`」当成「确认是 FAS」
   永久推迟，文件一读不到通知就再也发不出来，只留每 10 分钟一条 warn。真正的 FAS 一定有该文件
   （调度线程 5s 自愈重写），读不到属异常态，此时优先保证用户被通知。新增 warn key
   `logger-log-restart-mode-unknown`。
4. **`module/scripts/notify.sh` 补 `echo "OK S$ACCEPTED"`**：`notify::strategy_of()` 找的是 `OK ` 前缀，
   原脚本成功路径只打 `S<n>:ok`、从不打 `OK …`，于是日志里 `strategy=-`，把「走的哪条策略」丢了。
