## 2. 关键发现

### 2.1 热阶梯：三个缺陷

**(1) 硬限档回滞缺失（代码级确认）**

`src/chiri/mod.rs:146-166`：

```rust
if temp_c >= hard { hard_cap }              // >= 45℃ → 0.40，无回滞
else if temp_c >= soft { soft_cap }         // >= 41℃ → 0.85
else if temp_c < soft - hyst { 1.0 }        // < 38℃ 才解除软限（有回滞）
else if current >= 1.0 { 1.0 }
else { current.min(soft_cap) }
```

只有「软限 → 解除」这一条边带回滞（38℃），**硬限 → 软限这条边没有**：温度一降到 44.9℃ 立刻从 0.40 跳到 0.85（再经 `THERMAL_UNPRESS_STEP=0.15/2s` 斜坡，`mod.rs:2145-2151`）。日志表现完全吻合：每次进硬档都是 batt=45.0、每次退出都是 44.9，批次2 出现 5 次进档（21:51:41 / 21:55:11 / 21:55:45 / 22:00:08 / 22:02:03），其中 22:00:06.48 退出、**22:00:08.49 又进**（2.0 s）。

后果：45℃ 附近形成 0.40↔0.85 的锯齿，表现为「周期性卡顿 + 周期性能耗尖峰」，且 `hysteresis_c=3` 的防抖设计在硬档上失效。

**(2) 中段无压制力**

`clamp_heavy=true`（`8550/feature.yaml:76`）时 `free_above=0.95` 完全不参与判定（`cpu_load_governor.rs:493`），钳制形态是「所有簇恒 `min(current_perf, cap)`」。而 CLG 自己选的 `current_perf` 通常低于 0.85，于是 cap=0.85 大量空转：

- 批次3 cap=85 期间 22819 个 tick 只有 3157（13.8%）真被削；coolapk 段 `in_band` 710/12394 = 5.7%
- 反观 cap=40 段（批次2）8696 tick 中 5704（65.6%）真被削，硬件钉在 little 902400 / big 1401600 / prime 864000 kHz（44.8% / 50% / 27% HW）

结果是 41→45℃ 这一 4℃ 区间（占总时长 64%）实质是「无压制区」，一路升到 45℃ 才被 0.40 一刀砍下。**软限档阈值/数值至少有一个是失配的。**

**(3) tuned 模式无热压制（结构缺口）**

`thermal_cap` 原子量只传给 CLG 的 Worker（`cpu_load_governor.rs:916/982`），`config.rs:859` 明确写着「仅对 CLG 接管模式生效（reduce/default/boost/doze/scenemode）；vector/akmode 不受影响」。playback 走 tuned，**没有任何温度响应**。

细节补充：播放态各簇 tuned 上限为 little 0.55 / big 0.75 / prime 0.50（`module/config/normal/tuned_profiles.yaml:61,66,69`），**全部 ≤ 0.85** → 软限档对播放态本来就是 no-op，真正无保护的是硬限档 0.40。本次未抓到「硬限档窗口 + 播放态」重叠（批次2 的 5 次硬档窗口落在 coolapk/lark/idlefish/QQ 上），但播放态长时间处于 40–42℃ 且 cap=85 在效（status.csv playback cap avg 89）却毫无响应，结构缺口是确凿的。

### 2.2 CLG 决策层

- **playback**：决策上限 little 44.8%（902 MHz）/ big 50%（1401 MHz）/ prime 27%（864 MHz）；snap 侧 `cpu_cur/cpu_max` = 84–92% → 票值长期贴住决策上限，**上限是约束**。决策分布 hold 41.9% / up 21.7% / down_wait 23.3% / down 13.0% / up_wait 0.0%。prime 实际频率中位数恰为其最低档。
- **default**：up + up_wait 占 70–82%，down 系仅 10–21%（升频侧限速单边偏重）。
- **little 阈值失配**：`8550/feature.yaml:159` 把 little 的 `up_threshold` 覆写成 **0.95**（全局 0.88）→ little 几乎永不判 high load，只能走 `slow_up=0.02`/tick 爬升。kernelsu 段实测 20:13:48–20:14:30 连续 **242 tick（39 s）** deb_up，期间 max_util 均值 0.80，而上限只爬到 cap 的 55%。
- **方向抖动**：big 簇方向翻转 52–86 次/分（coolapk 379 次/4.4 min，1 秒内最多 6 次；QQ 达 7 次/s）。实际写频被 `write_dwell_ms=320` + `write_deadzone=0.03` 限制在 ≤3 次/s，故抖动部分是打点噪声，但方向反复说明死区没吃掉它。
- **降频空转（正常现象，勿误判）**：kernelsu prime 连续 992 tick 判 down 而值不变，是 `[deadzone_hold]` 吸收的结果（`cpu_load_governor.rs:445-450`），不是写频失败。

### 2.3 亲和 / core_ctl

- **无泄漏**：pin : restore ≈ 1:1（F1 21907:22254、F2 21372:21162、F3 15816:15338、F4 2962:2920），差额全为 e3(ESRCH)。`home` 全为 -1（只下组掩码，不钉核）。「累积数单调上行」是差分日志假象（释放后不再落行）。
- **bulk 清理不是写放大**：每会话 72561 / 70965 / 65198 / 18313 条，其中逐条 `bind_release` 仅 2.6% 真动过核，97% 是纯记账删除。
- **e22 全在 pin、成 32 条突发**（41/210/198/40 行/会话，32 = `FG_SCAN_WINDOW`）：含义是 32 位任务被钉到无 AArch32 的核（`affinity.rs:705-707`），不是 core_ctl halt（本包 corectl 事件 0 条）。
- **绑定覆盖率**：max u≥90 的高负载线程只有 39–48% 进过绑定表。
- **BOOST 态 prime 静默失效**：`core_ctl.rs:278-292` 写 `min_cpus = cluster_size` 时**不检查 `enable`**，而本机 prime `enable=0`（daemon.log：`[CoreCtl] core_ctl enable=0`）→ 写 sysfs 返回 ok、内核不受理、日志记 ok。BOOST 态「全组常在线」在 prime 上落空且打点失真。

## 3. 调度优化方案

### P0-1 热链路：给硬限档加回滞（改 1 行 + 1 个可选配置）

`src/chiri/mod.rs:146-166`：

```rust
// 现状
if temp_c >= hard { hard_cap }
// 建议（进入仍是 45℃，退出必须降到 hard - hyst 以下）
if temp_c >= hard || (current <= hard_cap && temp_c >= hard - hyst) { hard_cap }
```

- 效果：硬档从「44.9℃ 即退」变为「跌破 42℃ 才退」，与软档回滞对称，消除 0.1℃ 级锯齿。
- 权衡：45→42℃ 期间维持 0.40，压制时长变长；若嫌过激，新增独立配置 `hysteresis_hard_c`（建议默认 1.0–1.5）而不复用 `hysteresis_c`。
- 验证：改后重跑同场景，`thermal_change` 序列里「40 档进档次数 / 60s 内重入次数」应降到 0–1 次；`cap=55/70` 的瞬时档位不再频繁出现。

### P0-2 热链路：让中段真正有压制力（二选一）

- **低成本**：`module/config/8550/feature.yaml:65` `soft_perf_cap: 0.85 → 0.70`（与 8475/8998 口径一致）。cap 值必须下调、改阈值无用——因为 CLG 自身目标很少超过 0.85，降低阈值不会增加 bite rate。
- **更精细**：`eval_thermal_cap` 从三级扩为四级，新增 `batt_mid_temp_c`（建议 43）与 `mid_perf_cap`（建议 0.60），形成 0.85 → 0.60 → 0.40 的阶梯，避免 41–45℃ 无压制区。
- 预期：批次2 那种「85 档内一路升到 45.8℃」的爬升应在 43–44℃ 被止住，硬档进入次数下降，代价是重负载的中段性能。
- 验证：`thermal_change` 时间线 + 各档持续秒数 + 真钳制率（`cap/100 < cur_perf` 占比）。

### P0-3 热链路：把硬限（或独立下限）接入 tuned

- 位置：tuned 侧写频处（`src/chiri/tuned.rs`）或 `cpu_load_governor` 的热钳逻辑复用一份到 tuned；`thermal_cap` 需要像 CLG 那样传引用给 tuned manager。
- 建议形态：tuned 侧 `eff_perf = min(profile_ceil, max(cap, TUNED_THERMAL_FLOOR))`，`TUNED_THERMAL_FLOOR` 取 0.55–0.60，避免直接把播放态砍到 0.40 掉帧。
- 前置条件：必须先有帧信号（见 P2-3），否则无法判断是否掉帧。
- 验证：硬档窗口与播放态重叠时，播放功耗应下降、`batt_temp` 峰值下降，且 fps 不劣化。

### P1-1 CLG：little 阈值与升频速率

- `feature.yaml:159` little `up_threshold: 0.95 → 0.90`，或把 `slow_up_scale` 改为随 `(util - up_threshold)` 缩放 / 提到 0.05。
- 依据：kernelsu 段 39 s 连续 deb_up、util 0.80、上限只到 cap 的 55%——light app 的前台上限被爬升速率拖住。
- 验证：同场景 deb_up 最大连续值应显著下降（现值 little 最高 1437 tick / 242 tick 级）。

### P1-2 CLG：抑制 big 簇方向抖动

- 先把 `write_dwell_ms` 320 → 480–500 做一次 A/B；若抖动仍在决策层，再查 `spike_jump 0.40 / spike_decay 0.10` 的锯齿来源（`default` 段，`feature.yaml:167,169`）。
- 验证指标：`max 1s 内方向翻转次数`、实际 sysfs 写频次数（`clamp_change` / tick 决策分布）。

### P2-1 core_ctl：BOOST 态 prime 的假 ok

- `core_ctl.rs:278-292` 写 `min_cpus` 后**读回校验**；`enable=false` 的簇按「无效」处理（改走逐核 `online` 兜底或明确不写 + 明确打点），不要把 ok 当成功。
- 依据：本机 prime `enable=0`，BOOST 态「全组常在线」在 prime 上并未生效。

### P2-2 aff 打点与重试

- uclamp bg：`/dev/cpuctl/restricted` 在本机不存在（`affinity.rs:82-84` 注释已写明），`affinity.rs:107-117` + `utils.rs:61-86` 吞掉逐节点 errno → 打点恒 50% `e0`。建议探测一次缓存缺失、并把 errno 带进打点，否则该指标长期像故障。
- pin e22：目标掩码先与原允许掩码求交；EINVAL 后把该 tid 标记为不可钉、不再在每轮 `FG_SCAN_WINDOW`（32）里重试。

### P2-3 工具：播放态也需要帧信号

- 现状 fps uprobe 仅在 FAS 活跃时写入（本包 16288 行 status.csv 全为 `-`），导致**播放态的任何调参都无法用流畅度判定**——这是 P0-3 与后续播放态省电实验的共同前置条件。
- 建议：把 fps 采样扩到 tuned playback（或加一个轻量掉帧计数），成本和现有实现同源。

## 4. 不确定 / 需更多数据

1. **播放态是否有省电余量**：无法判定。决策上限 44.8%/50%/27% 且票值贴上限 84–92%，只能说明「上限是约束」，不能说明该放宽还是该收紧；没有帧信号就没有判据。
2. **deepseek 段 little 39 s 连续 deb_up** 的确切归因（`smoothing_up=0.60` + `up_rate_limit_ticks=3` + little 阈值 0.95 的合成效应）需专项验证。
3. **「cap=40 期间 CLG 仍写 83% 上限」这类单点记录**：在 `clamp_heavy=true` 语义下不成立，已按 S2 实测（cap=40 时硬件钉在 44.8%）判为**钳制正常工作**，不列为缺陷。
4. **本次与 2026-09-23 基线不可直接比**：battT 40.4 vs 37、cpuT 53.7 vs 52.7，且本次开诊断。播放 2.92 W 略高于 09-23 的 2.78 W（devimp 同法），差异量级与温度差一致，不宜归因到调度改动。
5. **诊断本身的开销**：`devimp/` 在约 75 min 内触顶 128 MB（≈25–30 KB/s），4.6 h 内触发 3 次重启；该写入开销计入本次全部功耗数字，且每次重启把热状态重置回 100（批次1 有 47.3% 时间仍在 cap=100），长程热轨迹不可跨批次连读。
