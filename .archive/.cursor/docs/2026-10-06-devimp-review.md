# 1005-1006 四包日志分析与改进建议

## 结论

优先修 FAS 状态与帧源归属，不先调低频率、热阈值或性能地板。

1. **P0：延迟退出期间切回游戏，仍被到期处理拆掉 FAS。** 国际服王者在前台连续 659 个样本由 CLG/default 接管，约 11 分钟；不是只有显示列写错。
2. **P0：FAS 延迟退出期间缺少帧源归属校验。** 切到设置或 bilibili 后，探针切到新前台 PID，旧 FAS 实例仍有档位控制动作。代码允许新前台帧进入旧实例，但事件不带来源，日志不能确定每次动作来自新帧还是旧游戏积压帧。
3. **P1：记录开销仍值得优化。** 最新批次 daemon 单核占用：8650 亮屏 12.14%，PHB110 最新亮屏 6.09%、息屏 3.16%；这些是 daemon 全部开销，不能全部归给 aff。
4. **P1：分析工具有误导性口径。** 重复启动被误报为混版本；无表被误报为老包；采样缺口被当作连续秒数；基线以上整机能量被直接叫作 CPU 增量。

本次只分析与提出方案，没有修改运行时代码或参数，也没有进行 A/B 实验。

## [fas-state] P0：切回游戏后错误退出，且不自愈

证据源：`devimpbin/1006-180755/x_1006-180717/daemon.log:189-211` 与同行 status。

- 16:16:12：游戏切到 `com.android.settings`，进入延迟退出。
- 16:16:27：AppDetect 明确记录 `default -> fas (com.levelinfinite.sgameGlobal)`。
- 16:16:28：三个 policy 从 performance 恢复 uag，游戏 FAS 实例去激活，随后按 **default** 重新接管。
- `status.csv:2395` 是游戏的 fas 样本；`:2396-3054`，16:16:29-16:27:27，仍是同一游戏，但 `mode=default / clg_active=1 / fps=-`，共 659 行。
- 下一秒前台才变成微信。故是游戏在前台时失去 FAS，而非正常离开游戏后的 15 秒尾段。

当前源码与这个现象相符，但源码核验不是对日志包二进制的反编译证明：

- `src/chiri/mod.rs:2671` 附近，ModeChange 的实际操作放在 `old_mode != mode` 内。延迟期间 scheduler 的 old_mode 仍为 fas，回来时再收到 fas，整段模式处理被去重，不能通过该路径取消 deadline。AppDetect 此次模式确实变化，生产的是 ModeChange，而不是可续期的同模式 PackageSwitch。
- 同文件 `:2153` 先执行 `fas_mgr.tick()`，`:2258` 才检查前台同包并续期。到期当轮即使前台快照已是游戏，也会先退出，再因 mode 已变 default 而错过后续续期。日志不能确定回前台事件具体何时入队或消费，不应把“消息尚在队列里”当作已证实原因。
- 到期把 mode 改成 default 后，后面的 FAS 自愈分支又要求 mode 已是 fas，因此可能永久漏掉这次重入，直到下一次真正的模式切换。

建议的最小修复方案：

1. 处理目标为 fas、且 package 等于活跃实例的 ModeChange 时，先验证 FAS 启用、白名单有效、未停摆且满足冷却约束，再取消 deadline 与 pending_mode_after_fas，最后做模式去重。
2. 每秒到期处理前，先用当前前台快照确认是否回到活跃白名单包；同包且满足上述门控才续期，不能仅凭包名取消退出。
3. 自愈依据应包含“当前前台白名单、允许 FAS、未停摆/未禁用/不在冷却”，不能只依赖 scheduler 当前 mode 恰好是 fas。
4. 非 fas 前台在延迟期间继续变化时，pending 目标跟随最新前台，避免退出后恢复到旧目标。

验收只需构造性状态机测试与日志事件离线重放：返回发生在 deadline 前、同刻、后；同包/不同白名单包；禁用、DOWN、冷却、息屏；全部保持只有一个接管者。上述 16:16 时间线应在回来时取消退出，不能产生 659 行 default。

不建议为绕过这个缺陷直接删除 15 秒延迟：会改变用户切出再切回游戏的既有语义。

## [fas-source] P0：延迟期间的帧源没有跟随 FAS 所有者

同一 daemon 的 `:191-195`：切到设置后，uprobe 改挂 PID 23991，游戏实例仍产生“降档加速”日志。

更清楚的证据在 `daemon.log:263-283`：

- 16:34:16 从国际服王者切到 bilibili，uprobe 改挂 PID 6813。
- 到 16:34:31 真正退出前，**旧游戏 FAS** 连续出现降档加速，以及 `120 -> 60 -> 120 -> 60` 档位切换。
- 探针已改挂 bilibili，但 FrameUpdate 丢失了来源信息。这段档位变化不能解释为游戏真实帧率变化，也不能逐条断言由 bilibili 帧导致；旧游戏已入队帧或两者混合尚无法排除。

源码旁证：`fps_monitor.rs:680-686` 无条件消费前台 PID 广播并 switch_pid；`:729` 附近发出的 FrameUpdate 只有 delta。`chiri/mod.rs:3118-3122` 只看 FAS 活跃就投喂，未验证源 PID/会话。

正常 switch_pid 路径先摘旧 PID，再以 OneProcess 挂新 PID；连续 attach 日志不证明多个 PID 同时有效。take_pending 遍历全部 states 是消费边界风险，不是本包已发生多 PID 并行混流的证据。新帧逐条投喂改善了 delta 新鲜性，但不保证其属于当前 FAS 实例。

建议将 FAS 帧源所有者与普通前台观察者分开：

- 活跃游戏的 PID/实例 generation 是控制输入的归属，FrameUpdate 带来源信息，调度端拒绝不匹配或旧 generation 的事件。generation 必须覆盖采集、换源及排队事件的生命周期，不能把旧帧在出队时重新标为新会话；仅增加 PID 字段不能防止 PID 复用与旧事件积压。
- 延迟退出仍保留游戏实例，但暂停非游戏帧对其档位控制；也可继续监听原游戏 PID。不要把下一应用的显示刷新率灌进去。
- 主动换源时重置窗口并丢弃旧帧队列，保证退出重入不能用上一实例的帧。
- 播放态离线直方图保持独立门控，不为诊断旁路增加控制权限。

功能回归：游戏 -> 设置/视频 -> 游戏的事件序列里，非游戏帧不能推进游戏 gear_state。此修复优先于调 gear 参数。

## [overhead] daemon 自测量：仍有可优化项，但不可直接折算省电

计算 `100 * sum(delta(utime_ms + stime_ms)) / (1000 * sum(delta wall_seconds))`。分别在每个文件内计算，跨午夜展开；负差分及 >=10 s 缺口不纳入，区间按前一行 screen_prop 分组。这是有效采样短区间的单核等效百分比，不是整机 CPU 百分比，也不是整个会话的墙钟摊销平均。10 s 是筛选阈值，不足以证明余下区间全部活跃或被排除区间全部 suspend；屏幕切换区间也可能有归组误差。

- PJX110 最新：亮屏 10031.44 s 中消耗 1217.45 CPU s，即 **12.14%**；息屏有效区间 662.31 s 中消耗 18.34 CPU s，即 2.77%。
- 2210132C 最新：亮屏 **3.69%**；息屏 5.29%，但只有 475.30 s，不能当长时间待机结论。
- PHB110 / 131110 最新：亮屏 **5.89%**；息屏 **1.15%**，有效息屏区间 16016.75 s。
- PHB110 / 180755 最新：亮屏 **6.09%**；息屏 **3.16%**，有效息屏区间 3324.09 s。该筛选口径高于台账的息屏 2% 数值目标；若目标采用全会话墙钟分母，则不能直接判定验收失败。

建议先复用已有 `devimp_aff_secs` 与息屏倍率，在相同版本的后续自然观察中记录有效配置；不能根据这些跨场景百分比声称某配置节省了多少电。

实现候选按收益依据排序：

1. 用现有 self CPU 计数和 @S 帧规模定位 daemon 内部成本，不新增重型周期探针。
2. 不再对冷长尾线程逐帧读取所有 stat；保留前台、受管线程的必要刷新及 full=1 存活集合契约，不能用“省略行就是退出”替换。
3. 已完成验证的临时旁证按仓库 PAUSED 约定停旁路，不删消费者仍在用的 telemetry。
4. `energy_cost.rs:[accounting]` 每秒还会单独读三个频率节点，可复用同秒 freq snapshot，减少重复读取并改善时间对齐；它是小优化，不能宣称会消掉全部 daemon 占用。

现有包不能分离 aff、FAS 帧处理、CLG、日志写入的各自 CPU 份额。没有直接 profiling 证据前不重写调度架构、不换语言。

## [accounting] 功耗分解及分析脚本需要先纠正口径

### 动态 CPU 是估计，不是已标定的实测下界

- 8650 status 已有 `cpu_dyn_w / resid_w` 列，但值全为 `-`，因为没有功耗表；`energy.txt` 的“老版本没有两列”提示不正确。
- PHB110 / 131110，干净 A01-08 的整包亮屏回归：a=1.97 W、b=1.20、R2=0.520；180755：a=2.05 W、b=1.30、R2=0.556。截距量级合理，但不能据此证明动态功耗表已校准。
- 131110 息屏 R2=0.005；180755 息屏 R2=0.045。混场景、采样不同步和外围变化都能产生低相关性，不足以单独证明能效表量纲错误。
- 现有回归只按 screen_prop 分组，混合了包名、模式、内容和热状态；baseline 则按 screen_prop 与 package 分组，两者控制口径不同。a 是外推截距而非实测外围功率，b 不是已校准的转换常数。下述更细分回归是改进建议，不是现有产物已完成的控制。
- 原始 `180755/x_1006-180717/status.csv:2236`：整机 4.658 W，而 CPU 动态估计 7.068 W，残差 -2.410 W。存在明显的瞬时不闭合；不能把模型输出当这一秒物理上的确定下界，也不能把负残差夹零后宣布账已闭合。

改进：先对齐电量计刷新、频率与 util 的时间窗，报告有效比例与负残差比例；按同包、同模式、同屏幕状态、连续批次回归，注明动态表电压来源的系统偏差。暂不改模型常数来强行拟合整机功耗。

### “基线以上整机能量”不等于“CPU 增量能量”

`dvenergy.py:[2]` 的 baseline 是低 CPU 分位时的 **整机功率**，其中 CPU 动态项并不为零；`[3]` 从整机减它，却再减未扣低分位基线的全部 CPU 动态能量，基准不一致。

例：第二包 energy 输出给王者总增量 23.02 Wh、CPU 动态 30.51 Wh、未解释 -7.49 Wh。这个负值不直接意味着 CPU 模型多算了 7.49 Wh。

建议同时报告三份同基准的量：

- 总增量：`sum(P_total - baseline_total) * dt`。
- 模型动态增量：`sum(P_cpu_model - baseline_cpu_model) * dt`。
- 未解释增量：前两者之差，仍包含 GPU、外围与模型误差。

低分位 baseline 是观察性的统计代理，不是物理上的纯外围常数；显示内容/亮度不同会变。低相关性场景的总增量尤其不能全算在调度头上。

### 行数、时间、FPS、版本警报

- `131110/x_1006-120018` 跨约 **11.84 h**，却只有 20391 行，远低于每秒一行应有的约 42635 行。脚本 `sum(W)/3600` 是假设每条覆盖 1 s 的样本能量，**不能当整个会话实耗 Wh**，热档行数同样不能当完整墙钟秒数。
- 长缺口可能与 suspend 有关，也可能来自采样链路停止、失败或日志缺失；仅凭时间戳不能区分。须交叉核对屏幕、重启及其他周期观测。功耗的样本等效 Wh 与上述排除长缺口的 CPU 百分比使用不同分母，不能混合解释。
- 改进输出采样覆盖率、缺口与有效 dt；短间隔可按明确积分约定计账，长缺口单列未知覆盖，不把末值外推一夜。若需要全会话能量，优先使用已有电量计累计量，缺失就承认无法恢复。
- `dvstatus.py:daemon_report` 用含日期时间的整行 set 判版本，导致第一、三、四包同版本重启也报警。改用解析后的 module/versionCode/SoC/kernel 值判定。
- “fps 全空 = FAS 从未接管”不是充分证据：FAS 可以活跃但没有帧或探针失败。应同时核对 mode、实例激活记录、governor 与帧源状态。
- `dvenergy.load()` 只识别 root 下一层 status；本次对单批次目录调用不会产生分解。建议支持显式文件/批次选择，以及 `--since`，避免默认混版本汇总。第二包默认 energy 只能作 A01-08 有有效列样本的背景，不能当最新批次统计。
- 判读热带要尊重实际 `clamp_heavy`；`main.txt:[5]` 的固定“free_above 总是豁免”模板也应与现行配置门控一致。
