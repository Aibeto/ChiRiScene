## 二、地板拆分（三个 mode 拆法各不相同）

### 2.1 方法论修正：地板法对 fas 失效

`tmp_an202 [5]` 用「硬地板 + 专属地板 + cpu_dyn + 其余」四段相加时，fas 的「其余」= **−1.524Wh**（负值）。

**原因**：fas 的 governor=performance，三簇恒定钉满（`cur/max` 三簇均 100%），cpu_dyn 均值 2.703W 本身就是「地板 + 恒载」的合体 —— 再单独减一次地板就会重复扣除。

> **教训（写进判读口径）**：地板法只适用于**频率随负载变化**的 mode（default / playback / akmode）。对 `governor=performance` 的恒定供给 mode（fas），只能用 **cpu_dyn + resid 两分法**。

### 2.2 三 mode 拆分结果

**playback（15.059Wh，地板法成立）**

| 成分 | Wh | 占比 |
|---|---|---|
| 硬地板（息屏 p25 0.327W + 屏幕 0.474W） | 3.609 | 24.0% |
| playback 专属地板 +0.658W | 3.67 | 24.4% |
| CPU 动态 | 4.129 | 27.4% |
| 其余（resid + 活跃外围） | 2.787 | 18.5% |

**fas（3.974Wh，两分法）**

| 成分 | Wh | 占比 |
|---|---|---|
| CPU 动态（含恒定满频） | 2.206 | **55.5%** |
| resid（GPU + modem 游戏联网 + 屏幕刷新增量） | 1.768 | 44.5% |

**akmode（2.664Wh，地板法成立）**

| 成分 | Wh | 占比 |
|---|---|---|
| 硬地板 | 0.348 | 13.1% |
| akmode 专属地板 +1.760W | 0.95 | 35.7% |
| CPU 动态 | 0.721 | **27.1%** |
| resid | 0.566 | 21.2% |

### 2.3 专属地板是什么（不可动）

| mode | 专属地板（息屏取 p25） | 候选构成 |
|---|---|---|
| playback | **+0.658W（3.67Wh）** | VPU 视频硬解 + 音频 + Wi-Fi 流媒体持续下载 + 高刷屏 |

⇒ playback / akmode 各有约 1/4 ~ 1/3 电量是**场景固有成本**，调度层碰不到。

## 三、逐 mode 归因与可动性判定

### 3.1 fas（3.974Wh）—— 典型过度供给，但降频有帧率风险

**证据链**：

1. **CPU 满频但不是帧率约束**：`corr(cpu_dyn, fps) = −0.234`（n=2854）；cpu_dyn 四分箱 → fps 单调**下降**：

   | cpu_dyn 箱 | n | fps 均值 | avgW |
   |---|---|---|---|
   | Q1 [0.25,2.35]W | 713 | **96.33** | 4.476 |
   | Q2 [2.35,2.76]W | 713 | 92.51 | 4.730 |
   | Q3 [2.76,3.15]W | 713 | 92.03 | 4.864 |
   | Q4 [3.15,8.01]W | 715 | **91.60** | 5.253 |

2. **无排队压力却满频**：`psi_cpu` 均值 **9.4**，是四 mode 最低（default 18.6 / playback 19.5 / akmode 16.6）。`freq_trans` 仅 **78/s**（其余 mode 3839~8098/s）—— 因为 governor=performance 根本不调频。
3. **掉帧窗口不是 CPU 不够**：fps<90 的 157s，avgW 5.552 / cpu_dyn **1.756W** / psi 11.8；fps≥90 的 2697s，avgW 4.789 / cpu_dyn **2.749W** / psi 8.6。**掉帧时 CPU 反而更闲** ⇒ 掉帧是 GPU/场景侧的事，不是 CPU 频率的事。
4. **热档**：fas 全程 cap=100%，未触热限 ⇒ 无热致降频混淆。

**判定**：fas 的满频对帧率边际贡献为 0 或负，属**过度供给**。但：

- 该负相关**可能含反向因果**（场景变重 → fps 降 + CPU 用得多），不能据此断言「降频能提帧」。
- 项目铁律禁止 A/B 对照 ⇒ 只能用「同场景观察 fps 分布」验证，**不能承诺帧率不劣化**。

**可动**：cpu_dyn 2.206Wh，削 10~20% → 0.22~0.44Wh（直接项）。AMP 仅 **0.417**（R²=0.212，最低），说明 fas 的整机功率与 CPU 动态几乎不共变 ⇒ 折算后 **0.09~0.18Wh（10%）/ 0.18~0.44Wh（20%）**。

**建议**：**灰度，不作承诺收益**。具体手段 = `tuned_profiles.yaml` 的 fas headroom（与 akmode/playback 的 headroom 同族）。

### 3.2 akmode（2.664Wh）—— GPU 主导，CPU 侧天花板很小

**直接证据**（`tmp_an202 [3]`）：

| gpu_busy 分桶 | 秒 | 占比 | avgW | resid | Wh | 占 akmode |
|---|---|---|---|---|---|---|
| ≥60% | 978 | 50.5% | 6.208 | 4.728W | 1.686 | 63.3% |
| <20% | 331 | 17.1% | 3.977 | 2.639W | 0.366 | 13.7% |

**ΔavgW = +2.231W，其中 Δresid = +2.088W 占 94%，Δcpu_dyn 仅 +0.143W。**

⇒ akmode 的 GPU 边际功率**全部落进 resid**，CPU 侧随 GPU 负载几乎不动。

**推论**：akmode 的 cpu_dyn 只有 **0.721Wh（27.1%）**，即使全部削掉也只有 0.72Wh；实际可削 10~20% → **0.07~0.14Wh**。且 `tuned_profiles.yaml` 里 akmode 已配 `headroom=1.15 / perf_ceil=1.0`（天花板本就拉满）。

**建议**：akmode 的省电战场在 **GPU**，不在 CPU 调度。CPU 侧只值得做 headroom 微调（akmode 1.15→1.10），收益 **0.07~0.14Wh**，主要交付物是**触档延后**（见方案 §3.2 的热模型折算）而非电量。

### 3.3 playback（15.059Wh）—— 已足够平稳，尖峰极少

**证据链**：

1. **平稳**：p5=1.252 / p50=2.605 / p95=4.521W，带宽 3.269W，峰均比 **1.74**（default 3.59）。
2. **集中度极低**：top5% 秒占 11.1%、top10% 占 18.6%（default 16.6% / 28.8%）。
3. **分层**：`gpu_busy` 在 [5,15)% 的秒占 49.3%、占电量 50.3% —— 这是**视频硬解常态带**。`gpu<1%` 的 3277s 仅 avgW 1.631（暂停/缓冲）。
4. **>5W 尖峰只有 696s**：`tmp_an204 [4]` 显示该窗口 Wh=1.266，avgW 6.548，放大倍数 功率 2.43× / gpu 2.07× / **cpu_dyn 2.93×** —— 与 default 的「GPU 合成主导尖峰」不同，playback 的尖峰是 **CPU 侧也一起抬**（可能是起播/切清晰度/弹幕突发）。但总时长仅 696s（占 playback 3.5%），**削掉一半也只有 0.6Wh，且是必要的起播开销**。
5. **CPU 很轻**：cpu_dyn 均值 **0.740W**，仅占 27.4%。

**判定**：playback 已经接近平稳最优，**没有 default 那种「尖峰可削」的空间**。可动只有恒定供给那一层：cpu_dyn 4.129Wh 削 10~20%，AMP=0.792 ⇒ **0.33~0.65Wh**。

**建议**：playback headroom（1.0→0.97）保留但**仅灰度**；真正的大头 3.67Wh 专属地板（VPU/音频/Wi-Fi/高刷）**不在调度层权限内**。

## 四、AMP 不可跨 mode 套用（重要口径修正）

`P_total = b0 + b1 · cpu_dyn` 的斜率按 mode 分别拟合（`tmp_an200 [H]`）：

| mode | AMP (b1) | R² | 判读 |
|---|---|---|---|
| default | **1.4833** | 0.615 | 与 CPU 负载共变的外围多（UI 合成、唤醒连锁） |
| playback | **0.792** | 0.286 | 外围基本恒定（VPU/音频），与 CPU 弱共变 |
| fas | **0.417** | 0.212 | 整机功率由 GPU/modem 主导，CPU 影响最小 |
| akmode | **1.020** | 0.241 | 居中 |

**⇒ 方案 §1.2 的 AMP=1.4833 是 default 专属值，不能套用到其它 mode。** 本文 §〇 的收益一律按 mode 取对应 AMP（playback 0.792 / fas 0.417 / akmode 1.020），上界才用 1.0。

（附带：GPU 偏系数 W/% 也是按 mode 分化 —— default 0.0878、playback 0.0728、akmode 0.0452、fas 0.0193 且 R²=0.015 无意义。）

## 七、不确定性（诚实声明）

1. **fas 的 cpu_dyn–fps 负相关≠因果**：更可能是「场景变重 → fps 降且 CPU 用得多」的反向因果。铁律禁止 A/B ⇒ **无法在这个数据包内证明降频不掉帧**。
2. **AMP 的 R² 偏低**：playback 0.286 / fas 0.212 / akmode 0.241 ⇒ 折算系数本身不可靠，收益区间应理解为量级估计而非点估计。
3. **`gpu_busy%` 是占用率不是功率占比**（判读铁律）：akmode GPU ≥60% 桶的 resid 高 ≠ GPU 功耗等于 resid；resid 还含 modem（游戏/视频联网）、屏幕刷新增量、模型误差。
4. **负 resid 4.24%（最小 −5.13W）** 同样污染这三 mode 的 resid 拆分。
5. **专属地板是残差推断**：+0.658W(playback) / +1.760W(akmode) 由「mode p10 − 息屏地板 − 屏幕」反推，没有直接遥测证实是 VPU/音频/Wi-Fi。
6. **三 mode 只有 24968s（6.9h）样本**，且 fas/akmode 各只有一次连续游戏会话（单包 2919s / 1936s），批间不可连读（8 次 daemon 重启）。
7. **fps 只在 fas 有非空值**（2854/2939）；playback / akmode 无帧率数据 ⇒ 这两个 mode 的流畅度回归**完全无法验证**。
8. **未做充电态**：本轮与全局一致只取 `charge==discharging`。
