## 二、归因

### 2.1 【问题 1】69% 残差（27.55Wh）里各成分的可估计份额

自顶向下，用实测地板拆（N=48209s = 13.39h）：

| 成分 | 功率 | 电量 | 占残差 | 占整机 40.04Wh | 调度层能否碰 |
|---|---|---|---|---|---|
| **A 屏幕本体**（背板+DDIC+触摸） | 0.474W | **6.35Wh** | 23.0% | 15.8% | ❌ **碰不到** |
| **B 息屏地板级外围**（静态漏电+modem 待机+PMIC+CPU 静态+模型误差） | 0.327~0.608W | **4.38 ~ 8.14Wh** | 15.9~29.5% | 10.9~20.3% | ⚠️ **部分可动，见下** |
| **C 亮屏活跃外围** | — | **13.07 ~ 16.82Wh** | 47.4~61.0% | 32.6~42.0% | 部分 |
| └ C1 GPU（偏系数口径 / 分桶上界） | — | **8.80 ~ 11.28Wh** | 32~41% | 22~28% | ⚠️ 仅间接协同 |
| └ C2 GPU 之外（modem 活跃 + CPU 静态增量 + 模型误差） | — | **1.79 ~ 8.02Wh** | 6.5~29.1% | 4.5~20.0% | ❓ 本包不可再分 |

> **B 项修正（v2，由 t2 息屏路径归因交叉触发）**：初版把 B 定死为 0.608W / 8.14Wh 并标"碰不到"，**这个 claim 过强**。t2 实测息屏 avgW 随 perf_ceil 档从 0.466W（ceiling≤0.135）变到 0.781W（ceiling≈0.30），说明息屏地板**不是物理常数，而是被当前天花板抬高的**。B 的三锚点：
> - **B1** 息屏全量低 10% 地板 0.608W → **8.14Wh**（原口径，未区分 perf_ceil 档，**上限**）
> - **B2** t2 实测息屏最低 ceiling 档均值 0.466W → **6.24Wh**（含该档已施加的天花板，推荐中值）
> - **B3** 息屏 P<0.466 子集再取低 10% 地板 0.327W → **4.38Wh**（双重选低，严格下界，偏保守）
>
> → **B ∈ [4.38, 8.14]Wh**。其中可争议部分 **3.76Wh** 由 perf_ceil / CLG 路径决定，**归 t2 / t3 的杠杆，不归本文的 up / down / 迁移杠杆**。本文后续一律用 B2 = 6.24Wh 作为中值，并在不确定度里带上 [4.38, 8.14] 全区间。
| **CPU 动态（已在账外）** | — | 12.49Wh | — | 31.2% | ✅ 主战场 |

**全景账（B 取 B2 中值）**：40.04Wh = CPU 动态 12.49 (31.2%) + 屏幕 6.35 (15.8%) + 息屏地板外围 6.24 (15.6%) + 活跃外围/误差 14.97 (37.4%)。
（B 取上下限时的另两版：B=B1 → 活跃外围 13.07 (32.6%)；B=B3 → 活跃外围 16.82 (42.0%)。）

**明确"不是自己的功劳"**：
- 调度层**直接**可控的只有 CPU 动态 **12.49Wh (31.2%)**。
- **A（屏幕）6.35Wh 是真空不动的硬地板**，任何调度改动都碰不到。
- **A + B ∈ [10.73, 14.48]Wh（26.8%~36.2% of total）**。注意这是**区间而非定值**：初版写的"14.49Wh 完全碰不到"是**上限成立、下限过强**——下限只 10.73Wh，中间 3.76Wh 由 perf_ceil/CLG 路径决定（t2/t3 杠杆）。谁把 A+B 的**上限**整块算进"调度侧可动收益"就是虚报；但也不能反过来说 A+B 全部可动。
- GPU 的 8.80~11.28Wh (22~28%) 由 GPU 侧的 DVFS/合成负载决定，ChiRi 只能通过 CPU 侧协同（减少喂帧/唤醒）**间接**削一点，不能算 CPU 调度直接收益。
- **modem 无法从本包分离**：status.csv 无 modem 字段，`batt_power_w` 里 modem 与屏幕/GPU/静态混在一起；B 里的 0.608W 息屏地板**包含** modem 待机，但无法拆出。C2 的 1.79~4.27Wh 是"GPU 之外的活跃外围"，含 modem 活跃但不可分。
- **模型误差**显式不可分离的证据：负 resid 占 4.24%（最小 −5.13W），说明 cpu_dyn 表（纯动态项、电压借自另一批次 Odin2）在重载段系统性高估/低估；`src/chiri/energy_cost.rs` 自述"只能相对排序、不做绝对功耗预测"。

**上下限怎么读**：屏幕 6.35Wh 用的是两个硬地板之差（最稳，且亮/息屏同口径相减抵消了共同的静态项）；B 用三锚点（0.327 / 0.466 / 0.608W → 4.38 / 6.24 / 8.14Wh），**取 B2 中值、全区间作不确定度**；C1 的 8.80~11.28Wh 是偏系数/分桶两个口径的差（偏系数已扣掉 CPU/psi 共线，分桶没有）→ 取区间而非点估计。C 随 B 反向变化，报 C 时必须同步声明用的是哪个 B 锚点。

### 2.3 【问题 3】launcher「idle 但不 idle」

launcher 亮屏 default：n=4808，Wh 2.86，P avg 2.14 / p50 **1.28** / p90 **5.08** / p95 7.12 / p99 9.45 / max 11.98（与题目一致）。

分布特征：gpu% avg 6.01 但 **p50=0、p75=0**、p90=27、p99=66、max=95；psi_cpu p50 12.04 / p90 31.99；wk/s p50 2890 / p90 14469 / max 28143；mig/s p50 999 / p90 6263；**ft/s p50 1403 / p90 5568 / p99 25788 / max 37462**（尾部极陡）；cpu_dyn p50 0.16W / p90 2.17W / p99 6.74W；fps 全 0。

**按 P_total 分层——"是什么在动"**：

| 层 | n | Wh | gpu% | psi | wk/s | mig/s | ft/s | cpu_dyn | resid |
|---|---|---|---|---|---|---|---|---|---|
| [0.7,1.28) | 2389 | 0.69 | 0.1 | 11.1 | 2269 | 792 | 1313 | **0.14W** | 0.89W |
| [1.28,2.5) | 1374 | 0.65 | 1.7 | 17.2 | 4558 | 1848 | 2166 | 0.44W | 1.25W |
| [2.5,4) | 377 | 0.33 | 16.0 | 25.3 | 9600 | 4236 | 4814 | 1.29W | 1.87W |

**结论：launcher 是"双峰"而非单一 idle 态。**
- **中位数层（2389 秒，占 launcher 秒数 49.7%、电量 24%）是真 idle**：gpu 0.1%、cpu_dyn 0.14W、resid 0.89W —— 这 0.89W 就是屏幕地板 + 静态 + 轻唤醒，**p50 1.28W 基本等于地板价**，没什么可削。
- **尾部（659 秒，13.7% 秒数，却占 launcher 电量 41.6%）是"伪 idle"**：gpu 30.7%、wk/s 15928（≈中位层的 7 倍）、mig/s 6488、ft/s 9044、cpu_dyn 3.05W、resid 3.45W。形态与 QQ 尖峰（gpu 55%、wk/s 14800）**高度同构** → 是桌面小部件刷新 / 负一屏 / 动画 / 图标合成一类的**周期性重绘**，不是 CPU 单干（resid 3.45W > cpu_dyn 3.05W，说明有一半功耗仍在 CPU 之外）。
- 关键旁证：launcher >4W 的秒里，**gpu<1% 的 93 秒仍有 P 6.28W、wk/s 15538** → 单靠事件流本身就能把整机拉到 6W，GPU 不是唯一必要条件。所以治理要**同时**压事件流和 GPU 参与，只压一边无效。

### 2.4 【问题 4】调度侧可动改进项与折算收益

**折算方法（无对照组，构造性）**：`收益 = 窗口秒数 × 该窗口可削减的 cpu_dyn 功率 / 3600`，再乘放大系数 AMP。
AMP = **1.4833**（P_total = 1.606 + 1.4833·cpu_dyn，R²=0.6183 的观察斜率）—— 区间下界用 1.0（只算 CPU 动态直接项），上界用 1.4833（把与 CPU 动态共线的外围一起算进来，**上界偏乐观，含共线，非因果**）。

**窗口定义与当前量**（亮屏 default 分位：cpu_dyn p50 0.477 / p75 1.160 / p90 2.445；wk/s p50 5840 / p75 10678；mig/s p50 2944 / p75 5578）：

| # | 改进项 | 窗口定义 | 窗口 | 分钟 | 窗口内 cpu_dyn |
|---|---|---|---|---|---|

## 三、改动建议（按性价比排序）

1. **优先打 QQ 的 gpu≥60% 尖峰亚型**（2085s / 5.14Wh / P 8.87W）。它是单点最大、形态最清晰的靶子。方向：QQ 前台 + gpu_busy 高位时，限制 CPU 侧无谓 up（不要再给已经 GPU 瓶颈的链路加 CPU 频率）。注意该窗口已被热限幅（cap 91.45%、cpu_temp 63.6°C），实际可削量要打折。
2. **修 launcher 尾部"伪 idle"**（659s，占 launcher 电量 41.6%）。它与 QQ 尖峰同构（gpu 30.7% + wk/s 15928 + mig/s 6488），说明是**通用重绘/小部件路径**问题，不是 QQ 独有 —— 修一次可能同时惠及多个包。且 gpu<1% 的 93 秒仍有 6.28W，说明**必须同时压事件流**，单压 GPU 无效。
3. **down 迟滞/回落加速虽然窗口最小（1851s / 1.04Wh），但它是唯一"零风险"项**：cpu_dyn 已 >p75 而 psi<15 的秒，属于忙完没降下来，削它不牺牲响应。收益 0.10~0.46Wh，小但确定。
4. **wakeup + 迁移抑制**窗口最大（174.4 分钟），但**重叠最严重**（与 A 交 6888s、与 E 交 5382s），单独报收益必然虚高；建议作为"与其它项共享同一批秒数"的联合项处理。
5. **屏幕 6.35Wh 不要动**（真空硬地板，不在调度层权限内）；**息屏地板 B ∈ [4.38, 8.14]Wh 中可争议的 3.76Wh 归 perf_ceil / CLG 路径**（t2 / t3 杠杆），本文的 up / down / 迁移杠杆碰不到它。任何"降低整机 X%"的承诺必须先扣掉 A（6.35Wh）与 B 的下限（4.38Wh）共 **10.73Wh = 26.8%**。
6. **GPU 侧本体功耗（8.80~11.28Wh）不作为 CPU 调度 KPI**：只能通过协同间接影响，建议单列观察项。

### 4.1 收益汇总（亮屏 default 40.04Wh 口径）

| 口径 | 保守（直接项） | 乐观（×AMP 1.4833） |
|---|---|---|
| 并集窗口削减 10% | 0.97Wh (2.4%) | 1.44Wh (3.6%) |
| 并集窗口削减 20% | 1.94Wh (4.8%) | 2.88Wh (7.2%) |
| 并集窗口削减 30% | 2.91Wh (7.3%) | 4.32Wh (10.8%) |
| 全局削减 10%（兜底） | 1.25Wh (3.1%) | 1.85Wh (4.6%) |

**建议对外表述**：亮屏 default 上，调度侧可动空间的现实量级是 **1~3Wh / 40.04Wh（2.5%~7.5%）**；超过 4Wh 的估计都依赖 ×AMP 的共线上界，不可作为承诺。

### 4.2 不确定性清单（按影响大小）

1. **不是对照实验**：全部为构造性折算。"削减 20%"是**假设**，不是实测；真机是否真的能降 20% 未验证。
2. **AMP=1.4833 含共线**：P_total~cpu_dyn 的斜率把与 CPU 负载共变的外围（GPU/屏幕刷新/调制解调器）也算进去了。把它当"每削 1W CPU 动态整机降 1.48W"是**上界**，真值应在 1.0~1.48 之间。R²=0.6183 也说明 38% 的方差不由该关系解释。
3. **cpu_dyn 模型未标定**：`src/chiri/energy_cost.rs` 自述表是纯动态项（DPC·f·V²，不含漏电/静态/idle-exit），电压借自另一批次 Odin2，"只能相对排序、不做绝对功耗预测"。负 resid 占 4.24%（最小 −5.13W）是模型误差的直接证据。因此 12.49Wh 这个"CPU 动态"本身有未量化误差，残差 27.55Wh 亦然。
4. **屏幕 0.474W 是差值估计**：来自两个硬地板之差，假设亮屏/息屏的 modem 与静态漏电相同。若亮屏时 modem 更活跃，屏幕份额被**高估**；反之低估。±30% 不确定度（≈±1.9Wh）。
5. **B 项是混合地板且区间比初版宽得多**：静态漏电、modem 待机、PMIC、CPU 静态、模型误差**全部混在一起**，本包无法拆分。初版只用低 5%/10%/25% 三档（0.566/0.598/0.626W）给 ±0.4Wh —— **严重偏窄**，因为那三档都取自同一个"当前 perf_ceil 已抬高"的息屏总体，无法反映天花板本身可动。结合 t2 的 perf_ceil 分档证据后，B 的真区间是 **4.38~8.14Wh（±1.9Wh）**，见 §2.1 的三锚点。
6. **modem 无法分离**：status.csv 无 modem 字段，C2 的 1.79~4.27Wh 是"GPU 之外的活跃外围"残值，含 modem 活跃但不可分。
7. **GPU 归因区间宽**：8.80Wh（偏系数）vs 11.28Wh（分桶 Δ），差 2.5Wh。分桶口径含 CPU/psi 共线（gpu 高的秒 CPU 也高），偏系数口径 CPU 系数为负（−0.2162）明显是共线伪影 → **两个口径都不可当点估计**。
8. **gpu_busy% 是占用率不是功率占比**：不能按 gpu% 线性拆功率（判读铁律）。GPU 功耗还取决于频率/带宽，日志里没有 GPU 频率。
9. **fps 全 0**：`fps` 列在本包未上报，"UI 刷新风暴"这一假设**既不能证实也不能排除**；尖峰归因里的"GPU 合成主导"是基于 gpu_busy + 事件流耦合的推断。
10. **尖峰已被热限幅压制**：尖峰秒 cap 91.45% vs 稳态 95.10%、cpu_temp 63.6°C，实测值是被压后的值 → 削峰空间比数字看起来小，收益应打折。
11. **package 归因是前台包名**：status.csv 的 package 是当前前台/焦点包，后台唤醒混在里面；QQ 的 17.65Wh 不等于"QQ 自己用的电"。
12. **8 次 daemon 重启**：cap 序列不可跨批次连读；本文所有聚合都做了跨批合并，但批次边界处的 cap 阶跃未单独剔除。
13. **充电行已剔除**（charge==discharging 过滤）亮屏充电 10595 行未参与，若产品关心插电场景需另算。
