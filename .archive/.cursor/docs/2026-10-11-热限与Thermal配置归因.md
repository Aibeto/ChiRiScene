## 1. 证据

### 1.0 口径（先把易错点钉死）

1. **批次不可连读**：8 个批次目录名 = 该会话**结束**（下一次 daemon 重启）时刻，链条为 05:15→14:48→19:32→00:10→05:07→14:13→18:57→23:09→00:09；1010-000959 与 1011-000901 跨零点，时间戳按 +86400 修正。所有档位秒数均为**批次内 dt 加权**（相邻 status 行时间差，钳到 ≤5s），不跨批次拼接。
2. **重启只重置「解除斜坡状态」**：`thermal_cap_current` 是热块局部状态，重启后第一个 2s 热块就按温度重判并**直接落到正确档**——证据：x_devimp_1011-000901 会话 23:09:36 起，首个事件是 23:09:38 的 `cap=60 batt=43.5`（无 0.85 过渡）。因此「重启造成的假 100 档」不存在，但因温度仍高、档位可跳级，跨批次 cap 序列确实不可连读。
3. **cap 是 perf 索引，不是 hw 频率百分比**：写入频率 = `find_floor_freq(cl, cap)` 向下取档 ⇒ 0.85 档实际是 little 1670400（hw 的 83.0%）、big 2457600（87.7%）、prime 2726400（85.6%）；0.60 → 1228800/1785600/2092800；0.40 → 902400/1401600/1593600。
4. **tick 行只在 CLG 驱动的窗口出现**（default 为主）；tuned 驱动的 playback/akmode 段几乎无 tick（全包仅 2 行）⇒ 判 tuned 侧是否被压必须走 snap 行（cap 列在 snap 里有值）。
5. tick 每簇约 123-190ms 一行（little 6.3/s、big 8.1/s、prime 5.3/s），故 tick 的「占比」是时间占比、「钉死」是时间占比，不是行数巧合。

### 1.2 [Q2] 0.85 档是否空转 + decide-vs-actual 交叉

**判据链（三层，互相独立取证）：**

1. **决策侧（tick 行，`cur_perf` = 钳制前决策，`cur_freq_khz` = 写入值）**
   - cap=85 窗口内 `cur_perf > 0.85` 的采样：little 3576/30827 = **11.6%**、big 2105/32715 = **6.4%**、prime 1869/23434 = **8.0%**。
   - 这些「想要更多」的采样里，写入频率**正好等于天花板值**的比例：little **92.3%**、big **92.4%**、prime **92.8%**。
   - 全部 tick 行中 `cur_freq > 天花板` = **0.0%**（所有 mode×簇×档）。比值直方图在天花板处形成硬墙：little 80-85% 4071 行、big 85-90% 2157、prime 85-90% 1938，其上一格直接为空。
   - ⇒ **0.85 档不是空转**：想要越线的秒有 6-13%，其中九成以上被真正钉在 85% 天花板上。
2. **读回侧（clamp_change 行，`smax` = 直接读回 scaling_max_freq）**
   - cap=85 窗口共 2664 次/簇快照：smax 越过天花板仅 **2 次（0.08%）**，正好等于天花板 355(little)/50(big)/90(prime) 次。
   - cap=60：1965 次/簇，越线各 6 次（0.3%），钉住 545/588/190；cap=40：173 次/簇，越线 1/1/0，钉住 78/153/33。
   - 硬件热压（`dcvsh < hwmax`）只在 cap=85/60 的 big(65/45)、prime(52/38) 少量出现 ⇒ 本包几乎没有 LMh 硬件热压参与。
3. **实际频率侧（snap 行，`cpu_cur_khz` = 真机频率）**
   - 全部 mode×档×簇 `cpu_cur > 天花板` = **0.0%**（5385 个 cap=85 default 秒全数通过）。
   - `cpu_max == 天花板`（= 热档天花板就是当时的绑定上限）占比：default cap=85 → policy0 **10.7%**、policy3 1.9%、policy7 3.7%；cap=60 → 40.3/44.4/18.1%；cap=40 → 52.8/94.3/34.9%。

**结论**：软限 0.85 档**有实效但不强**——cap=85 窗口内约 6.6%（big）/13.2%（little）/8.3%（prime）的秒被真正压在天花板；其余 ~90% 的秒 CLG 本来就只想要 85% 以下（cap=85 窗口内 `freq/max` 均值仅 0.446/0.503/0.298），这正是 feature.yaml:142-143「实测命中率 13.8%」同一现象在本次包的重现（本次算得 6.6-13.2%，量级一致）。**「cap=85 ≠ 已压制」的铁律在数据上成立：进入 85 档不等于普遍被压，只有一成左右的秒真被咬住。**

### 1.3 [Q3] hysteresis 与 cap 迁移时间线

**实测跳闸/解除点（thermal_change 事件 `batt=` 字段，全包 31 个事件）：**

| 迁移 | 阈值（配置） | 实测 batt | 批次数 |
|---|---|---|---|
| 100 → 85（软） | ≥41.0 | **41.0**（1011-000901 首事件 43.5 直落 60） | 7 |
| 85 → 60（中） | ≥43.0 | **43.0** | 6 |
| 60 → 40（硬） | ≥45.0 | **45.0** | 1 |
| 60 → 75（中解除） | <43−1.5 = 41.5 | **41.4** | 6 |
| 75 → 85 | 斜坡 | +2.0s | 6 |
| 40 → 55（硬解除） | <45−2 = 43.0 | **42.9** | 1 |
| 55 → 60 | 斜坡 | +2.1s | 1 |
| 85 → 100（软解除） | <41−3 = 38.0 | **37.8 / 37.9** | 7 |

- 三个解除点全部**严格低于**各自的理论解除阈值，且从不跨级跳改 ⇒ `eval_thermal_cap`（src/chiri/mod.rs:168-178）的语义与线上行为一致。
- normalize（src/chiri/config.rs:1261-1274）的 `hyst_mid ≤ mid−soft` 检查：1.5 ≤ 2.0 ✔ ⇒ 中档解除点 41.5℃ **≥ 软限 41℃**，铁律里担心的情况在 8550 上不存在（该检查在别的机型缺省 3.0 会被自动钳到 2.0 + warn）。
- 档内驻留：软档 85 从触发到升中档 173-520s（3-9min，取决于负载）；中档 60 从 43℃ 到 45℃ 仅 284s（唯一一次硬档）；解除段更长（冷却慢）：60→75 用 361-1476s、85→100 用 420-1040s。

**75/55 档（12/3 个样本）是什么**：解除方向由 `THERMAL_UNPRESS_STEP=0.15` 每 2s 热块抬一次（src/chiri/mod.rs:3537-3541），于是 0.60 →(2s) 0.75 →(2s) 0.85，0.40 →(2s) 0.55 →(2s) 0.60。这与数据完全吻合：

- 6 个批次各出现 **恰好 1 个 2s 的 75 档**（× 2 条采样行 = 12，正是 power.txt [4] 的 12）；
- 只有 1010-230936 出现 **55 档 3s**（2s 台阶 + 1s 采样边界）；
- 7 次 75→85 事件间隔实测全为 **+2.0s**，55→60 为 **+2.1s**。
⇒ 75/55 **不是独立档位、也不是抖动/震荡**，而是「解除限速」的确定性中间台阶；把它当档位统计会误判为「系统性抖动」。

补充：0.85 → 1.0 只需一步（0.85+0.15 正好到 1.0），所以软档解除不产生中间台阶——这也是为什么只有 75/55、没有 70/90/95。

### 1.4 [Q4] clamp_heavy / tuned_thermal_floor / tuned 段如何判断被压

**(a) clamp_heavy=true 确实在起作用（且这次的量化很扎眼）**

- 旧豁免带 (0.95, 1.0] 内的采样：cap=85 窗口中 `cur_perf > 0.95` 占 little 7.1%、big 4.4%、prime 5.6%。
- 而「想要 >0.85」的采样占 11.6%/6.4%/8.0% ⇒ **被钳命中样本中 61%(little)/69%(big)/70%(prime) 正落在旧豁免带内**。
- 这些采样**全部**仍被写到 ≤ 天花板（越过率 0.0%）⇒ free_above 豁免在 clamp_heavy=true 下**确实被完全旁路**，与 feature.yaml:152-156 的声明一致。
- 反过来说：若哪天把 clamp_heavy 关掉，0.85 档的实效会**损失约三分之二**。free_above=0.95 当前是**死配置**（只有 clamp_heavy=false 时才被读取），不构成自相矛盾，但两个键并列极易误读为「95% 以上不钳」。

**(b) tuned 侧（playback/akmode）有没有被压——间接判据**

题面「热态下 tuned 段 cap 列恒 `-`」只对 **tick 行**成立（tuned 不走 CLG，无 tick：全包 playback/akmode 的 tick 仅 2 行）。**snap 行（1s 全量快照）在 tuned 段有 cap 列**，且 carry `cpu_cur/cpu_max/cpu_min`，这就是间接判据：

| mode | 档 | snap 秒 | cpu_max 峰值 | 天花板 | cpu_max=天花板占比 | cpu_cur>天花板 |
|---|---|---|---|---|---|---|
| akmode | 100 | 1759 | 2016000 | 2016000 | 16.6%(p0) | 0.0% |
| akmode | 85 | 195 | 1670400 / 2188800 / 2476800 | 1670400 / 2457600 / 2726400 | **47.7%(p0)** / 0% / 0% | 0.0% |
| playback | 100 | 25547 | 2016000 | 2016000 | 0.3% | 0.0% |
| playback | 85 | 753 | 1670400 | 1670400 | 9.2%(p0) / 0% / 0% | 0.0% |
| playback | 60 | 1508 | 1228800 / 1785600 | 1228800 / 1785600 | 0% | 0.1-0.2% |

⇒ tuned 侧确实收到并执行了 `min(1.0, max(cap, tuned_thermal_floor))`：akmode 在 cap=85 时 little 天花板被写到 **1670400**（正好 0.85 档天花板），近半秒数它就是绑定上限。playback cap=85 的 policy7 有 0.1% 秒、cap=60 的 policy0/3/7 有 0.1-0.5% 秒越线（峰值回落到 hw max），集中在 cap 变更那一两个 2s 周期（tuned/CLG 同块下发，1s snap 可能落在变更前），是瞬态而非长期失效。

**(c) tuned_thermal_floor=0.55 本包零行使**

- cap=40（硬档）合计 557s **全部** mode=default，playback/akmode 在硬档为 **0 秒** ⇒ `max(cap, 0.55)` 这条兜底在 39.8h 内从未被触发。
- 它的正确性只能靠构造性自检：cap=0.40 时 tuned 有效上限 = max(0.40, 0.55) = 0.55（比 CLG 的 0.40 宽），normalize 保证 floor ≥ hard_perf_cap（config.rs:1275-1281）。保留即可，但不能声称「本包验证过」。

### 1.5 [Q5] 热模型与功耗结构（折算的基础）

**(1) 升温模型（离线回归，status.csv 1s 行，60s 分桶 + 10min 滑窗，仅放电+亮屏+温度<40.8℃）**

```
dT/dt [℃/min] = 0.0600 · P_batt [W] − 0.0517     (P0 = 3.29W, r² = 0.20, n = 504 窗口)
各批斜率 b: 0.0939 / 0.0271 / 0.0846 / 0.0736 / 0.0780 / 0.0239 / 0.0618  (0.024–0.094)
```

即：**整机平均功耗每降 1W，升温速率降 0.060℃/min ≈ 3.6℃/h**（批间散布 4 倍，r² 偏低，见 §4）。

## 2. 归因

1. **热压制的性质**：不是「偶发异常」，也不是「持续常态」，而是**由高负载使用驱动的、每会话必到的背景机制**（7/8 会话、8 段、每段 12-34min），其时间占比被**充放状态**主导：放电期 4.03%、充电期 48.95%。把 8.62% 当「热压时间」是口径错误。
2. **触发条件单一且可预测**：唯一判据是电池温度（CPU 温度只写进事件文本，src/chiri/mod.rs:3524-3526），跳闸点实测精确落在 41.0/43.0/45.0。因此「少触发」只能通过**降低触及 41℃ 之前的整机功率**或**抬高阈值**（安全代价）实现，没有第三条路。
3. **四级配置没有逻辑矛盾，但有 3 处「死配置/边界脆弱」**：
   - free_above=0.95 在 clamp_heavy=true 下不被读取（钳制形态已改为恒钳）；实测被钳样本 61-70% 落在该带内，说明这个键**不再是路标**，误关 clamp_heavy 会掉 2/3 实效。
   - hysteresis_hard_c=2 **正好等于** normalize 上限 hard−mid=2（config.rs:1270-1274）⇒ 配置在这两个温度键上零余量，任何 batt_mid/batt_hard 微调都会被静默改写（仅 warn）。
   - tuned_thermal_floor=0.55 只作用于硬档，而硬档在 tuned 段本包 0 秒 ⇒ 未经验证的保护。
   - 另：cpu_soft/mid/hard=90/92/95 与压制判定完全无关（代码只读电池阶梯），是历史冗余，注释已声明，不算矛盾。
4. **四级在边界上「刚好接棒」**：软解除 38 < 中解除 41.5，中解除 41.5 > 软跳闸 41，硬解除 43 == 中跳闸 43（靠中档「本级仍压住 且 ≥41.5」的持有条款闭合）。链条闭合但无余量——这正是每次解除都精确出现一次 2s 台阶的原因。
5. **改进空间的结构性上限**：放电期 CPU 动态功耗只占整机 27-30%，充电期仅 2-5%（外围屏幕/modem/GPU/充电通路占大头，见前提文档判读要点）。所以「调度侧降功耗 → 少触档」在**放电期**最多撬动 ~30% 的发热源，在**充电期基本无效**。

## 4. 折算收益区间与不确定性

### 4.1 折算公式（离线，不新增 A/B 对照）

```
r  = 0.1439 ℃/min                     # 实测 37→41℃ 斜坡
r' = r + b · ΔP,  b = 0.0600 ℃/(min·W)   # 合并回归（批间 0.024–0.094）
Δt(触档延后) = (41−37)/r' − 27.7 min
```

| 整机 ΔP | Δt（合并 b=0.0600） | Δt 区间（b=0.024~0.094） |
|---|---|---|
| −0.2 W | +2.6 min | +1.1 ~ +4.3 min |
| −0.3 W | +4.1 min | +1.6 ~ +6.9 min |
| −0.5 W | **+7.4 min** | **+2.6 ~ +13.6 min** |
| −1.0 W | +20.0 min | +5.7 ~ +52 min（外推，超出线性区，不建议采信） |

**怎么把 CPU 侧收益换算成整机 ΔP**：ΔP_batt ≈ ΔP_cpu × 3.3~3.7（实测 2.107/0.641、2.405/0.657、4.895/1.320）。举例：

- default 场景 CPU 动态功耗 −10%（0.064W）→ 整机 −0.21~0.24W → **触档延后 +2.6~3.0 min**；
- default 场景 CPU 动态功耗 −25%（0.16W）→ 整机 −0.53~0.59W → **触档延后 +7.5~8.4 min**；
- akmode 场景 −10%（0.132W）→ 整机 −0.44~0.49W → **触档延后 +6~7 min**。

**「少触发」的两种收益形态**（不要混为一谈）：

1. **延后**（确定性）：每段热限的起点后移 2.5~13.5min（中值 7.4min @ −0.5W），温度峰值与驻留时长同步下降；
2. **整段避免**（需要条件）：首触时间分布 34.5/149/191/258/369/486 min，若某次使用在「原触发点 ~ 原触发点+Δ t」之间结束，则该段完全消失。以最短的 34.5min 会话为例，+7.4min 不足以避免（34.5+7.4=41.9min 仍在会话内）；要整段避免需要 ΔP ≥ −1W 级别或更长的连续低功耗窗口。**因此不要按「避免次数」承诺收益**。

### 4.2 不确定性（必须随结论一起给出）

1. **b 的批间散布 4×**（0.024-0.094），源自环境温度/壳体散热/屏幕亮度差异 ⇒ 同一 ΔP 的延后时间可能差 3 倍以上；本包只有 2 个批次能取到干净的 37→41℃ 斜坡，样本少。
2. **r²=0.20**：batt_temp 的升温还受 GPU/屏幕/环境温度影响，模型只解释了 1/5 方差；结论应表述为「量级/方向可信，绝对值 ±3 倍」。
3. **soc.yaml 的 power_w 只含动态项**（soc.yaml:189-190 明示「只能用于相对排序」）⇒ §1.5(4) 的 1.43Wh 是下界，含漏电/电压轨效应后可能 2-3×。
4. **充电期不可折算**：发热主体是充电流通路（7.3-25.2W），CPU 侧仅占 2-5%，任何调度侧改动都不能用上面的模型换算。
5. **本项目禁止 A/B 对照实验**（.cursor/docs/2026-10-11-分派共同前提.md 铁律 + agentsdocs/04-hard-lessons.md）⇒ 上述收益全部是离线重放/模型折算，落地后只能用「同版本同场景观察」验证方向，不能用差值判据。
6. **未验证项**：tuned_thermal_floor=0.55（本包零样本）、FAS 活跃期（本包 2952s）无热保护这两个行为本包均无法证伪或证实。
