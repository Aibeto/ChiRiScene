## 2. 【P0】8650/PJX110：tick 行去重 key 冲突导致日志翻倍写

**现象**：213457 包 tick 行合计 **360.6 万行**，其中 `big` 占 **284.7 万行（79.0%）**。分 mode×cluster 的密度（tick 行数 ÷ 同 mode 的 snap 行数 ≈ 每簇每秒行数）：

| mode | little | big | prime |
|---|---|---|---|
| default | 5.84 | **11.96** | 2.42 |
| playback | 6.67 | **50.03** | 1.68 |

对照同版本 Pixel（3 policy）与老版本 8550（3 policy），三簇密度均衡（default 5~6、playback 6~9.5），**只有 8650 的 big 出现 2×（default）~7.5×（playback）**。

**根因**（源码已定位）：

- `8650/soc.yaml:9-12` 把 CPU2-4 与 CPU5-6 两组 A720 并进同一个 `big` 组，但它们各自是一个 cpufreq policy（policy2 / policy5）→ **4 个 policy 判出 3 个簇名**。
- `src/logger.rs:789` 的 tick 节流表 `MAIN_TICK_STATE` 以 **cluster 名字符串**为 key（`logger.rs:793`）。两个 `big` policy 共用同一表项、互相刷新签名 → 每次比对都不同 → **双双每拍落盘**。
- 决策周期：default 160ms（6.25/s）、tuned(playback/akmode) 40ms（25/s，由 `cpu_monitor.rs:21 SAMPLE_MS_TUNED`）。25×2 = **50.03 行/s**，与实测完全吻合。

**连带后果**：

1. devimp 日志体积约翻倍（`main_*.log` 行数 360 万）→ 更快撞 128MB/日志预算 → 本包 28 小时内 9 次归档重启，而每次重启都把热状态重置回 cap=100。
2. daemon 自身 CPU 抬升（见 §1）。
3. 分析侧随之变慢（dvrun 全流程在 150MB 包上跑数分钟）。

**修法**：`MAIN_TICK_STATE` 的 key 由「cluster 名」改为「policy 唯一标识 + cluster 名」（如 policy 首核号），调用侧 `cpu_load_governor.rs:663-680` 与 `tuned.rs:589-619` 同步传入。改后 8650 的 big 密度应与 little/prime 同档。

## 3. Pixel/zumapro：CPU 温度列缺值（**不是缺陷**，2026-10-04 撤回）

> **本节 2026-10-03 曾判为 P0「CPU 温度源缺失导致热保护失效」，按「压制只看电池温度」的既定口径撤回。**

**现象**：

- `1003-214440` 的 `status.csv` **cpu_temp 列全文为 `-`**（缺值），batt_temp 正常（24~40℃）。
- `thermal_cap_pct` **73161 行全部 100**，`[4]/[5]/[6]` 段无任何 85/60/40 档秒数，`thermal_change` 事件 0 条。
- 阈值核对：`zumapro/feature.yaml:61` `batt_soft_temp_c=41`，而本包电池最高 40℃ → 按电池这条唯一判据，全程不越线，cap 恒 100 是预期结果。

**代码侧已对齐该口径（2026-10-04 改动）**：`mod.rs` 的 cap 判定分支删掉 CPU 阶梯，只构造电池阶梯 `ThermalLadder` 参与四级判定；`config.rs` 的 `[hyst_invariant]`（中/硬档解除点不得低于下一档跳闸点）随之只对电池阶梯取 room，回滞不再被 CPU 阈值牵连。CPU 温度仍写 snap / status.csv / `thermal_change` 事件文本，性质是遥测。

**遗留（低优先，未做）**：

1. `clg-thermal-no-sensor`（`mod.rs:1594-1596`）是 **debug!**，1s 采样点（`mod.rs:1938-1942`）用 `.ok()` 静默吞错，`TempFilter` 量程门（`mod.rs:108-134`）静默丢弃不合理读数 → CPU zone 到底存不存在、单位对不对，运行期看不出来。现在只影响遥测列完整度。
2. `scripts/devimp/dvcommon.py` 的 `avg()/pct()` 空样本返回 **0.0**，报告会渲染成「恒温 0.0℃」。已补注释提示回原始列确认是 `-`，行为未改。

## 4. 【P1】CLG 升降频数量悬殊（棘轮），三 SoC 同状

**数据**（tick 行 decision 分布）：

| 包 / 场景 | hold | up | up_wait | down | down_wait | up类:down类 |
|---|---|---|---|---|---|---|
| 213457 default `com.tencent.mm` | 103476 | 91018 | 51936 | 3699 | 1873 | **25 : 1** |
| 213457 default `-` | 93759 | 75875 | 44466 | 2556 | 1037 | **22 : 1** |
| 220345 default `com.android.incallui` | 19285 | 41374 | 8479 | 5368 | 2786 | **6 : 1** |
| 220345 default `com.autonavi.minimap` | 18559 | 51391 | 13586 | 6563 | 3293 | **6 : 1** |
| 214440 default `com.dragon.read` | 42749 | 41626 | 19090 | 10391 | 3194 | **5 : 1** |

`deb_up`（= `up_wait`）最大连续值达 522（213457 `com.tencent.mm`）、508（`com.android.launcher` 同包），`deb_down` 多在 10 以下 → 这些段里**几乎没有一个 tick 落到降侧**。

**这不是阈值不对称**（三个 SoC 的 default 档 `down_rate_limit_ticks=2` < `up_rate_limit_ticks=3`），源码侧的结构性原因：

| # | 位置 | 机制 |
|---|---|---|
| ① | `cpu_load_governor.rs:205-211, :410` | 簇内取 **max(util)**，一个核跑满就顶住整簇的 target |
| ② | `:537, :544` | 升侧是**渐近逼近**（`current_perf += Δ×α`），负载恒定时 current_perf **永远低于 target** → 每 tick 都进 up 分支并把 `down_wait` 清零（`:522`） |
| ③ | `:569` | down 执行后 `current_perf` 被放回 ≤ target 的位置 → 下一 tick **立刻重建一个 up**，「降一档、回半档」，无驻留带 |
| ④ | `:530-545` | up 分支不清零自己的 `up_wait` → deb_up 失去「确认进度」语义，单调涨到 500+ |
| ⑤ | `:584-591, :653-655` | 触摸 floor 是唯一免确认/免 dwell/免死区的即时抬频，直接改写 `current_perf`；8650 上 **policy2 与 policy5 同判 big，同时被抬** |
| ⑥ | `:440-472, :610-615` | `steady_decay` 是唯一回落机制，但触摸窗口内不叠加、`util ≥ up_threshold(0.88)` 立即清零、上限仅 0.20 |

**建议改动（按风险升序）**：

- **A（读口径）**：up 分支执行后清零 `up_wait`，让 deb_up 恢复语义，可作为棘轮的在线指标。
- **B（低成本行为）**：引入「降后驻留」——down 执行后 N tick 内禁止再抬（`N = down_rate_limit_ticks`），打破降一档回半档的净上漂。这是 §4 里收益最大、风险最小的单点。
- **C（8650 专项）**：触摸 floor 在 policy2/policy5 双 big 上重复生效，需明确「按 capacity 只取一组」还是「两者并用」并写成契约；若只取一组，worker 写频次数同步下降。
- **D（需再取证）**：簇内 max → 次高/p90 混合；`write_deadzone`（现 0.03 代码默认，三个 SoC 均未配）在 8650 上试 0.04~0.05 看 hold 占比变化。该项属决策语义变更，**先做离线评估再动**，且按 2026-09-28 口径不得用 A/B 判据。

## 5. tuned 侧写频（**评估后不改**，2026-10-04）

- 决策周期 40ms（25/s per policy，8650 上是 4 个 policy），每周期只写 `scaling_max_freq`（`tuned.rs:440`）。
- `FastWriter` **没有上次值缓存**（`utils.rs:442-450`），`write_value_force` 每次都 seek+write；同值短路只存在于 CLG（`cpu_load_governor.rs:143-147`），tuned 侧没有对应判断。
- `tuned.rs:546` up 分支的 `gated_write` 返回值被丢弃（down 分支 `:571` 有 `if`）。**2026-10-03 报告里「目标持续满足时每 tick 重试同一个 target」这句是错的**：进 up 分支的前提是 `target_max > current_max + hyst_freq`，写成功后 `current_max` 前移到 `target_max`，同一 target 不再满足该条件，不存在重复写。
- 播放态 tick 里 `hold` 约占一半（213457 playback: hold 475005 / 总 669349），即约一半周期本无写频动作，决策仍在全速跑。

**开销评估（2026-10-04）**：会连续重试的只剩两种——写失败（`last_failed`）与被 dwell 翻摆延迟；后者在 `gated_write` 里于 syscall 之前就 return false。加 `if` 的成本是 ns 级（返回值已在寄存器），比重试路径（µs 级 syscall）小得多，但 **up 侧没有任何状态迁移依赖该返回值**（down 侧才有：`down_since` 写成功才清），加了也只是个空操作分支 → **不改**，保持丢弃返回值的写法。

## 6. 【P1】FPS 探针 perf_event_open 失败 217 次（跨三包）

`[monitor::fps_monitor] PID 切换失败: perf_event_open failed`：214440 **124 次**、220345 **85 次**、213457 **16 次**。

后果：点是进程级 uprobe（见命令文件播放态帧信号条）——同 app 多进程交替占坑（实测同秒 `9913→18144→9913` detach/attach）→ **直方图实际只覆盖当前挂着的那个进程**，长尾/占优簇的代表性有缺口。这是已知现象，本次给出量级。

**2026-10-04 裁决：暂缓不动**，只留记录。候选修法（同一 pid 退避 N 秒 + 失败计数落 status.csv）待需要时再取；判读时记住 `[7]` 段长尾率可能被漏采抹平，别读成「该时段无卡顿」。

## 9. 处理结论（2026-10-04）

| # | 项 | 裁决 | 落地 |
|---|---|---|---|
| 1 | tick 节流 key 冲突 | 修 | `logger.rs` `MAIN_TICK_STATE` 改两级 `policy_id → cluster 名`，`main_tick` 加 `policy_id` 首参；CLG 传 `cluster.policy_id`，tuned `ClusterState` 加 `policy_id`。待下包复核 8650 的 big 密度 |
