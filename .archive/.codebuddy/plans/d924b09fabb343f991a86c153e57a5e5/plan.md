**R5 的判读规则**（基准 = 图③：8 核 6720 组合 / 每个总算力档位取最小总功耗的 46 点下凸前沿）：

- 工作点 = (总算力 Mdmips, 总功耗 W)；建议成立的条件只有两条：等算力降功耗、或等功耗升算力。
- 前沿上的放置顺序：**先 big 低频段（499200→614400 一段 3655 Mdmips/W），little 低频段交替插入；prime 只在算力需求顶到前沿末端时才出现**（2092800→3187200 只剩 600 Mdmips/W）。
- 只在"某核单位算力能效更高"这类非前沿口径上成立的结论，一律不采纳——那只是前沿的输入，不是前沿本身。

**R5 的地位（2026-09-28 用户定调）**：前沿不只是评审判据，而是**调度内核的目标函数**——CLG 选点、affinity 放置、FAS 档位与特调下探，都要以"**等算力下的总功耗最小**"为准绳；凡与该目标冲突的既有做法，都要按 R5 重新评估（3.3 是放置侧的落地方案）。

**R7（v14 新增）·模式语义 = 前沿上的取点，不得用封顶表达差异**：

- `reduce` / `default` / `boost` 三个模式**对应同一条帕累托前沿上的三种取点策略**（对应"最低功耗 / 成本最优 / 功耗宽松"三种偏好），**不是三组彼此无关的拍脑袋参数**；
- 三个模式**一律不许封顶**：模式差异只能通过 ①**取点**（目标档/目标簇）②**到达速度**（升频审批、下探步长、滞回带宽）③**降权**（uclamp）表达；`perf_ceil`/`headroom<1` 在任何模式下都不许出现（R2）；持续满负载在任何模式下都必须能写到硬件最高频（R1）；
- 目标是"**在保证流畅度的前提下省功耗**"——流畅度是第一约束，省电是目标函数（不是反过来）；
- 模式差异还体现在**取点的预判提前量**上：在临界点（需求跨桶 / 落点贴顶）之前就扩大允许集形成"交叠带"以便平滑切换——**以 default 为基准，reduce ×0.5、boost ×2，单位 = 需求百分比**（用户定）；**需求下降时做对称操作**（提前纳入更省的一侧、把待离簇降级为待撤）。

**R6（v10 新增）·放置类动作的两条护栏**：

- **必须过现有三道时间闸**：`MIN_MIGRATE_INTERVAL` 4s、`REPIN_DEBOUNCE` 8s、`RETURN_COOLDOWN` 16s（`affinity.rs:118-129`）。新增的放置/迁移动作**不得绕过、不得改小**这三道闸——它们是为打破 A→B→A 乒乓而存在的。
- **必须成对给出滞回**：任何新增门槛都要同时给"进入"与"退出"两个阈值（现成范例：`FG_BUSY_UTIL_PCT` 30 / `FG_BUSY_RELEASE_UTIL_PCT` 15、`LITTLE_HIGH_WATER` 0.70 / `KEY_BIND_RELEASE_WATER` 0.50、`DEMOTE_UTIL_PCT` 5 + `DEMOTE_STREAK` 3，`affinity.rs:135-147`），且**阈值跨度 ≥ 一个频档的等效 util 差**（沿用"死区必须 ≥ 相邻档步长"的既有教训）。
- 只改"到达速度/落点倾向"、不设天花板，与 R1/R2 一致。

**R3 的边界（v12 补，防执行时走回 A/B）**：允许的是**观察**——同一版本、同一场景、不并行对照、不控制变量，只记录现象与指标；不允许的是**对照实验**——并行或交错对比两个版本/两个配置、以差值做判据。凡"开/关某配置比功耗"的做法都算 A/B，一律不做。

**回退流程（v12 补，最小要求）**：每条改动上线前必须写清 ① **回退触发条件**——落到可观测项（掉帧、首帧/启动时长、绑定变化率、功耗分位），不许写"变卡了""不跟手"这类无法判定的表述；② **回退动作**（配置项/字段级可逆）；③ **回退后留档位置**。三者缺一，视为"未定义回退"，不排期。

**什么算天花板**（R2 的判定标准）：

| 形式                        | 为什么算                                                  | 查法                        |
| --------------------------- | --------------------------------------------------------- | --------------------------- |
| `perf_ceil < 1.0`           | 直接限制上限                                              | 搜 `perf_ceil`              |
| `headroom < 1.0`            | 目标 = util × headroom，util 最大 1.0 → headroom 就是上限 | 搜 `headroom`               |
| 抬高 `scaling_min_freq`     | 阻止降频，方向相反                                        | 除 FAS 锁频机制外不应出现   |

## 1. 读通算法后的三个结论（决定了方案怎么排）

### 1.1 CLG 的稳态频率等于 util，门槛类参数不改稳态

- 稳态公式：`写入上限 = clamp(util × headroom(util), perf_floor, perf_ceil)`，再向下对齐到档位。
- `headroom` 三个分支在 `headroom_factor = 1.0` 时全是 1.0 → `target ≡ util`；8550 `default` 档现在正是 `headroom_factor: 1.00`。
- 因此 `up_threshold` / `up_rate_limit_ticks` / `up_jump_threshold` / `smoothing_up` / `slow_up_scale` / `down_threshold` / `down_rate_limit_ticks` / `down_fast_threshold` / `write_dwell_ms` / `write_deadzone` **全部只影响到达速度或抖动期峰值**，不改稳态落点。
- 能改稳态落点的只有：`perf_floor`（下限）、`perf_ceil`（R2 已禁）、`headroom < 1`（R2 已禁）、热钳 `cap`（非策略手段）、触摸地板（只会抬升）。

### 1.2 CLG 的 util 是自算的，uclamp 走的是另一条通道

- CLG 的 util 由 eBPF `sched_switch` 记账自算（`busy/(busy+idle)`），**不含 uclamp 钳制**。
- 所以 `uclamp.max` 不改变 CLG 写入的上限，但会改变 `schedutil` 选出的**实际频率** → **用 uclamp 降权仍能省电，走"实际频率"通道**。

### 1.3 三个调度器的「稳态下探」能力不对等

| 调度器     | 稳态由什么决定                                                              | 能否在稳态下探                                                 |
| ---------- | --------------------------------------------------------------------------- | -------------------------------------------------------------- |
| CLG        | util（见 1.1）                                                              | **不能**（只能靠天花板或热钳，前者被 R2 禁）                   |
| 特调 tuned | `util × headroom`，**升频无确认、立即写**；只有降频有 `down_hold_ms`        | **不能**（唯一乘性旋钮 headroom 被 R2 禁，`perf_ceil` 也被禁） |
| FAS        | 帧率闭环 PID + **稳态衰减**（帧稳后按步长下探），平衡点 ≈0.70 或 PID 托底处 | **能**（`steady_decay_*`）                                     |

**结论**：在 R2 之下，CLG 与特调**没有可用的稳态降功耗手段**；要真降功耗只有三条路 —— ① uclamp 降权、② 放置/绑核、③ **补一个 FAS 同类的「稳态下探 + 严格升频审批」（T11）**。

关键读数：

- **同簇内能效随频率单调劣化**：同一核上每加一档，算力/mW 就往下掉（A510 4352→2113、X3 3142→1060）→ 同簇内最省点永远在最低档，跨簇才存在取舍。
- **低频段排序**：A710 5405 ＞ A715 4804 ＞ A510 4352 ＞ X3 3142（各自最低档）；**高频段排序翻过来**：A510 2113 ＞ A710 1862 ＞ A715 1662 ＞ X3 1060。
- **等算力锚点**：同一份算力（657 vs 652 Mdmips）在 A510 2016000 上只有 2113 算力/mW（0.311 W），在 A710 940800 上是 4234（**0.154 W**）→ 同算力大核功耗只有一半。
- **X3 门槛**：X3 的算力必须靠 1132800 以上才兑现，那一段能效 2618→1060，全在前沿内侧；单核算力需求 **>2600 Mdmips** 才值得上。
- 以上只是**前沿的输入**：跨簇怎么放、放到哪一档，一律按第 2.4 节的前沿判据决定，不按这里的单核排序拍板。

### 2.2 真机 capacity 口径（**文档已于 2026-09-28 勘误**）

换算方式：内核 `cpu_capacity` 是「各自最高频处的相对性能」（prime 归一化 1024），**不是每 MHz 速率**，故真机算力 = `cpu_capacity × f / f_max`（真机 capacity 280/855/1024）。把 DT 的「算力/mW」折算到「真机容量单位/mW」要**除**系数 `dmips_mhz × f_max ÷ (1000 × cpu_capacity)`：little **2.347**、big **2.272**、prime **3.187**（等价于 little ×0.426、big ×0.440、prime ×0.314）。

| 核心 | 低频段（容量单位/mW） | 高频段（容量单位/mW） |
| ---- | --------------------- | --------------------- |
| A510 | 1.855                 | **0.901**             |
| A715 | 2.114                 | 0.731                 |
| A710 | **2.381**             | 0.820                 |
| X3   | 0.983                 | 0.333                 |

→ **两个频段排序都与 DT 口径一致**（低频 A710 最省、高频小簇最耐看），变化只在相对差距：big 相对更便宜（little 2016000 = 0.900 vs big 940800 = 1.863 容量单位/mW）、prime 相对更贵（X3 即便最低档也只有 0.983）。故策略立足点仍是「**中低算力优先给大核低频段**」——两种口径一致，且与图③前沿的起手段落吻合。
（原文档第 5 节「高频段 big 反超」是把 capacity 当成每 MHz 速率、漏了 1/f_max，已勘误。）

#### 3.2 引导 / 防拥挤 / 防震荡：三组要求与落地评审门（v10）

**结论先说**：现在的计划**能做到"少去贵的地方"**（不进 prime、别在 little 高频贴顶、别把后台钉在大核），**但还做不到"向能效更优的核心"**——因为 ChiRi 的引导通道只有三条，而选核打分里**没有能效输入**。三组要求如下。

**（一）引导通道的边界（先把"能做什么"说死）**

ChiRi 不给任何线程直接写频率，能动的只有四种（**v12 订正：务必区分线程级与组级**）：

1. **per-thread 多核掩码**（`set_tid_affinity(tid, &[…])`）——决定"这个线程可以被放到哪些核"，掩码内由内核 WALT/EAS 自己选；
2. **per-thread 单核掩码（pin）**——引导最强，代价是同核排队与 cache/TLB 抖动，故有每核上限 3；
3. **cpuset 组 cpus**（`/dev/cpuset/<组>/cpus`）——**组级**，一次改动波及该组全部线程（如 `pin_background` 把后台三组收窄到小核），属"场景级布局"手段，**不能当线程手段用**；
4. **uclamp**（`cpu.uclamp.max`，cgroup 级）——不改 CLG 上限，只改 schedutil 选出的实际频率（见 1.2）。

→ 所以"引导任务向能效更优的核心"只能落成两件事：**把允许集收窄到能效更优的簇/频段**，或**用 uclamp 把该线程的实际工作点压到低频段**；**不能**直接指定频率。若要做**线程级**能效引导，需要 per-task uclamp（`sched_setattr` 的 util_clamp，须先核实内核 `CONFIG_UCLAMP_TASK` / tg 限制）——属新增能力、要评审；**系统级 `sched_util_clamp_*` 一类全局钳制不得使用**（那是事实上的全局封顶，违 R1/R2）。

**（二）引导：选核打分要引入能效项**

现状打分 = `逐核 util + 已钉数 × 0.4`（`affinity.rs:919-939`），**无任何 capacity/能效输入**；簇偏好是硬编码的"big 优先、钉满溢出 prime"（`affinity.rs:1207-1210,1723`）。要求：

- 打分/分流要能回答 P-a/P-c：**轻负载（little 低频段能完成）不进 big、中负载不留在 little 高频贴顶、可并行批处理不进 prime**（A3/A4 的口径落点）；
- 决策依据必须是"**等算力成本**"而不是"簇名气"：同一份算力在 big 低频段只有 little 高频段的一半功耗（§2.1 锚点）——这是"向能效更优的核心"在代码里唯一可验证的形态；
- **允许集与 uclamp 配对**：能收窄掩码时优先收窄；收窄会引发排队（顶到 pin 上限/单核竞争）时改用 uclamp 压实际频率。

→ 这三条的机制设计见 **3.3**（不再停留在"要求"）。

**（三）防一拥而上：三道已有 + 两道要补**

已有、**必须保留**（改动时不得削弱）：`PINNED_WEIGHT` 0.4（已钉核加权，把后来者推向别核）、`MAX_PINS_PER_CORE` 3（"分散非圈养"，达上限改留宽掩码交内核自调度）、`pick_core_pref` 两段式（main 未钉满不溢出 overflow）、过载分散（`CORE_OVERLOAD_UTIL` 0.70 + `OVERLOAD_MARGIN` 0.15）。

要补：

- **big 饱和保护目前只在 boost 态生效**：`big_pressure = boost && big_max > BIG_HIGH_WATER`（`affinity.rs:1619,1693`）→ 亮屏 default（非 boost）时后台线程照旧往 big 塞，这是"一拥而上"的现成缺口，应推广到所有会 promote 的模式；
- **缺池级/簇级容量概念**：现在只有"每核钉数上限"，没有"整簇已拥挤/频率已爬进高频段就停止迁入"的判据 → 需要一条"目标簇工作点已在可行域内侧时不再迁入"的规则（方向，量值待定）。

**（四）防来回震荡：已有防线 + 新增纪律**

已有、**必须保留**：两窗确认（`busy_window_update`）、4s/8s/16s 三道时间闸、`OVERLOAD_MARGIN` 分数滞回、成对水位（30/15、0.70/0.50）、`DEMOTE_STREAK` 3 轮、`GroupBind` 枚举化（替代两个易失布尔量）。

新增纪律（即 R6 的落地）：

- **成对滞回 + 最短驻留**：新增门槛必须同时给进入/退出阈值与最短驻留时间；**禁止单向门槛**（进门难出门快 = 抖动源）；
- **写后确认与冷却**：写完掩码/uclamp 要有确认或冷却窗（现只有"写失败保留重试"，成功路径无回读；参考 FAS `VERIFY_SETTLE` 思路），避免"写完立刻按旧状态再决策"；
- **切换只做差集**（A10）：前台切换是当前 restore 的第一大来源（`fg_group_reset` 9757/9042 次），整组解绑重绑会把 churn 放大成全局震荡；
- **确定性**：同一输入序列必须得到同一落点（不依赖 `HashMap` 迭代顺序 / 浮点相等），否则震荡不可复现、不可判读。

**（五）落地评审门（不满足不进实现）**

每条 A 类建议落地前须答四问：① 它把工作点移向前沿的哪一段（R5）？② 它走哪条通道（允许集 / uclamp / pin）？③ 目标簇已拥挤时它的退路是什么（防拥挤）？④ 它的进入/退出阈值、最短驻留与冷却是什么（R6，防震荡）？——**四问答不全视为未定义，不排期**。

**（六）怎么验（R3 禁 A/B，只能离线重放 + 观察）**

- **离线重放**：把 `aff_*.log` 的 `@S`/`@A` 帧（util/core/home/pin 序列）当输入重跑决策函数，统计：同一 tid 的 home 变化次数与**往返（A→B→A）次数**、`pin : restore` 比、`overload_hold`/`hold` 计数、每核钉数分布（是否顶到上限）；
- **真机观察**：绑定变化率（每秒 pin+restore 次数）对比场景基线带；**目标簇频率是否因拥挤爬进高频段**（爬进去 = 防拥挤没生效）；
- **判据**：稳态段同一线程的 home 应**单调收敛**（无往返）；全局绑定变化率不高于基线；同簇工作点不进入高频段。

#### 3.3 前沿主导的放置内核（FDP）：把"做不到"改成"怎么做"（v11）

**一句话设计**：把 affinity 现在"按簇名气 + util 打分"的落点选择，换成**显式成本函数**——给定线程需求与各簇当前工作点，算出"把它放到每个候选簇上要付多少**边际功耗**"，选最小的那个。**边际项天然抑制拥挤（拥挤→贵→转走），滞回项天然抑制震荡（差不显著→不动）**，这正是 R5 作为调度目标函数的落地形态。

**（2）成本函数（双边比较 + 只用排序）**

> ⚠️ **修正（v12 审查）**：初版写的是 `ΔP(c) = P_c(f*) − P_c(f_c_now)` 且"选最小者"——**逻辑不成立**：目的簇的增量恒 ≥ 0，与"不搬（增量 = 0）"比永远更差，规则会退化成"永不动作"；而且用 CLG 的**决策上限**当"当前工作点"，会把该簇当成已在高位、**低估**承接成本，反而鼓励继续往它塞，与防拥挤的目标相反。

- **工作点取实际频率**：`f_now(c)` 用该簇**实际运行频率**（`scaling_cur_freq`，与 devimp 的 `cpu_cur_khz` 同源）；CLG 的决策上限**只用来判断该簇还剩多少余量**，不得当作工作点。
- **双边比较**：把线程从源簇 `s` 迁到目的簇 `c`，比较两簇工作点变化后的功率差：`净收益 = [P_s(f_s_after) − P_s(f_s_now)] + [P_c(f_c_after) − P_c(f_c_now)]`（前项 ≤ 0 为让出收益、后项 ≥ 0 为承接成本），**只有净收益 < 0（等算力下总功耗下移）才迁**。若源簇让出后频率不变（其他线程仍顶住），让出收益为 0 → **默认不动**（保守口径）。
- **口径降级声明**：单线程 × 簇级的比较**不等于**图③的整机前沿（前沿含并行度、核数、漏电）。FDP 只把它当**同需求、同并行度下的局部代理**：用于①同簇内选档 ②跨簇同需求比较；**不用于预测整机功耗**，也不得据此宣称"总功耗下降 X W"。
- 需求 `d`：线程窗口 util 折算成"需要多少真机容量单位"（真机 `capacity × f / f_max`）；由 `d` 反推满足需求的最小档 `f*`。
- **成本差小于阈值（≈ 一个频档的等效需求差）时不动作**；只用相对排序、不做绝对功耗预测（静态表是 Odin2 借位电压且不含漏电，§2.2 / 文档 §6）。
- **冷启动**：首见线程、观测不足 N 个窗口的线程**只建档、不决策**（沿用既有"首见不 promote"惯例）。

**（3）防一拥而上：内生 + 配额（内生不足以防 burst）**

> ⚠️ **修正（v12 审查）**：初版说"边际项天然抑制拥挤"——只在**跨轮**成立。同一轮内几十条线程看到的是同一份快照，会**同轮一起判"big 最便宜"**；而 CLG 抬上限又有一轮延迟 → 至少一个 2s 周期内的同向涌入是拦不住的。

- **内生（跨轮生效）**：拥挤抬高该簇实际频率 → 承接成本上升 → 后续线程转走；
- **配额（新增，硬约束）**：每轮对每个目的簇的**迁入条数上限** + "**净增算力 ≤ 该簇空闲余量**"，任一触顶即本轮不再向该簇迁入。防 burst 靠这个，不能只靠成本项；
- **兜底（保留、不得削弱）**：`MAX_PINS_PER_CORE`、`PINNED_WEIGHT`、`pick_core_pref` 两段式、过载分散；**并把 big 饱和保护从"仅 boost 态"推广到所有会 promote 的模式**（`affinity.rs:1619,1693`）；
- **反自激**：成本输入用**本轮开始时的快照**（实际频率取平滑值），本轮决策不改变本轮输入（一轮延迟）；
- **残留风险**：一轮延迟下最坏情况存在一个周期的同向涌入 → 由配额兜住，不指望成本项立刻生效。

**（4）四条通道怎么分工（v12 订正：区分"线程级"与"组级"）**

| 通道 | 粒度 | 何时用 | 限制 |
| ---- | ---- | ------ | ---- |
| **per-thread 多核掩码**（`set_tid_affinity(tid, &[多核])`） | 线程 | **默认方向手段**：只表达"哪个簇/哪几个核" | 掩码内选核仍归内核；不得窄到让内核无核可选 |
| per-thread 单核掩码（pin） | 线程 | 延迟敏感 + 目标核不拥挤 | 受每核上限 3 与排队代价约束；32 位线程不得指向无 AArch32 簇 |
| **cpuset 组 cpus**（`/dev/cpuset/<组>/cpus`） | **组** | 场景级整体布局（boost / 息屏 / lab） | **波及该组全部线程**，不能当"线程手段"用——已有实例：`pin_background` 把 `background`/`system-background`/`restricted` 收窄到小核（`affinity.rs:1940+`，boost 与 normal 两路都调） |
| uclamp（`cpu.uclamp.max`） | 组（top-app / background / restricted） | 压"实际工作点"而不改核集合 | 组级；线程级需 `sched_setattr` 的 util_clamp（待核实内核支持，见（1）） |

**（5）防震荡：R6 全保留 + 两条补充**

- 成本差滞回（差 < 阈值不动）+ 最短驻留 + 三道时间闸（4s/8s/16s）+ 反跳回冷却；
- **确定性**：决策必须是纯函数（输入快照 → 输出落点），不依赖迭代顺序 / 浮点相等 → 才能离线重放与复现；
- **一轮延迟**：本轮只写落点，不改用于计算成本的输入（见（3）的反自激）。

**（6）静态表来源与校正（不引入运行时自适应）**

- 表来自 `mdocs/8550/sm8550-freq-power.md`（已逐档校验过），编译期嵌入，并与 `soc.yaml` 的 `capacity/freq_khz` 对账；
- **校正走离线**：用 `main_` 的（簇、实际频率、util）三元组 + `status.csv` 的 `batt_power_w` 回归，得到"相对 Cx 修正建议"→ 评审 → 进下一版常量。**不做运行时自适应**（伪反馈本身就是震荡源）；

**（7）落点与验证**

- 新增模块（建议 `src/chiri/energy_cost.rs`：静态表 + 纯函数成本/决策）+ `affinity.rs` 打分改造；位宽检测（A6）与线程级 uclamp 是完整性前提；

- **离线重放**：`aff_*.log` 帧 → 决策函数 → 统计 home 往返次数、成本差分布、每核钉数分布、拥挤触发次数；

**（8）风险与代价**

- **静态表偏差 → 排序错**：靠"只用排序 + 离线校正 + 硬兜底"缓解，不能靠调参掩盖；表存疑时**宁可不动作**；
- **收窄允许集削弱内核选核自由度 → 排队/延迟回退**：靠"允许集 ≥2 核"与 pin 上限约束；
- **与 CLG 的耦合**：必须显式去耦（快照输入 + 一轮延迟），否则是新的震荡源；
- 计算开销可忽略（3 簇 × 数十档的纯算术，2s 一轮）。

#### 3.4 三模式 = 前沿上的三个预设点（预计算结果向量；含预判交叠带，v15）

**一句话**：`reduce` / `default` / `boost` 不再是"三组拍出来的参数"，而是**同一条帕累托前沿上的三种取点策略**——目标函数不同、结果表不同；**运行时只查表，不算账**。

| 模式        | 目标（用户口径）                     | 在前沿上的位置                                       | 允许的取向                                                       | 流畅度口径                             |
| ----------- | ------------------------------------ | ---------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------- |
| `reduce`    | **最低功耗成本**                     | 前沿**最左端**（总算力最低、功耗最低的段）           | 只在"算力不足已影响可用性"时才向右移；落点优先 little 低频段与 big 低频段 | 只要能完成交互即可（更钝：升频更慢、下探更早） |
| `default`   | **成本导向**：保流畅前提下尽可能省电 | 前沿上**等算力成本最小**的主段（P-a / P-c 的落点）   | 中低算力增量由 big 低频段承接；避免任何簇贴顶；不为"等下一波负载"留高频 | 交互跟手、无掉帧的常规标准             |
| `boost`     | **对功耗宽松**                       | 前沿**偏右段**（更高算力、更高功耗，含 prime 冲顶段边缘） | 允许用算力换响应：升频更快、降频更慢、更早动用 prime             | 最激进（响应优先，接受更高功耗）       |

**与 R1/R2 的边界（先钉死）**：三模式**都不许封顶**（见 R7）——`reduce` 也不得砍 `perf_ceil` / `headroom`；差异只能靠取点、到达速度、降权表达；持续满负载在任何模式下都能写到硬件最高频。

**预判：临界点前的"亲和交叠带"（三模式提前量不同，上升/下降两侧对称）**

- **为什么**：若等跨桶那一刻才改掩码，就是"**掩码突变 + 线程被强制迁移**"，排队与抖动恰好发生在最不该发生的时刻。提前把**即将迁往的簇**并入该线程的允许集，让内核在两簇之间自选，跨桶时只需**收窄旧簇**——把一次大动作摊成两次小动作。
- **两种临界点都要预判**：① **需求跨桶**（`demand_buckets` 的桶边界）；② **落点贴顶**（当前簇已到该模式允许的最高落点，再涨只能换簇）。
- **动作形态**：允许集 = 当前簇 ∪ 目标簇（**交叠带**），过带后收敛为单簇。**只改"许可"、不搬线程**——因此不受 4s/8s/16s 迁移闸约束，但必须：**成对滞回**（进/出各一个提前量）、**最短驻留**、每次只增/减**一个簇**、并落 aff 动作帧（可观测）。
- **双向对称（用户明确要求）**：需求**下降**时同样处理——提前把**更省的一侧**纳入允许集，并把将要离开的昂贵簇降级为"待撤"，最短驻留后撤出；**上升沿与下降沿共用同一组提前量参数**。
- **提前量随模式不同（用户已定量）**：以 `default` 为**基准**，`reduce` = **基准 ×0.5**（更晚才交叠）、`boost` = **基准 ×2**（提前一倍，更激进，并允许提前取得 prime 的许可）；**单位 = 需求百分比**（即"距临界点还剩 X% 需求就交叠"），**贴顶预警也用需求百分比**（距该模式允许的最高落点还剩多少）。基准值由离线生成器按模型取点给出，运行期只查表。
- **风险**：交叠期间内核可能落到**更贵的一侧** → 交叠只允许"相邻桶对应的簇"，宽度受模式提前量约束；用离线重放统计"交叠期实际落点分布"判定是否划算（若多数落在贵侧，就收窄提前量）。

**"结果向量"怎么预设（离线生成 → 配置表 → 运行期查表）**

- **输入**：`mdocs/8550/sm8550-freq-power.md` 的逐档表（Cx / 电压 / 推理功耗 / 算力）+ `soc.yaml` 的 `capacity` / `freq_khz`（真机口径）。**运行时不读 energy_model**（文档 §6 已证厂商内核不注册 EM，读不到）。
- **生成**：一个**离线生成器**（开发期工具，**不进设备、不进运行期**；建议 `scripts/frontier_policy.py`，纯标准库）——只做三件事：① 读 `mdocs/8550/sm8550-freq-power.md` 的逐档表与 `soc.yaml` 的 `capacity`/`freq_khz`；② 按三模式的目标函数在图③前沿上取点（含预判提前量基准、`cluster_pref`、up/down 倾向、模式乘子）；③ **把结果写成表段**（默认写回 `module/config/8550/soc.yaml`）并打印一份人类可读的对照摘要。它的价值是**可重复运行**：模型表或 `capacity` 一变，重跑即可复算对账（构造性自证）；**设备侧永远只查表，不跑它**。
- **落点（用户已确认）：并入 `module/config/8550/soc.yaml`** —— 复用既有 `soc_config()` 解析链、`embedded_config_file` 嵌入与 `None` 兜底（`src/common.rs:316`），不新增机制；代价是 `SocConfig` 要扩结构体，且三机型各自都要有该段（表本来就与 SoC 相关，逐 SoC 放正合适）。**前置**：`build.rs` 必需清单里的 `soc.yaml` 断言当前指向**不存在的根路径**（HEAD 缺陷，见第 8 节附注），本项落地前必须先修那个断言。
  - （备选，仅记录）新建 `module/config/8550/frontier_policy.yaml`：字段独立、可整表替换与单独对账；代价是多一套嵌入/解析/兜底链。
  - （不推荐）不写生成器、人工一次性算出结果向量直接填表：代价是失去"可复算自证"，模型表一更新就得人工重算。
  - 建议的表内容：
  - `model_fingerprint`：模型表版本 / 生成日 / 内容哈希 —— **表与代码漂移必须能被发现**；
  - `demand_buckets[]`：需求分桶边界（真机容量单位，按频档对齐）；
  - `per_cluster.<簇>.perf_target[]`：每个需求桶 → 该簇目标 perf（**已 floor 对齐到档位索引**，运行期不再做比值换算）；
  - `cluster_pref[]`：每个需求桶 → 首选簇（P-a/P-b/P-c 的落点结论）；
  - `up_tendency[]` / `down_tendency[]`：每桶对应的升频审批强度与下探步长倾向（把"到达速度"也一并预设，省掉运行期调参）；
  - `anticipate`：**预判参数**——每桶的**基准提前量（需求百分比）** + **模式乘子**（`reduce 0.5` / `default 1.0` / `boost 2.0`，用户定）+ 交叠带最短驻留 + 允许交叠的相邻簇（默认只允许相邻桶的簇）。**上升沿与下降沿共用同一组基准提前量**；乘子写表不写代码，便于整表复算。
- **运行期**：CLG / 特调只做「**查表 → 热钳 clamp → floor 对齐兜底**」，**不做 `Cx·f·V²` 实时计算**（省 CPU，也避免模型误差在运行期被放大）。

**震荡与拥挤的判读（v10 新增，与 3.2（六）同口径）**：

- **无往返**：稳态段同一 tid 的 `home` 变化应单调收敛，不出现 A→B→A（现成口径：`RETURN_COOLDOWN` 注释里的"乒乓周期 8s，取两倍错开节奏"）。
- **无泄漏**：`pin : restore` 应接近 1:1（实测 1.01–1.04 : 1）；末帧 `pin=1&home=-1` 的残留量应与活跃前台线程数量同量级，不是历史累积（历史坑：Busy 释放臂缺失导致 1115 条滞留 95 分钟）。
- **不拥挤**：目标核钉定数不应长期顶到 `MAX_PINS_PER_CORE`；目标簇频率不应因新迁入而爬进高频段。
- **不绕过时间闸**：新增放置动作后，`MIN_MIGRATE_INTERVAL` / `REPIN_DEBOUNCE` / `RETURN_COOLDOWN` 三条仍须生效（列为代码审查项）。

**采集侧开销（v13：评估已完成，结论与处置如下）**

- ⚠️ **先撤回一个错误引用**：本计划 v12 写的"采集自身在视频场景约占 **~14%**、桌面 **~18%**"**是转述漂移，不是功耗数字**。原始出处是 8745 上 `tgtop` 的**负载占比**（待机 logd 17.44% / launcher 15.82% / 游戏 9%；8550 另有一处 launcher 19.9%），"视频 ~14%"在仓库里**查无出处**。**禁止再用该数字论证开销。**
- **实测账本（本机会话，同机同版本 PHB110/A16）**：devimp 写盘 **20.3–27.9 kB/s**——其中 `aff_` 的每秒 `@S` 帧占 **88%**（单帧 17.9–25.7 kB），`main_` 仅 2.6–3.0 kB/s；logd 侧（status.csv + daemon.log）**0.09–0.13 kB/s** → devimp 是 logd 的 **~176 倍**，采集开销主体在 devimp，**不在 status.csv**。`playback_fps` 探针：**0.77–1.0 行/s**（整秒一行、该秒无帧则不落行），投喂帧率 **11–151 帧/s**（播放稳态 40–90）。
