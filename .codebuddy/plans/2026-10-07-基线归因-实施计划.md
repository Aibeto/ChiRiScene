## 为什么现在做

- @S 帧的 30~40ms 只在**息屏**配对测出来过。亮屏侧不但没验证，跳帧对照还给出反向信号（−11.9 / −22.0 / −6.3 ms，样本有选择偏差）。
- 「剩余量」= 亮屏总量 −（息屏估的单帧成本 × 亮屏帧率），**跨场景减法，两头都不稳**。
- 现在拿这个数去排序优化项，等于抽奖。

## 分三个阶段

### P0 前置（先把尺子校准，否则后面全是估的）

| 项   | 做什么                                                                                                     | 为什么必须先做                                                                       |
| ---- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| P0-1 | 给 @S 帧加帧内计时：build 和 write 前后各取一次 `Instant`，**超过 50ms 才节流落一条 debug 行**，不动帧格式 | 剩余量 = 总量 − @S。@S 在亮屏没有可信数字，减出来的就不可信                          |
| P0-2 | 补采一段「devimp 采集关闭、daemon 仍在跑」的日志                                                           | 现有三包的 main 日志覆盖几乎全部墙钟，**没有对照窗口**，「剩余量是否非诊断」无法验证 |
| P0-3 | 采一个 `aff_secs>1` 的亮屏对照包                                                                           | 亮屏 98.6% 帧距 = 1s，没有非帧秒，不做对照就分不开 @S                                |

P0-1 不降采样质量（不改采集内容、不动帧格式），可直接做。P0-2 / P0-3 需要设备操作。

### P1 第一层：用现有日志筛候选（纯离线，零风险）

1. 按**同版本、同配置、同屏幕状态、同调度模式、同连续有效区间**分组。
2. **排除跨缺口的差分和模式切换的边界**，不拿包平均值做机型归因。
3. 观察自耗与线程规模、模式、事件活动、周期相位的关系，排出候选路径。
4. 记住：**落行次数不等于执行次数**（CLG/tuned 的 tick 行有签名去重），相关性只能排候选，不能当计数量。

产出：候选路径清单 + 每个候选的量级排序 + 明确列出「现有日志分不开」的部分。

已知样本约束：稳定区间很碎（中位段长 P1=5s / P2=4s / P3=1s），≥60s 的段只覆盖 62% / 57% / 33%；P3 缺行 52.2%，缺失是否随机未验。

### P2 第二层：对少数候选做直接归因（只在 P1 分不开时才做）

- 少量累计执行计数、分块的线程 CPU 时间与墙钟耗时。
- **汇总输出**，不逐事件刷日志。
- **不减少原有采集**（属新增，不是裁减）。

产出：每个候选的「执行次数 × 单次成本」，以及仍未归因的残差。

## 边界（这几条别踩）

| 别做                                  | 原因                                                                             |
| ------------------------------------- | -------------------------------------------------------------------------------- |
| 拿亮屏跳帧配对估帧成本                | 选择偏差：跳帧发生在系统忙时，紧随那一秒自耗本就偏高                             |
| 把跨场景减法当严格分解                | 减数来自息屏，被减数的样本偏差也没查                                             |
| 把 `/proc/self/stat` 当调度线程专属账 | 它是整个进程的 CPU（含 monitor、诊断、调度线程），也不覆盖 eBPF 系统事件路径成本 |
| 用包平均值做机型归因                  | 分组条件没对齐，差异可能只是工作量或单位成本不同                                 |
| 任何降采样质量的改动                  | 2026-10-07 裁决红线（详见方案文档卷首）                                          |

## 顺序与依赖

**基线归因 → 诊断线程化。** 后者实施前必须先固定原始基线，否则 @S 的真实耗时口径会和迁移混在一起，之后更难拆。

两项可以并行**准备**，但线程化的**实施**排在归因之后。

## 三种结果分别导向什么

| 查出来                   | 说明           | 投入方向                                     |
| ------------------------ | -------------- | -------------------------------------------- |
| 剩余量在诊断关闭时仍存在 | 常驻成本       | 价值最高，压它对日常态也有效                 |
| 剩余量只在诊断开启时存在 | 诊断自观测成本 | 只对诊断会话有意义，且受不降质约束，空间有限 |
| 剩余量其实没那么大       | 减法有偏       | 先修方法，别在错误的数上排序                 |

三种结果都不改变「不降采样质量」的红线，改变的是投入方向。
