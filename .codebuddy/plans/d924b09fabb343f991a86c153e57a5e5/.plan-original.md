## 产品概述

产出一份《8550 调度能效改进策略》评审文档：以 `mdocs/8550/sm8550-freq-power.md` 的频率↔功耗能效模型为量化账本，结合 `devimpbin/0927-142328` 会话的调度实测证据（另一份已有分析产物），对 ChiRi 全局调度参数做一次按能效重新评估，形成可评审、可复验、可回退的改进策略。本轮只产出文档，不改任何代码与配置。

## 核心功能

- **证据账本**：把能效模型的可操作推论（每核 Cx 与能效排序、跨簇等价换算、内存角落台阶、X3 使用门槛、帕累托前沿形态）与本次日志实测（分场景功耗、频率决策、唤醒/迁移、亲和 churn、探针开销）对齐成一张可引用的证据表。
- **分线策略**：按「非游戏亮屏（CLG default/reduce）→ 视频 playback 特调 → 游戏 FAS → 亲和与 core_ctl → 采集与探针开销」五条线，逐条给出改进方向与理由。
- **参数建议表**：逐项写明「现状值 → 建议值 → 模型依据 → 预期收益量级 → 风险与回退」，字段名与现有配置文件一一对应，频率值对齐真机频表档位。
- **验证矩阵**：给出场景×改动×采集口径×接受判据×回退条件的 A/B 矩阵，采集统一走项目预置 devimp 分析流程，明确哪些结论必须真机取证后才能定稿。
- **评审材料**：结论摘要按收益/置信度排序列出可执行建议，附未决项与 TODO 台账条目建议，供评审通过后再决定落地。

## 交付物与工艺

纯文档产出，不涉及代码实现。技术要点是「文档工程 + 口径纪律」：

### 输出位置与命名

- 唯一产出文件：`e:/code/ChiRi/.codebuddy/docs/2026-09-27-8550-sched-energy-strategy.md`（AI 产出文档放本环境 `docs/`，不得放 `mdocs/`）。
- 本轮不写 `agentsdocs/`、不改 `module/config/`、不改 `scripts/`、不写 memory。

### 文档结构（七节）

1. 结论摘要（可执行建议清单，按收益×置信度排序）
2. 证据与方法（数据源、口径、可信边界：模型为 Odin2 借位电压、非运行时输入）
3. 能效模型可操作推论（跨簇等价、角落跳变、X3 门槛、前沿起手在 big 低频）
4. 分线策略 A–E（亮屏 / playback / FAS / 亲和+core_ctl / 采集与探针）
5. 参数建议表（现状→建议→依据→收益→风险回退）
6. A/B 验证矩阵（场景×改动×口径×判据×回退）
7. 未决项与 TODO 台账建议

### 事实约束（防臆造）

- 参数建议只允许引用现行字段：`feature.yaml` 的 Affinity/CoreCtl/Thermal/Sched/reduce/default/boost/powerbase 段、`tuned_profiles.yaml` 的 akmode 与 tuned_profiles.playback 段、`special_tuned.yaml`、`fas.yaml` 与 `fas/` 目录；引用前须核对现值。
- 频率建议必须 floor 对齐三簇真机频表（little 16 档 307200–2016000、big 20 档 499200–2803200、prime 21 档 595200–3187200）。
- 模型侧口径：Cx = 251/472/421/1057；能效低频段 A710 最优、高频段 A510 最优；little 2016000 ≈ big 948000；X3 仅单核算力需求大于 2600 Mdmips 才值得上。
- 日志侧口径（不得混用）：功耗以 status.csv 的 charge+batt_power_w 为权威，devimp 侧 P_avg 只作交叉验证；wakeups/migrations 是 2s 差分（÷2）；cap 序列不可跨批次连读。
- 论证主线以能效模型与调度行为证据为主，温度/cap 档仅作限幅状态描述，不作归因主线。

### 验证与回退设计

- 文档中的每条建议携带验证方式与回退条件；验证矩阵引用 `.cursor/commands/devimp-log-analysis.md` 的基线表与 `scripts/devimp/dvrun.py` 流程，注明「需真机采集」。
- 结论按「模型可定 / 需真机取证」分级，未取证项写入 TODO 台账建议（标准 `TODO: ` 前缀）。
