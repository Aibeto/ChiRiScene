description: 用户点名"修复/改进"某缺陷清单时只改文档；擅自改源码会被斥止；撤回先给清单再等指令，不代跑 git checkout
type: feedback

**规则**：

1. 用户说"修复/改进/处理一下 X"（X 是计划里的缺陷或缺口清单）时，**默认作用域是计划/文档**——把方案写到可实施即可；**源码、配置、构建脚本一律不动**，直到出现明确指令（「开始改」「动手」「实现」这类）。
2. 若已擅自改了源码：**列文件级精确清单 + 可复制的撤回命令**，把决定权交给用户；**不要代跑 `git checkout` / `git restore` 等批量回滚**（可能误伤用户 WIP，已被拒一次）。
3. 汇报时把「我改的 / 工作区已有的 / HEAD 自带的缺陷」三者分开写，不混在一句里。

**Why:** 2026-09-28 用户列了四条（其中"4. 修复"指的是修 FDP 三缺口），我当成"立刻写代码"，改了 5 个源码/配置文件加 `build.rs`，被明确斥止（"谁让你执行计划了"）；随后用户澄清是"继续修复计划"（文档层面）。仓库既有硬口径同样是「评估与准备 ≠ 批准开工」（`MEMORY.md` 构建与仓库约定节）。

**How to apply:** 见到"修复/改进/处理"这类动词，先按文档处理并**在回复里写明作用域**（"本轮只改计划、不动源码"）；确实需要动源码时，先给"要改哪些文件 + 怎么改 + 怎么撤"，再等一句明确许可。
