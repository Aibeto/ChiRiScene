## 亮屏突发尖峰的调度决策分析（结论，未动代码）

场景：息屏 → 突然亮屏，system 进程瞬时 156% CPU、持续几 ms 后回落 20%，问动画会不会卡。

结论要点：
- 尖峰本身**不驱动任何升频**：160ms 采样窗口把几 ms 尖峰稀释到 ~5% util；再经
  util_smoothing 0.5 EMA → spike(0.35/0.30) → up_rate_limit 2 tick → smoothing_up 0.60，
  写频还被 write_deadzone 3% / write_dwell 320ms 吞掉。追已结束的尖峰 = 纯浪费。
- 防卡靠**起跳 ceiling**：亮屏 `ScreenStateChange(true)` → `reload_config` 把 current_perf
  重置到原模式 perf_init（default 0.50 / boost 0.60）并立即写频，先于动画到位。
- CLG 侧唯一 gap：电源键亮屏无 touch 事件 → touch_boost 兜底不触发；且 20% 稳态
  3 tick 后一步降到 0.20，第二波动画要从地板爬 2 tick。候选改法：亮屏复用
  `on_touch()` 通道做一次性 400ms ceiling 窗口（待用户批准，未实现）。
- SceneMode 侧风险是**延迟**不是参数：perf_ceil 0.12 / up_threshold 1.0 下尖峰零影响
  （也不触发 0.75 饱和退出），但亮屏退出是串行三步（prime hotplug 上线 → CLG reload →
  首个负载 tick）；uevent 漏报时 app_detect 自愈轮询 1s 一轮 → 最坏 1s 卡在 0.12。
  候选改法：亮屏方向改成「任一权威节点报亮即恢复」的不对称判定（息屏仍保留多数票）。
