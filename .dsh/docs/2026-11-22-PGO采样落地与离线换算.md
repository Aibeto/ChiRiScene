## 0. 一句话结论

PGO 采样链路已按「ETM 优先 → cpu-cycles 回退 → 都不可用则关闭」三段落地，全流程事件驱动、**零 tick 轮询**；采样开销实测可忽略（daemon 60 s 内仅 3.41 CPU 秒，约 5.7% 单核）。但本机无可用 ETM，AutoFDO 只能拿到函数级热度，跨版本重建 profile 才有收益——离线换算链（`chiri.debug` → `-Cprofile-sample-use`）是下一块，未落地。

## 2. 架构

### 2.1 唤醒源 → 判态（事件驱动）

| 事件 | 来源 | 唤醒动作 |
| --- | --- | --- |
| 开关热重载 | `src/chiri/mod.rs:2656` config_watcher → `Config::load` → `set_enabled` | 值变化才 `notify()` |
| 屏态切换 | `src/common.rs:643` `set_screen_on`（4 处调用点：`chiri/mod.rs:2808/3879/3918/4727`） | 原子量 `swap` 返回旧值，变化才 `notify()` |
| 采样会话结束 | 每会话一条 `pgo-reaper` 线程 `child.wait()` 后 `tx.send(()) + notify()` | manager 侧 `try_recv()` 判结束 |
| 定时到期 | 无外部事件时 `Condvar::wait_timeout_while` 到 `next_at` | 超时即醒，非轮询 |

### 2.2 状态机（`run` 循环，每轮第一行取 `seen = snapshot()`）

```
[gate_off]   !ENABLED                → 收拾会话(丢弃产物) → wait_until(None, seen) 无限等
[session]    采样中                  → finished() 判结束：settle → next_at=+IDLE(1800s)；否则 wait_until(None, seen)
[deadline]   now < next_at           → wait_until(Some(next_at), seen)
[screen]     !screen_on()            → wait_until(None, seen) 等亮屏
[probe]      tier ∈ {UNKNOWN, OFF}   → 实录 1 秒探测；OFF 则 next_at=+REPROBE(1800s)
[start]      启动 60 s 会话          → 失败 fails+1；满 3 次重置 tier=UNKNOWN 且 next_at=+RETRY(300s)
```

### 2.3 防丢唤醒（关键正确性点）

事件侧顺序是「先改状态，后递增代次」；等待侧若「先判态、后取快照」会漏掉两者之间的那一次事件。故：

1. `snapshot()` 在判态**之前**取代次；
2. `wait_until(deadline, seen)` 在锁内比较代次，只要 `*gen != seen` 立即返回；
3. `Condvar::wait / wait_timeout` 返回后循环重查，不假定单次唤醒语义。

### 2.4 档位探测必须实录

设备 `/sys/bus/event_source/devices/cs_etm` 节点存在、`simpleperf list` 也列出 `cs-etm`，但实际录像返回 `etm devices are not available`（该机只有 `coresight-audio-etm0`，APSS ETM 未向 userspace 暴露）。因此探测不能看 sysfs 存在性，`trial()` 对每个候选事件**实录 1 秒**（`--duration 1`，cpu-cycles 额外 `-f 200`），判 `status.success()` 且产物非空，用完立即删除临时文件。

## 3. 产物、上限与归档

- 产物：`logs/pgo/perf_<epoch_ms>.data`（仅当 ≥ `MIN_SAMPLES_BYTES`=1024 才保留）。
- 清单：`logs/pgo/manifest.txt`，每会话一行：
  `ts= file= tier= size= dur= freq= soc= kernel= exe=<len:epoch_mtime>`。
  `soc` 取 `matched_soc_config_name()`，`kernel` 取 `/proc/sys/kernel/osrelease`，`exe` 指纹用于跨版本判断「profile 是否还能复用」。
- 上限：最多 16 份、合计 ≤ 24 MiB，按 mtime 新→旧淘汰（纯逻辑 `prune_keep` 有单测）。
- 归档：`logs/pgo/` 落在 `src/logger.rs:2193` 的启动归档范围内，会随 `logd/<ts>.tar.zst` 一起进包，无需新链路。
- 短会话：`is_short_session`（< 30 s）会连 `logs/pgo` 一起清空，不产生垃圾样本。

## 4. 配置面与热重载链路

| 层 | 位置 | 变更 |
| --- | --- | --- |
| YAML 结构 | `src/common.rs:1182` `MetaYamlFile` | `pgo_sampling: Option<bool>`（该结构带 `deny_unknown_fields`，不加则 WebUI 写入后整行被删） |
| 外部覆盖 | `src/common.rs` `ExternalMetaOverrides` | `pub pgo_sampling: Option<bool>` |
| 解析 | `src/common.rs` `parse_disk_meta` | `pgo_sampling: f.pgo_sampling` |
| 运行时 | `src/chiri/config.rs` `Meta` | `#[serde(default = "crate::utils::default_true")] pub pgo_sampling: bool` |
| 应用 | `src/chiri/config.rs` `apply_meta_overrides` | `meta.pgo_sampling = o.pgo_sampling.unwrap_or_else(crate::utils::default_true);` |
| 下发 | `src/chiri/config.rs` `Config::load` 同步区 | `crate::pgo::set_enabled(config.meta.pgo_sampling);` |

**为什么用 `unwrap_or_else` 而不是 `if let Some`**：模板 28 份 `meta.yaml` 都不写该键，`heal_disk_meta` 对"模板不带"的键非法即删行=沿用代码默认；若用 `if let Some`，`Meta::default()` 的 `false` 会胜出，等于默认关。必须显式 `true`。

**热插拔链路**：`config_watcher`（`src/chiri/mod.rs:2656`）与 5 s 兜底重读（`:2379`）都走 `Config::load` → `set_enabled`；值未变化时不发事件，避免每 5 s 打断采样线程。

## 5. 实测：值不值得做

| 指标 | 数值 | 口径 |
| --- | --- | --- |
| 设备 | OPD2511 / kernel `5.10.236-android12-9-00003-gfb24cf99ad97-ab14313284` | adb |
| `perf_event_paranoid` | `-1` | 读 `/proc/sys/kernel` |
| `perf_event_max_sample_rate` | `25750` | 同上 |
| `cpu-cycles` @ 200 Hz, 60 s | 682 samples / 0 lost / 588,817 B | `simpleperf record -e cpu-cycles -p <chiri> -f 200 --duration 60` |
| 折算 CPU 占用 | 682 ÷ 200 = **3.41 CPU 秒 / 60 s ≈ 5.7% 单核** | 推算 |
| `cs-etm` | `etm devices are not available` | 实录失败 |

含义：daemon 本身极轻，profile 可挖掘的热点本就不多；PGO 的价值主要在**跨版本累积**发现"某个重构让某函数热了 3 倍"，而不是指望单次优化榨出 10% 性能。

## 6. 离线换算链（未落地，下一板块）

1. **带符号二进制**：`llvm-objcopy --only-keep-debug` 产出 `chiri.debug`（strip 不改 `.text` 布局，地址可直接对应）。
2. **无 ETM 路径**：`simpleperf report --sort dso,symbol` → 转 LLVM 文本采样格式（`函数名:样本数:0`）→ 构建时 `-Cprofile-sample-use=<abs>.prof`。
   `llvm-profgen --perfdata` 需要 Linux `perf -b` 的分支栈，ARM64 无 LBR，大概率不可用（需冒烟确认）。
3. **ETM 路径**：`simpleperf inject --output autofdo`（仅 `cs-etm` 录的 perf.data 可用）→ `.afdo` → 同上 `-Cprofile-sample-use`。
4. **注入位置**：走 `CARGO_TARGET_AARCH64_LINUX_ANDROID_RUSTFLAGS`，避免 `RUSTFLAGS` 把 Android 专用 flag 带到 host build script。
5. **构建档**：新增 `pgo` profile = release 参数 + `-Cprofile-sample-use`；另需 `profile` 档（`debug=1, strip=false, force-frame-pointers=yes`）产出可采样的符号版，仅本地 QA 用。

## 7. 风险与未决

| 风险 | 影响 | 现状 |
| --- | --- | --- |
| 设备无 `simpleperf` 或 paranoid≥3 | 探测失败 → 永久 OFF（30 min 重探） | 已静默降级，不影响业务 |
| 只采 daemon 自身 PID | profile 不含 app 线程，无法指导 FAS 调参 | 设计如此：PGO 只优化 daemon 代码布局 |
| LTO + strip 后符号缺失 | 地址无法归因 | 需 `chiri.debug` 配套（未做） |
| 采样时段额外开销 | 每分钟 5.7% 单核 × 60 s | 默认开；不需时可 WebUI 关闭，热插拔 |
| 未构建验证 | 编译期错误未暴露 | 用户要求不构建；已逐项核对签名/宏/变参 |
