# 评估：把 ChiRi 日志从「追加文件」换成「嵌入式数据库」的性能影响

> 结论先行。所有数字分两类标注：**[实测-本机]** = 在 20 核 x86_64 + NVMe(btrfs) 上跑出来的；
> **[推算-设备]** = 用本机数字 + 设备侧已知量（fsync 量级、核心功耗）折算，**必须真机复验**。
> 真机基线取自真实导出包 `devimpbin/logd_1016-151808.tar`（14h 会话，35,455 行 status.csv、134.3MB devimp）。
> 盘点明细见 `inventory/inventory.md`；本轮独立基准见 `bench/bench-report.md`。

## 0. 一句话结论

**换成数据库在热路径上只会变慢，在归档上只会变大，在离线分析上才有收益；而离线分析的绝对耗时本来就只占 5 分钟流水线的零头。**
若目标是「省 CPU / 省电 / 减少重启」——数据库是负收益；若目标是「分析更好写、查询更快」——收益存在但可以用更小的代价拿到（见 §7 的三条替代路线）。
真要上，唯一可接受形态是 **WAL + synchronous=NORMAL + 16~60 行批量提交 + 归档直接发 .db**；按行提交（`synchronous=FULL` 或 `journal_mode=DELETE`）会把写路径成本放大 7.8×~1560×。

## 1. 现状的量级：写日志到底占多少

14h 会话（50,400 s）内的绝对耗时，以及占 daemon 自耗 CPU 的比例：

| 项 | 14h 绝对耗时 | 占单核 | 占 daemon 自耗 | 口径 |
|---|---|---|---|---|
| **daemon 自耗 CPU 总量** | **1,714 s** | **3.40%** | 100% | [实测-设备] status.csv `daemon_utime_ms`+`daemon_stime_ms` 差值，均值 34.0 ms/s |
| `@S` 帧 `build`（读 /proc 建快照） | **248.8 s** | 0.49% | **14.5%** | [实测-设备] selfcost 9,888 帧 × 25.16 ms |
| `@S` 帧 `write`（真正落盘） | **1.42 s** | 0.003% | 0.08% | [实测-设备] selfcost 同 9,888 帧 × 144 µs |
| main + status 行写入 | **3.08 s** | 0.006% | 0.18% | [实测-本机] 4.96 µs/行 × 621,374 行 |
| **存储写入合计**（后两项） | **4.5 s** | **0.009%** | **0.26%** | — |
| devimp 产出量 | 134.3 MB | — | — | [实测-设备] |
| status.csv 产出量 | 5.38 MB | — | — | [实测-设备] 151.7 B/行 × 35,454 |
| 128MB 门限重启节奏 | 每 13.3 h 一次 | — | — | [推算] 由 230.2 MB/天 直接除，停机 3s ⇒ 5.4 s/天 |

**这是整份评估最重要的表**：**整个日志写入链路只占单核 0.009%**，占 daemon 自耗的 0.26%；
而读 `/proc` 建快照占单核 0.49%、占 daemon 自耗 **14.5%**，是存储的 **55 倍**。**换存储引擎动不了大头。**

> 注：上述 14.5% 是按实测帧率 **0.196 帧/s** 算的（息屏 ×5 倍率 + 非 FAS 时段）。
> 若按设计满速 **1 帧/s** 折算，`build` 升到单核 **2.52%**（25.16 ms/s），
> daemon 自耗随之从 34.0 升到 ≈54.2 ms/s，`build` 占比升到 **46%**——
> 无论哪种口径，结论一致：**存储不是瓶颈，`/proc` 采样才是。**

## 2. 写路径：逐行落盘的代价

本机 btrfs/NVMe，同一份 10,000 行真实 status.csv（152.1 B/行）：

| 方案 | µs/行 (p50) | 相对文件 | 说明 |
|---|---|---|---|
| 文件：1 次 `write()`/行（现状，无 fsync） | **4.96** | 1.0× | 600 行 = 600 次 `write()`，关闭时 1 次 fsync |
| SQLite WAL/NORMAL，逐行提交 | 35.97 | **7.3×** | 每次 COMMIT 一次 WAL 追加；p99 200µs |
| SQLite WAL/NORMAL，50 行/事务 | **14.53** | 2.9× | 但每行仍要 27 次 bind + B-tree 插入 |
| SQLite WAL/NORMAL，60 行/事务 | **0.97** | **0.20×** | 摊薄后反而比文件快（省掉 60 次 syscall） |
| SQLite DELETE/OFF，逐行 | 117.91 | 23.8× | 无 WAL，每行一次库文件写 |
| 文件：write+**fsync**/行（对照，非现状） | 1,465 | 295× | 单次 fsync p50 **920 µs** / p99 3,865 µs |
| SQLite WAL/**FULL**，逐行 | 2,423 | 488× | 每行一次 fsync，等价于给每行加 0.9ms |
| SQLite DELETE/**FULL**，逐行 | 9,435 | **1,903×** | p99 29,972 µs（30ms 卡顿） |

关键事实（[实测-本机] bench-report.md）：
- **fsync 在本机 p50 = 920~1,417 µs、p99 = 3.9~6.1 ms**。这是所有 `synchronous=FULL` 方案的单价。
- 现状文件路径**完全没有 fsync**，只有 `write()` 进页缓存 —— 所以它的持久性等级 = `WAL+NORMAL`，不是 `FULL`。
- **WAL 的 checkpoint 会制造尾延迟**：默认 `wal_autocheckpoint=1000` 页（≈4MB）下，35,454 行逐行提交中有 **74 次（0.21%）超过 1ms，最大 16.8ms**，累计卡顿 354ms。**这 0.21% 直接落在调度线程上**（status 写入在 `scheduler_ipc` 1s 块内），是数据库方案唯一无法通过批处理消除的确定性抖动。
- WAL 稳态体积 ≈ **4.0~4.1 MB 常数**（不随数据增长），但它与主库一起被计入目录预算。

### 2.1 换算到 1 Hz 设备（[推算-设备]）

| 方案 | 单核占用 | 每秒调用方阻塞 | 备注 |
|---|---|---|---|
| 现状文件 | 0.009% | ~5 µs | 无 fsync |
| WAL/NORMAL 60 行批 | 0.001% | 0.02~1 ms（批量窗口） | 需引入队列线程 |
| WAL/NORMAL 逐行 | 0.043% | **36 µs + 0.21% 概率 1~17 ms** | 抖动是主要问题 |
| DELETE/FULL 逐行（最坏） | 2.3% | 0.9~2.4 ms **每行** | 已接近 daemon 自耗的 2/3 |

**真正的风险是阻塞分布，不是吞吐**：`status_write_line` 在调度线程 1s 块内同步调用，
一次 16.8ms 的 checkpoint 停顿 = 一次调度决策延迟 16.8ms。现状文件路径的最大单次成本是 µs 级。

## 3. 磁盘与归档：数据库更大，且压缩率更差

| 对象 | 原始 | zstd -2 -T6 | 压缩率 |
|---|---|---|---|
| status.csv（35,454 行 / 14h） | 5,378,539 B | **1,059,967 B** | 0.197 |
| 同内容 SQLite（27 列 typed + 2 索引） | 7,098,368 B | **2,015,200 B** | 0.284 |
| **比值** | **1.32×** | **1.90×** | — |
| devimp 14h 文本目录 | 134.3 MB | **10.24 MB** | 0.076 |
| 同内容 SQLite（main 45 列 + aff 帧） | 145.1 MB | **15.77 MB** | 0.117 |
| **比值** | **1.08×** | **1.54×** | — |

**归档预算（`logd/` 256MB→200MB、`devimp/` 256MB→200MB）是按 zstd-2 后的字节计的**，
所以上表的压缩后列才是真账：
- status 侧：**归档体积 +90%**
- devimp 侧：**归档体积 +54%**

原因：CSV/文本的列内冗余（同一进程名重复、数字前缀重复）在 zstd 下压得极好；
SQLite 的 B-tree 页把行打散、填充零字节、加页头，破坏长距离匹配。**这是结构性的，换参数无解。**
（zstd -19 略好：status 768KB vs 1,012KB = 1.32×，仍不如 CSV。）

## 4. 离线分析：收益存在，但绝对量很小

14h 真实包上实测（[实测-本机]）：

| 查询 | CSV 逐行 | SQLite | 加速 |
|---|---|---|---|
| 1 小时窗口行数 | 70.3 ms | **0.2 ms** | **393×** |
| 按包求 `batt_power_w` 均值 | 113.0 ms | **8.6 ms** | 13.2× |
| 60s 聚合 | 80.4 ms | **18.9 ms** | 4.2× |
| **本仓库现成脚本** `dvstatus.py` 全文件 | **1.03 s** | — | 基准 |

但整条流水线的真实分布（[实测-本机]，对 `logd_1016-151808.tar`）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| `dvextract` | 0.1 s | 解 tar |
| `devimp-analyze.py` | 3.69 s | 独立脚本 |
| `dvmain.py` | 15.79 s | 逐行 split |
| `dvaff.py` | 21.42 s | 差分合并 + 存活集合 |
| `dvstatus.py` | 1.03 s | |
| 全链 `dvrun.py` | **5 m 07 s** | 8 个阶段 |

**换 DB 能省的是 `dvmain` + `dvaff` 那 37s 里的一部分（实测 SQL 聚合 229ms vs Python 17s 的解析），
但前提是导入成本先付掉：585,920 行导入 SQLite = 6.99 s（11.9 µs/行），
比 tar 解开 + 逐行 parse（0.17s）贵 40 倍。** 归档里直接发 `.db` 才能跳过导入（此时解包+查询 62ms vs 201ms）。

## 5. 数据库救不了的三件事（容易误判的收益）

1. **`build_aff_snapshot` 的 /proc 采样**：25.16 ms/帧、占 daemon 自耗 14.5%（满速 1 帧/s 时 46%），
   是 devimp 开销的绝对大头（是存储写入的 55 倍），与存储无关。
2. **128MB 重启节奏**：现状按「写入字节」记账，重启每 13.3h 一次、每天停机 5.4s。DB 化后
   记账口径必须换（`page_count*page_size` 或独立 AtomicU64，见 inventory I1），**但节奏不会自动变好**——
   devimp 的字节量本身没变。要减少重启得改采样率/字段，不是换存储。
3. **归档压缩与 tar**：`pack.sh` 只吃目录（禁止修改），tar 134MB = 0.12s、zstd-2 -T6 = 0.12s，合计 0.24s/次，
   1.80 次/天 = **1 J/天**。这部分无论换什么存储都要付，且 DB 会让它变大。

## 6. 迁移成本（不是性能，但会决定可行性）

- **破坏 11 条已确认不变量 + 2 条部分破坏**（14 条中 0 条可反驳）。最硬三条：
  - 启动归档对 `logs/`、`devimp/` 整目录 `fs::rename`（`src/logger.rs:2363/2390/2404`）——
    DB 有打开句柄 + `-wal`/`-shm` 时 rename 会写到已 unlink 的 inode，且 `-shm` 无法被新进程 attach；
  - 「dev_record 关闭时零 IO、`devimp/` 不预建」（`src/logger.rs:933/1226/1789/2118` vs `agentsdocs/02-convention.md:17⑦`）——
    打开 SQLite **必然**创建 3 个文件，契约级冲突；
  - `module/scripts/pack.sh:26-38` 只打**目录**且禁止修改。
- **下游**：Python 10 模块 4,040 LOC（+744 测试）、WebUI 7 模块 1,442 LOC；**必改 ≈ 4,440 LOC**。
- **离线构建**：本机两份 cargo 缓存共 1,228 个 crate，**sqlite 系零命中**，无 vendor、无网络 ⇒
  `rusqlite + bundled` 的 Android 离线构建**当前不可能**，需先联网 `cargo fetch`。
  拿到 crate 后机制可行（NDK r29 + `aarch64-linux-android` + `CC_/AR_` 注入已就绪，与 `zstd-sys` 同路），
  预计构建 +40~90s、二进制 +0.7~1.2MB。

## 7. 建议

| 目标 | 建议 | 理由 |
|---|---|---|
| 省 CPU / 省电 | **不做** | 存储只占 0.18% 自耗；DB 逐行提交反而慢 7.3×，且引入 0.21% 概率的 ms 级抖动 |
| 减小归档 | **不做** | 归档体积 +54%~90%，与「减小」相反 |
| 离线分析更快 | **不做 DB，改索引/列存**（见下） | 收益的 90% 可从「按需只读需要的列 + 一次遍历出多聚合」拿到，零迁移成本 |
| 分析代码更简单 | 混合方案（status+devimp 入库，`daemon.log` 留文件） | 只破坏 6 条不变量，保住 daemon.log 全部契约；Rust ≈900 / Python ≈2300 / WebUI ≈500 LOC |

**若一定要做，三条硬约束**：① `journal_mode=WAL` + `synchronous=NORMAL`（与现状文件同等持久性，实测 kill -9 零丢失）；
② **绝不逐行提交**，至少 16 行/事务（1Hz 场景下 60 行更优）；③ 归档直接发 `.db`，否则导入成本（26 µs/行）吃光读端收益。

**低成本替代（推荐先试，无需迁移）**：
1. `dvaff.py`（447 LOC 差分合并）与 `dvmain.py` 的解析热点改用 `csv.reader` + 单次遍历多聚合（现为逐行 `split(',')`），
   预计能从 37s 降到 10s 量级 —— 与 DB 的读端收益同级，但零风险。
2. status.csv 分析侧建一次性的「列偏移索引」（旁挂 `.idx` 文件），把窗口查询从 70ms 降到 ms 级。
3. 若只是要「SQL 手感」，加一个**离线一次性转换器**（tar → 临时 SQLite，分析完即删），
   完全不碰 daemon 写路径与 `pack.sh` —— 这是收益/风险比最高的切法。

## 9. 口径声明

- 所有「占 daemon 自耗」的比例以 14h 实测（daemon 3.40% 单核 = 1,714 s）为分母；
  `@S` 帧率实测 0.196 帧/s，非设计值 1 帧/s，两者折算结果在 §1 注中并列。
- 本机是 **x86_64 桌面 + NVMe + btrfs**，不是骁龙 8 Gen 2 设备；UFS 3.1 的 fsync 通常比本机慢 2~5×，
  因此所有含 fsync 的数字在设备上会**更差**，不含 fsync 的数字（文件 `write()`）量级接近。
- `status.csv` 行字节数实测 151.7 B（27 列），与早期文档中的「~300-400 B」不同，以实测为准。
- 128MB 门限 13.3h 由 230.2 MB/天 直接推算；真实包 14h 内只发生 1 次归档（daemon.log 第 2 行），
  与「每 13.3h」一致，但单包样本不足以做分布统计。
