## 2. 逐项审查结果

### 2.1 P0 FAS 写频失败状态污染

**第二轮 verdict：核心缺陷成立；原计划需要把写失败、读回钳制和恢复上界拆成不同状态。**

**源码证据。**

- src/scheduler/fas/policy_controller.rs:145-151 调用 min/max FastWriter 后丢弃两个 bool；:152-155 仍更新 current_freq、hold、verify_freq；:156-159 的 verify_at 只在 changed 或原值为空时更新。
- src/utils.rs:529-536 在 writer file 缺失时返回 false，:537-570 对 errno 也返回 false。policy_controller.rs:163-164 的 TODO 已说明只读 scaling_max 无法区分写失败与 QoS 钳制。
- policy_controller.rs:286-300 的当前读回以 read_scaling_max_freq 为锚；actual<expected 在 :222-226 可是 qos_clamped，:306-312 是 force reapply 路径。raise 的 max-success/min-fail 可能被 max 读回掩盖，lower 的 min-success/max-fail 可能进入 tamper/rewrite。
- reset :314-319、init :444-445 同样丢写结果；EACCES/EROFS 重开只覆盖一次 writer 生命周期，不等于无界重试，re_unmount 也只 umount，不自动重开旧 fd。

**后果与审查边界。** 双写失败仍可能推进 hold/verify，目标不变时冻结；qos_clamped 与真实写失败不能合并为同一恢复结论。审查没有声称所有失败都能被 force_interval 修复，要求分别给出 dirty/write_failed、qos_clamped 和 verified 的恢复上界。

**已吸收的修订。** 计划 :42-63、:193、:201、:231 已改为三层状态：min/max 各自 write_ok、scaling_max_freq readback、可行时 scaling_min_freq 或 settle 后 scaling_cur_freq；覆盖 init/apply/300s probe/tamper/force/reset、半写方向、QoS、dirty/hold/迟滞/force 优先序和恢复时间，并迁移 controller.rs:508-529、:653、:668、:812-813 的假成功测试。未先完成 fake writer seam 和 golden 状态机，禁止实施。

### 2.2 P1 EEM ELF32 预检拒绝与回执

**第二轮 verdict：ELF32 skip 是明确缺陷；它不能与已接受的 ledger 预提交或普通 abort 合并。**

**源码证据。**

- ELF32/AArch32 门在 src/chiri/affinity.rs:1231-1243，调用点在 :2726-2728；:2702-2723 是 dst_mask 求交和空集处理，不是 ELF32 门。
- src/chiri/placement.rs:509-519 在 affinity 落盘前已经写入 plan.target/e.window/cluster 并提交 ledger。该预提交是 placement.rs:512-516 明示的预算有界取舍，不应被误报成 ELF32 bug。
- :1240-1242 使用 any；config.rs:1538-1540 的 aarch32_clusters 缺省为空时放行。两拍 old∪new 可能第一拍含任一可行簇而通过，下一拍纯不兼容目标才 skip。
- readback None 与 Some(empty) 共同落入 unknown 分支；note_narrow(errno=None) 可增加 fail_streak，非空 clipped 的 note_applied 会清零。cgroup move 成功后的 abort 只恢复 engine/EEM 镜像，不回滚已完成 move；Subject/eem_window 可能仍指向旧证据。

**后果与量化。** skip 不会走普通结构性失败的 abort/backoff 归属，可能重复承诺同一不可写目标；仅补 abort 不保证下一轮锚点收敛。计划要求不依赖 diag_active 的 skip/clipped/readback-unknown 计数，逐轮对账 planned/applied/effective/window/ledger/Subject/eem_window、fail_streak/backoff、cgroup move 和下一轮候选。

**已吸收的修订。** 计划 :65-78、:194、:202、:232 已分离预检门、预提交 ledger、anchor 修复和可观测性，并增加 default-empty、并集首拍、Some(empty)、moved_group rejection fixture。保持 effective/transition、回读、cgroup move 不回滚和预算语义；不得把“补 abort”作为未经验证的统一修复。

### 2.3 P1 scenemode 两处 fold 的 prime 意图

**第二轮 verdict：sm8750 的 prime 漏算成立，但进入与退出的 canonical 成员集合不能假设相同。**

**源码证据。**

- src/chiri/mod.rs:4442-4448 的进入门和 :4498-4505 的退出/饱和门都只 chain little→big；src/common.rs:277-305 返回 little、big、prime 三段。
- sm8750 的 little 0..0、big 0..6、prime 6..8，所以当前两个 fold 只覆盖 CPU0-5；src/chiri/core_ctl.rs:982-985 是同仓库 chain 三段的对照。
- :4441 以“常驻簇顶满”为语义，:4495-4496 以“全部在线核”为语义；这两个站点可能有意不同。msm8998 的 prime 为空且 big 已覆盖全域，是必要的负对照。

**后果与验证。** 影响范围限于 scenemode 进入/保持/退出及息屏期状态，不外推到整条调度链。若盲目统一集合，可能造成 long_off+prime 饱和时进入→10s 退出→300s 冷却拉锯。需覆盖 sm8750、msm8998、其它 fallback、缺 topology、空 load、越界/离线（区分缺项=0 与陈旧 util）、阈值边界、60s precheck、FAS/特调排除、scene_hold_logged 和 cooldown。

**已吸收的修订。** 计划 :80-86、:203、:233 将两处 fold 作为独立意图确认项，修复前不缓存集合；只有 P1 语义对账后，才允许考虑拓扑集合去重缓存，不改 SoC 配置、阈值或锁序。

### 2.4 P1 EEM allowed 与 cluster_pool 的核级连续窗口

**第二轮 verdict：核级正确性缺口成立；原先把问题归因到 syscall/readback clipping 不准确。**

**源码证据。**

- src/chiri/placement.rs:298-306 的 cluster_pool 只表达拓扑；:51-77 的 Window::new/width/cores 要求连续编号。:207-269 的 cheaper_cluster/lighter_cores 在整簇连续池上选窗。
- src/chiri/affinity.rs:2550-2556 只有 cluster-level any 门控；部分 allowed 簇仍能把禁止核放进 plan.target。:2693-2701 才在 syscall 前将意图与 allowed 求交成 dst_mask，:2702-2724 处理空集。
- allowed 在 :2500-2503 是 cpuset∩online；decide 的 online 是簇级信息；allowed=None 在 :2550-2551 使用 online_all。:2726-2728 的 mask_write_allowed 拒绝不会 abort。
- placement.rs:504-516 的 plan.target/e.window/ledger 与 dst_mask、回读锚点可能分叉；Ledger::commit 按 Window::cores 摊 demand，未过滤的 dst_load/residual 会把禁止核计入成本。

**后果与验证。** 非连续 allowed 不能直接压成一个 Window，否则迁移和 ledger 成本都可能错误。计划要求 full/partial/empty、宽度>1 混合、非连续、None/Some(empty)、TTL/hotplug、拒绝和非连续回读 fixture；对 cheaper_cluster 宽 1 和 lighter_cores 宽 w 的每个返回 Window，逐核断言属于 allowed∩online∩cluster。partial allowed 只能拆成极大连续段，或显式拒绝。

**已吸收的修订。** 计划 :88-96、:203-204、:234 已把连续窗口和 ledger 逐核不变量作为 P1 闸门；P3 cpuset clone 不再替代这项正确性验证。

### 2.5 P1 CLG 条件性重复扫描

**第二轮 verdict：重复扫描存在，但只在非空 on_load_update 决策 tick 上形成通常 2A、条件 3A；不能用它代表所有 CLG/EEM/诊断开销。**

**源码证据。**

- src/chiri/cpu_load_governor.rs 的 on_load_update、max_util 和 high_zone_hits 分别扫描 affected_cpus；当前并发 worker stop 修改使 HEAD 行号可能后移，实施前必须以最终符号/差异为准。
- config.rs:367-369 的默认 high_zone_count=0 使 3A 默认不可达；只有 count>0（例如 8550）、old_perf>=gate、目标仍上抬且 hits>=need 等条件才增加 high-zone 扫描。over/under 只作诊断字段，不参与控制判据。
- 保留 over>、under<、hits>=、old>=gate、candidate>old+1e-6、hits>=need、wait>=hold；max_util/over/under/demand 对 NaN 的处理不同；high_zone_util=0 的 >= 语义、eff_cfg gate/hits 与 self.cfg need 不能合并。
- EEM flush/1s timeout 还会遍历 demand_units、occupied、busy_cores；并非 CLG 的 2A/3A。并发 stop 先 recv 再判 stop 可能丢末包。

**已吸收的修订。** 计划 :98-108、:195、:209、:235 将 on_load_update 决策、空包/timeout、EEM、diag、配置 count=0/8550 count=2 分开记账；保留 short core_utils、hz_hold 的 over/under 和 stop 丢末包语义，并要求 replay_clg.py 的 Rust 源码提取与 clg_replay.rs 模板同步。是否聚合扫描只在 pure seam、golden trace 和完整分母通过后决定。

### 2.6 P1 telemetry/status 事件线程开销

**第二轮 verdict：事件线程的同步节点读、status writer 和 PowerAVG 成本成立；将其移到 worker 的收益与等价性尚未证明。**

**源码证据。**

- src/chiri/mod.rs:3155-3421 混合不同门控：cpu_snapshot/main_snap/aff 受 diag_active、aff_snap_due 等门控，普通节点读、status 行和 PowerAVG 没有同一外门；:3422-3439 的 Debug 摘要另列。monitor 在 src/monitor/mod.rs:439、src/monitor/telemetry.rs:231-232 独立运行，不能把事件线程称为整体 telemetry build。
- src/logger.rs:585-624 的 status.csv writer 有 Mutex、两次无缓冲 write_all、失败重开、轮转和 LOGS_BYTES_WRITTEN 记账；:739-741 是 frozen 短路，:742-768 是 28 列顺序，未发现 status 路径 flush/sync_all。
- 应分别测 read_battery_temp_celsius、temp sensor read_f64_from_file、read_battery_charge_state、read_screen_prop_raw、self_cpu_ms、self_rss_kb、status 构造和 PowerAVG。diag_cost.rs:13-36、:148-171 的 selfcost/1 在 mod.rs:3245/3419 受 diag_active 门控，不能与无门段直接相加。

**后果与验证。** 线程化若队列满阻塞事件线程会把收益变成尾延迟；丢数据也不能作为降采样。计划要求独立 always-on 计数或已标注偏差的 diag 测量、sender 时间戳、有界 try_send/丢弃计数，保留 batt/cpu filter、身份/代际顺序、activity request、PowerAVG、DOWN、rotation、main_/status.csv 和 28 列。

**已吸收的修订。** 计划 :110-118、:196、:217-218、:236 先做 SnapshotRow golden-row、门控分层和队列/尾延迟基线；只有证明事件控制尾延迟受影响才考虑按序 worker。

### 2.7 P1 heavy/loading/warmup 长帧边界

**第二轮 verdict：边界和 stale→warmup 活性问题成立；“静默漏采样”或“全部 thermal/apply 停摆”均不成立。**

**源码证据。**

- src/scheduler/fas/frame_pipeline.rs:315-319 先做 500ms stale reset，:321-349 是 warmup，:351-353 用 <= max_ns，:355-357 是 app switch，:359-368 是 heavy/loading，:369-384 才是 >max 的长帧。
- 默认 heavy_frame_threshold_ms=150、fixed_max=500；因此默认 :369-384 不可达，只有 heavy>=fixed_max 或更早 app-switch 边界才可触达。150.001–3000ms 每帧从 loading/heavy 分支早退；累计 loading >2500ms 且退出 loading 才可能钳 perf。
- 连续 heavy 不刷新 last_frame_at，可能触发 stale→warmup=12，后续 600ms 帧又不减 warmup。SystemLoadUpdate/on_load_update 仍可推进 thermal/apply，不能把帧域早退写成整个调度器停摆。

**已吸收的修订。** 计划 :120-126、:197、:205、:237 要求 150.0/150.001、500.0/500.001、3000.0/3000.001、600ms、3100ms、连续长帧、heavy>=fixed_max、perf_lock、冷启动过期、loading 退出/普通恢复 fixture；分别断言 last_frame_at、warmup、jank、FpsWindow、PID、FrameUpdate writer 和 SystemLoadUpdate writer。不增加 capped sample 或窗口容量。

**已吸收的修订。** 计划 :128-134、:196、:238 先统计 fast_same 命中率和慢路径份额；第一阶段只把 :4569-4574 证据作为参数传入，其余调用点传 None，第二阶段才合并 latest，纯 evidence→decision 缓存最后评估。TTL 在读取时以 now-observed_at 重新计算，并用 cache on/off golden decision+side-effect trace 验收。

### 2.9 P2 频率迟滞归一化坐标

**第二轮 verdict：坐标混用成立，偏差有方向，修复应先于任何 policy 数学复用。**

**源码证据。**

- src/scheduler/fas/policy_controller.rs:71-77、:133-135 使用 A(f)=(f-fmin)/(fmax-fmin)；src/scheduler/fas/policy_mgmt.rs:267-272 使用 pre-blend f_ref/fmax 与 current A，真实档位在 :267 的 target_freq=find_nearest_freq(adj)。
- 偏差 old-new=fmin*(fmax-f_ref)/(fmax*(fmax-fmin))，可在真实位移为零时改变档位并超过 d_hysteresis=0.015；升频放大，降频缩小甚至跨零。w>1 时 adj<=ratio，pre-blend 坐标低估降频位移。
- current_freq 是命令值，QoS clamp 不等于实频；current_freq 不在表时 current_ratio 可大于 1。

**已吸收的修订。** 计划 :136-142、:204、:239 统一 target/current 经纯函数 F(f)，比较 |F(target)-F(current)|，覆盖 fmin/fmax、freq_max=0、空/单点/乱序表、中点低位 tie、adj==ratio、QoS/hold/force，并把 beta 明确为 blend。坐标修复与其它 policy 优化分批，不改 thermal/force/hold/tie-break。

### 2.10 P2 scenemode iterator 成本

**第二轮 verdict：迭代器本身是零分配；mode/config clone 和门控可能更值得测，默认缓存应关闭。**

**源码证据。**

- src/chiri/mod.rs:4428 的 mode clone、:4430 的 is_special_mode、:4436 的 CLG config clone 可能比 :4442/:4498 的 6–8 核 Range/Chain/FilterMap/fold 更贵。
- src/common.rs:265-305 的 Range/Chain/FilterMap/fold 与 OnceLock 不产生堆分配。prime 仍是 P1 成员语义问题；msm8998 可能有 big⊃prime 重叠，缓存集合必须去重。
- 初始化不能放在 :4433-4437/:4477 config 锁内；拓扑 OnceLock 固化，不需要失效钩子，但 online/last_core_utils/场景态不能缓存。

**已吸收的修订。** 计划 :144-148、:209、:240 要求拆分 chiri_core_ranges、iterator、fold 的成本；低于 ledger 分辨率或 <10us/帧且 <0.1% 调度线程 CPU 即结项。只有 P1 成员意图确认后，才考虑拓扑去重并集索引和 cache on/off 逐拍 golden trace。
