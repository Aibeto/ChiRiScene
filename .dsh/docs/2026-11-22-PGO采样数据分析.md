# PGO 采样数据分析（logd_1122-160240）

> 数据来源：`devimpbin/logd_1122-160240.tar`（14,658,048 B，2026-11-22 16:03），含两个 daemon 生命周期的日志与 PGO 产物
> 分析口径：只用 perf.data 自身的 DSO / tid / IP 记录 + 同源重建二进制的符号表；未改动任何线上参数
> 设备：OnePlus 11（`OnePlus/PHB110/PHB110`），SM8550，Android 16 / SDK 36，内核 `5.15.197-o-g5f6c469e916c`，模块 versionCode 50302
> 注意：这台机器不是本机 adb 常连的 OPD2511（`5.10.236-android12-9`），两份设备的 ETM 可用性不能互相外推

## 一、结论速览

| 问题 | 结论 |
| --- | --- |
| 数据完整吗 | 完整。9 轮会话全部成功落盘，`record_stat` 各轮 `lost=0` |
| 能直接喂编译器吗 | **不能**。样本量差 1~2 个数量级，且 98% 函数零样本，喂进去会被判冷 |
| 采样本身贵吗 | 便宜。9 轮共 549 s 墙钟只覆盖 49.2 s CPU（单核 9.0%），日志压缩后仅占 1.5 MB |
| PGO 收益天花板 | **≈0.5 s CPU / 4.3 h**（用户态+libc 共占 8.8%，就算整体快 10% 也只有这么多） |
| 数据真正说明了什么 | chiri 的 CPU 大头不在自己的代码：内核态 78.7%（唤醒 25.3% + `/proc` 任务扫描 10.8%）、`dumpsys` 子进程 6.4% |
| 现存代码缺陷 | `exe=` 指纹是噪音、`pid=` 打错对象、`-f 200` 太低、`inherit` 混入子进程；另缺 build-id 导致离线无法精确符号化 |

## 四、能不能拿它做 PGO

**换算链现状**（实测）：

- `llvm-profgen --binary chiri --perfdata perf_*.data` → `error: Perf not found`：它只认 Linux `perf` 的 PERF 格式分支栈记录，不认 simpleperf 的 `PERFILE2`
- `simpleperf inject --output autofdo` → 只接受 `cs-etm` 录制文件或 `branch-list`；本机两轮都是 `tier=2`，没有 ETM 数据
- 手工链路可行：`simpleperf report --sort symbol` 取 IP 偏移 → 用 `.text` 起点换算 → 查符号表得函数 → 写 LLVM 文本采样格式（`func:count:0`）。本轮已生成并在 `llvm-profdata show --sample` 下解析成功（449 个函数），**格式没问题，问题是数据量**

**数据量差距**：

- 用户态只有 1357 样本、512 个函数；最热函数 ~39 样本（±16%，1σ）
- `-f 200` 的语义是「每 CPU 秒 200 样本」，所以延长墙钟不涨样本，只有提高 `-f` 才涨：`-f 1000` → 约 4.9 万样本（最热函数 ~200），`-f 2000` → 9.8 万（perf.data 体积同步 ×5~10，单轮约 5~10 MB）
- AutoFDO 想在函数级稳定，热函数需要 1e4 量级样本；按当前负载要连续采几周
- 而且 **98% 的函数零样本**：`-Cprofile-sample-use` 会把未出现的函数按冷处理，直接喂进去大概率是负收益

**收益天花板**：chiri 用户态 + libc = 8.8% 的自身 CPU = 4.3 s / 549 s。就算 PGO 让这部分快 10%，也只省 0.43 s CPU / 4.3 h（约 0.02% 单核）。**在这台机器上，PGO 不是性能杠杆**；它的价值只剩「跨版本对比的长期遥测」。

## 五、`src/pgo.rs` 需要修的点（都不影响调度行为）

| # | 现象（证据） | 根因 | 建议改法 |
| --- | --- | --- | --- |
| 1 | `manifest.txt` 的 `exe=0:1795318822`；第二个实例两条还是 `0:1795331945` / `0:1795333723`（同一进程内都不同） | `src/pgo.rs:452` 对 `/proc/self/exe` 取 `symlink_metadata`（符号链接本身，大小恒 0）+ 链接 mtime（会随读取变化） | 改成 `fs::metadata` 跟随链接取真实 size+mtime；更稳的是记 ELF build-id 或 `sha256(core/bin/chiri)[..8]` |
| 2 | daemon.log 每轮 `pid=` 都不同（15500/15253/2968…），但 perf.data 的 cmdline 恒为 `-p 14929` | `src/pgo.rs:391` 打的是 simpleperf 子进程 pid | 改打目标 pid（`std::process::id()`），或两个都打并标注 |
| 3 | 9 轮只有 9845 样本 | `SAMPLE_FREQ=200` 太低 | 若还要继续做 PGO，提到 1000（`MAX_FILES_BYTES=24MiB` 需同步调大或减少保留份数） |
| 4 | `dumpsys` 子进程占了 6.4% 样本 | `inherit=1` 把子进程也采了 | 加 `--no-inherit`（只采 chiri 自身线程）；若想观测子进程成本则保留 |
| 5 | 离线无法精确符号化 | 发布二进制 strip 且无 build-id；`perf.data` 里 chiri 的 build_id 记录为空 | 链接期加 `-Wl,--build-id=sha1`（约 +48 B，不影响运行），或打包时保留未 strip 副本（更贵，约 +9 MB） |
| 6 | `dvextract.py` 解这份包时崩溃 | `FileNotFoundError: …/x_1122-151751/manifest.txt`（`pgo/manifest.txt` 在子目录，脚本按顶层找） | 脚本容错：顶层缺失时去 `pgo/` 找，并把 pgo 段纳入 `records` 统计 |

另外：`perf.data` 与日志同包时压缩比很好（7.06 MB → 这轮日志 tar 共 1.24 MB），**采样对归档体积的代价可以忽略**；单轮耗时固定 61 s、每 30 min 一轮，对续航影响可忽略。

## 六、顺带暴露的三个非编译优化点（需你拍板，涉红线）

1. **`/proc/<pid>/task/<tid>/stat` 全量扫描**（10.8% CPU，来源 `src/monitor/cpu_monitor.rs:62-64,172`）：可选方向是只采 Top-N 候选进程的线程、或在 TGID 级用 `/proc/<pid>/stat` 的 utime+stime 代替逐线程。注意 `agentsdocs/04-hard-lessons.md:38`「热路径值缓存」已定案不做，这里属于「减少读取范围」，与缓存不是一回事，但也改采样语义。
2. **唤醒/调度占 25.3%**：`aff_sample_0..3` 四线程 + `cpu_monitor` + `fps_probe` + `activity-sample` 各自定时唤醒，`finish_task_switch`+`__schedule` 合计 1299 样本。降频或合并定时器能省，但会改变采样时点。
3. **`dumpsys` 子进程 6.4%**：每次 `activity/window` 探测都是一次 fork+exec+dumpsys 启动。可考虑复用一次 `dumpsys` 输出或改用 `/proc`+`service call`，但属于行为改动。

## 七、建议

- **PGO 维持「长期遥测」形态**，离线换算链暂不投入（数据量要到 1e4 量级才有意义）
- 真正值得投入的是 §六 的第 1 项（`/proc` 扫描），量级比 PGO 大一个数量级；但三项都改采样/探测语义，需先定口径再动手

## 八、2026-11-22 整改（按用户决定落地）

用户口径：`2. PGO 采样可以再多一些`、`3. 修`（指 §五 第 6 项 `dvextract.py` 崩溃）。

### 8.1 采样量上调（`src/pgo.rs`）

| 常量 | 原值 | 现值 | 依据 |
| --- | --- | --- | --- |
| `SAMPLE_FREQ` | 200 Hz | **1000 Hz** | 每 CPU 秒样本数 ×5；200 Hz 下 9 轮只有 9845 样本、98% 函数零样本 |
| `SESSION_SECS` | 60 s | **120 s** | 单轮窗口 ×2，兼顾开机/前台切换等不同阶段 |
| `MAX_FILES` | 16 | **24** | 单文件涨到约 9 MB 后份数不再触顶 |
| `MAX_FILES_BYTES` | 24 MiB | **64 MiB** | 约 7 轮（≈3.5 h 历史）；归档时 zstd 压到约 1/8，仍在 `LOGD_MAX_BYTES=256 MB` 预算内 |

预期：单轮约 1.1 万样本（原约 1.1 千），每天（30 min 一轮、48 轮）约 50 万样本 ⇒ 数天即可让热函数积累到 1e4 量级。
代价：`logs/pgo` 常态占 64 MiB（`LOG_RESTART_THRESHOLD_BYTES=128 MB` 的一半以内），每份归档约 7~8 MB 压缩后体积。

### 8.2 数据可读性修正

| 项 | 改动 |
| --- | --- |
| `exe=` 指纹 | `std::fs::symlink_metadata` → `std::fs::metadata`（跟随链接，取到真实 size+mtime） |
| `pid=` 语义 | 改为 daemon 自身 pid，并新增 `sampler=` 记 simpleperf 子进程 pid（zh.ftl/en.ftl 同步） |
| build-id | `build.rs` 加 `cargo:rustc-link-arg-bins=-Wl,--build-id=sha1`，让 perf.data 能认出二进制（约 +48 B note，不影响运行） |

### 8.3 `dvextract.py` 修复

- **根因**：`extract_tar_bytes` 只返回 `os.path.basename`，含子目录的成员（`pgo/manifest.txt`）被拼成 `x_<stem>/manifest.txt` → `os.path.getsize` 抛 `FileNotFoundError`。现改为返回**相对路径**，并对未落地成员（符号链接等）跳过记录。
- **顺带**：`sniff()` 增加 `PERFILE2`（simpleperf perf.data）识别。此前 perf.data 被 tar 的名字/mode 启发式误判，每个文件刷一条「不是合法 tar / bad checksum」，既污染输出又浪费解析。
- **顺带**：`inventory.txt` 追加 `# pgo: N 个 perf_*.data，共 X bytes；manifest.txt M 份`，一眼看出这份包有没有可用采样。
- 验证：对 `devimpbin/logd_1122-160240.tar` 实测通过（237 文件、devimp 批次 2 / logd 批次 2、无告警、`# pgo: 9 个 perf_*.data，共 8196153 bytes；manifest.txt 2 份`）。
