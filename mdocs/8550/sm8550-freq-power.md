# SM8550 频率 ↔ 功耗对照（dtsi 基础数据 + Odin 2 实测电压）

> 索引：`[coefficients]` `[opp]` `[k2mw]` `[efi]` `[bw]` `[ratio]` `[limits]` `[check]` `[sweetspot]`

- 基础数据：`mdocs/8550/sm8550.dtsi`（mainline Linaro 2022）。频率档位、`capacity-dmips-mhz`
  （326/693/1024）、DPC（251/447/1057）、角落与 L3 票全部来自该文件（CPU 节点 76–295 行、

- 电压/实测功耗：AYN Odin 2 (QCS8550) EAS 补丁实测表（Xilin Wu, 2024-04-24,

- 定位：校准参照，不是运行时输入（ChiRi 读不到 DT）。频率档位已与真机
  `scaling_available_frequencies` 逐档核对一致（`.archive/.codebuddy/docs/2026-09-26-sm8550-opp-ladder.md`）。
- 生成 2026-09-27；同日改版：废弃统一 V=1.0 V 直线模型，引入 Odin2 电压，A715/A710 拆分。57 个 OPP 已回算校验（第 7 节）。

## 0. [coefficients] 结论先行

单核功耗模型仍是 `P_core[mW] = Cx × f[GHz] × V²`，但 V 不再是假设值：
电压逐档借自 Odin2 实测表（来源见文首）。V(f) 超线性，功耗-频率关系是一条曲线，
能效随频率上升而劣化，簇内出现拐点。

Cx 按核型取值（每 CPU 节点一个系数，按单核计）：A510 251 / A715 472 / A710 421 / X3 1057。
其中 251/1057 与 dtsi 官方 DPC 相同；big 簇 dtsi 只写一个 447 = (472+421)/2（Odin2 补丁
测得 A715、A710 各一值后取平均），逐核推理按 472/421 分列；簇级口径用 447 结果几乎相同
（472×2+421×2=1786 vs 447×4=1788，差 0.1%）。

电压来自 EPSS 硬件 LUT 而非 DT，内核侧结论不变：`drivers/cpufreq/qcom-cpufreq-hw.c` 的
`qcom_cpufreq_hw_read_lut()` 在 probe 时读 LUT 注入运行时 OPP：

```c
volt = FIELD_GET(LUT_VOLT, readl_relaxed(base + reg_volt_lut + i * lut_row_size)) * 1000;
... qcom_cpufreq_update_opp(cpu_dev, freq, volt);
```

DT 的 OPP 表在驱动里先被整体 disable，只用于交叉校验频率档位。真机实测功耗读
`/sys/kernel/debug/energy_model/cpu<N>/ps:<kHz>/power`；本文件用 Odin2 电压推算的功耗
是参考曲线，真机口径以 energy_model 为准。

## 2. [k2mw] 口径说明：两套功耗数字为什么对不上

表里同时有「单核功耗 W（推理）」和「实测参考 mW」两列，它们本来就不该相等，差异有两个来源：

1. 口径不同。Odin2 补丁的 mW 是假电池整轨实测扣底噪后的值（含漏电与板卡成分）；
   推理列 P = Cx·f·V² 只含动态项。补丁自带的逐档 Cx 列是差分口径，测量脚本
   （Doug Anderson `powernumbers.py`，2020-10 lkml，Odin2 作者在回信中确认用的就是它）按
   `Cx = (P_i − P_基线档) / (f_i·V_i² − f_基线档·V_基线档²)` 计算，基线是各簇未打印的最低档
   （little 307200 / big 499200 / prime 595200，这正是三张实测表缺最低档的原因），
   所以 Cx·f·V² ≠ P_i，偏差 ±14% 属正常；脚本最后 `DPC = round(mean(Cx 列))`，
   250.3→251、471.3→472、420.3→421、1056.1→1057，与 dtsi 的 251/447/1057 对得上
   （447=(472+421)/2）。
2. 芯片批次不同。Odin2 是 QCS8550 游戏掌机，批次/调校与 OnePlus 11 的 SM8550 不同。
   推理/实测比值：A715 0.949~1.026、A710 0.919~1.018、X3 0.926~1.040（±8% 内，可视为同款
   曲线）；A510 0.797~1.280（小核功率绝对值小，测量噪声被放大）。电压绝对值同理只作参考。

内核核实结论不变（`android_kernel_oneplus_sm8550`，OnePlusOSS sm8550_b_16.0.0 分支）：
每档电压不在源码/DT，`drivers/cpufreq/qcom-cpufreq-hw.c:266-290` probe 时逐项读 EPSS 硬件
LUT（`LUT_VOLT` 12 位，mV×1000 转 µV）经 `qcom_cpufreq_update_opp()` 注入运行时 OPP；
`sm8550.dtsi` 只有 rpmhpd 角落等级（`:5802-5859`，16 档等级 ID）与 GPU 频率↔角落映射
（`gpu_opp_table`，`:2894` 起），全文件无 `opp-microvolt`。真机每档电压仍取不到，
本文档用 Odin2 表借位。

每档算力口径也不变：单核算力 = `capacity-dmips-mhz` × f（`drivers/base/arch_topology.c:281-306`
读 DT 容量、`topology_normalize_cpu_scale()`（:245-268）归一化到 1024）；簇算力乘核数
（little 3 / big 4 / prime 1）。真机口径把 `cpu_capacity`（280/855/1024）按 f / f_max 缩放，
与 DT 口径只差一个线性标定系数。

## 3. [efi] 单核功耗-频率、单核功耗-算力 与 全簇总功耗-总算力 与 簇级功耗-频率/算力

五张图。①②是单核口径，横轴是单核功耗（推理值），纵轴分别是频率与算力；
图上每个小圆点 = 表里的一行。V(f) 超线性，所以 ①② 的曲线都是弯的：低频段平、高频段陡。
四条曲线（A510/A715/A710/X3）峰值差约 10 倍（little 0.311 W ↔ X3 3.079 W）。

  prime 冲顶段最贵（2092800→3187200 只剩 600 Mdmips/W）。
- ④ 多核功耗 → 频率：簇功耗 = 单核 × 核数（little ×3、big (A715+A710)×2、prime ×1），

## 5. [ratio] 簇间换算

| 关系                     | 公式                      | 结果                                                                                   |
| ------------------------ | ------------------------- | -------------------------------------------------------------------------------------- |
| 每 MHz·V² 功耗比         | Cx 比                     | A510 : A715 : A710 : X3 = **1 : 1.88 : 1.68 : 4.21**                                   |
| big 簇内同频功耗比       | 472/421                   | 同频同压下 A715 比 A710 费 **12.1%**；7-zip 实测 A710 反而快 4.6%（4632 vs 4416 MIPS） |
| 等价算力频率（DT dmips） | f × 326/693、f × 326/1024 | little f ↔ big 0.470f ↔ prime 0.318f                                                   |
| 每 Mdmips 功耗（低频段） | 表最低档                  | A710 0.185 < A715 0.208 < A510 0.229 < X3 0.319 mW                                     |
| 每 Mdmips 功耗（高频段） | 表最高档                  | A510 0.473 < A710 0.537 < A715 0.602 < X3 0.943 mW                                     |

等价算力频率与电压无关，照旧成立：little 2016000 ≈ big 948000（同算力）。
同功耗比较现在用真实 V：little 2016000 推理 0.311 W ↔ A710 940800 推理 0.154 W
（算力 657.2 vs 652.0 Mdmips 几乎相同，单核功耗差一倍），能效不吃亏时优先大核；
X3 只有单核算力需求 >2600 Mdmips 才值得上（它的每 Mdmips 从低到高劣化近 3 倍）。

capacity 注记：`capacity-dmips-mhz` 用 DT 的 326/693/1024，真机 capacity 实测 280/855/1024
（`module/config/8550/soc.yaml`）。

换算必须按内核 `cpu_capacity` 的语义来：它是**各自最高频处的相对性能**（prime 归一化到 1024），**不是每 MHz 速率**，所以真机算力(f) = `cpu_capacity × f / f_max`。
把「每 Mdmips 成本」换算成「每真机容量单位成本」的系数 = `dmips_mhz × f_max ÷ (1000 × cpu_capacity)`：little（326×2016÷(1000×280)）**2.347**、big（693×2803.2÷(1000×855)）**2.272**、prime（1024×3187.2÷(1000×1024)）**3.187**。

换算后（mW / 容量单位）：低频段 A710 0.420 < A715 0.473 < A510 0.537 < X3 1.017；高频段 A510 1.110 < A710 1.220 < A715 1.368 < X3 3.005。
→ **两个频段的排序都与 DT 口径一致**（低频 A710 最省、高频 A510 最省）；差别只在相对差距：big 相对变便宜（每 MHz 相对算力 2.13× → 2.20×）、prime 相对变贵（3.14× → 2.31×）。

（勘误 2026-09-28：本文件 2026-09-27 版曾写「真机口径下高频段 little↔big 排序翻转、big 反超」，用的是 ×(280/326、855/693、1024/1024) 的缩放。那是把 `cpu_capacity` 当成每 MHz 速率，漏了 1/f_max；三簇 f_max 不同（2016 / 2803.2 / 3187.2 MHz），漏掉 f_max 会系统性扭曲相对算力、prime 被高估最多，故高频段结论反了。已按上式更正，高频段仍以 A510 最省。）

## 6. [limits] 边界与注意

Cx 是每 CPU 的动态功耗系数（big 簇 4 个节点官方同写 447，本文按 A715 472 / A710 421 分列），
不是簇级系数；推理功耗 P = Cx × f × V² 只含动态部分，不含漏电/静态功耗，
也不含 DDR/L3/GPU 等 SoC 其他部分；后者只能看第 4 节的带宽票，或真机整机功耗。
实测参考列（Odin2）含漏电，但那是另一颗芯片的整轨口径，不能与推理列混用。
厂商内核（第 2 节核实）不解析 DPC、不注册 EM，本文件模型只存在于 mainline DT 口径，
ChiRi 运行时读不到。

簇内最优频率点现在可以直接读表：「每 Mdmips mW（推理）」列随频率单调上升，
即纯动态口径下同簇能效最优点在最低档（若计入漏电，最优点会略上移）。
跨簇放置决策看第 5 节与图③前沿。电压绝对值来自不同批次的 Odin2，批量套用前先与真机
`/sys/kernel/debug/energy_model/` 的实测 power 对一遍量级。

频率档位与真机 `scaling_available_frequencies` 一档不差；写 `scaling_max_freq` 记得 floor 对齐表内档位。

## 8. [sweetspot] 参考甜点
