# SM8850 频率 ↔ 功耗对照（qpt PMIC 逐轨实测 + SCMI 电压表）

> 索引：`[conclusion]` `[source]` `[caliber]` `[opp]` `[efi]` `[ratio]` `[limits]` `[check]` `[sweetspot]`

- **数据来源**：`/sys/class/powercap/qpt:*`（Qualcomm Power Telemetry）PMIC 逐轨实测，纯 CPU 轨（`qpt:0:0`=big / `qpt:0:1`=prime），不含整板/电池。主标定 57 点（v7/v8/v10/v11/v14 多批合并）+ 11-28 同会话复测 11 点 + 顶档三档冷态各 4 轮。
- **电压来源**：SM8850 SCMI 固件标称表（PDP0 28 档 / PDP1 29 档），`qcom-scmi-ro.ko` 输出 `physical_voltage_measured=0` → **是固件标称值，不是实测**。用 `P = coeff × f × V²` 反标定后与 qpt 实测拟合，big R²=0.9924 / prime R²=0.9964，形状可信。
- **定位**：校准参照，不是运行时输入（ChiRi 读不到 DT，配置以编译期嵌入的 `config/sm8850/soc.yaml` 为准）。本文件与 `soc.yaml` 受控块数值一致，后者由 `scripts/frontier_policy.py` 生成。
- **生成 2026-11-28**；同日完成：甜点复核（2496 → 2745.6）、指令数验证（EPSS 降压不缩水算力）、`cpu-cycles` 频率验证（4.2G 以上 TIS 不可信）、顶档冷态实测（4396.8/4512/4608）、SCMI 电压表交叉验证。

## 0. [conclusion] 结论先行

- **交叉点 2.736–2.738 GHz**（与极客湾 SPEC2026 的 2.742 差 <0.3%，两个独立来源互证）
- **甜点**：big **2745.6 MHz**（21/28 档，占峰值 75.7%）/ prime **3859.2 MHz**（21/29 档，占峰值 83.8%）
  - ⚠️ big 的 `2611→2745` 边际能效 **eff = 1.003（压线）**，是整条链最脆的一环——再有任何 1% 的数据修正就会掉回 2611
- **跨簇单核功耗比**（同频实测）：2112 → **2.443**、2227.2 → **2.419**、3398.4 → **1.804**，CV ≤2.8%
- **prime 顶三档不推荐使用**：热态（60°C）请求 4608 实际只得到 4339；冷态满血仅维持 1.15–1.25 秒
- **EEM 口径**：`energy_model` 只消费 `single_core_power_w`，簇内走 `cap_rel = f/f_max`（纯频率比）+ `pow_rel = (p−p₀)/(p_max−p₀)`；跨簇走 `cap_glob = capacity × f/f_max / 1024`、`pow_glob = p / 5.6249`

## 1. [source] 频率档位与来源核对

| 簇    | 核心            | 覆盖 CPU | policy  | 档位数 | 频率范围 kHz      | capacity |
| ----- | --------------- | -------- | ------- | -----: | ----------------- | -------: |
| big   | Oryon M ×6      | CPU0-5   | policy0 |     28 | 384000 – 3628800  |      762 |
| prime | Oryon L ×2      | CPU6-7   | policy6 |     29 | 768000 – 4608000  |     1024 |

**两簇布局，没有小核簇**：SM8850 是 6× Oryon M + 2× Oryon L，八核同为 64 位 Oryon。`topology.little` 是空区间、`frontier_policy.per_cluster` 无 `little` 键——**这是合法配置，不是缺失**（回归 `frontier_config_tests::sm8850_frontier_usable` 按两簇断言）。

**数据来源逐项**：

- **簇划分**：`soc.yaml [topology]`（DT cpu-map / 真机实测核心组）
- **频率档位**：sysfs `scaling_available_frequencies` 实测（big 28 档；prime 27 档 + `scaling_boost_frequencies` 2 档 = 29 档）——逐档写入 `soc.yaml [freq_khz]`
- **capacity**：sysfs `cpu_capacity` 实测（cpu0=762 / cpu6=1024）
- **EEM 落点必须等于真机档位**：EEM 返回的 kHz **不经 `find_floor_freq` 对齐**就直接写 `scaling_max_freq`（`src/chiri/cpu_load_governor.rs:715-728`），故本文件频率必须与 `soc.yaml [freq_khz]` 逐档一致——**已核对一致**
- **电压**：SCMI 表（见文首），逐档列在 §3

## 2. [caliber] 折算口径

1. **测量方法**：隔离测量（后台迁非测簇）+ idle/busy 差分 + 分档冷却；每点 3–10 轮取中位，剔除冻结/回绕/离群轮。**禁 doze + 飞行模式 + 关屏 + 每段重锁频**。
2. **`dp` 是单核增量**：`dp = busy − idle`（忙时簇功耗 − 空载簇功耗）。多跑满一个核增加的功耗。
3. **`single_core_power_w` 含静态项**：`= idle/核数 + dp`。顶档静态项占 1.7%，384 MHz 占 **6.5%**。运行期 `energy_model` **只消费这个字段**（`single_core_power()` 优先取 `single_core_power_w`，缺了才用 `power_w/核数`），所以 EM 的 p 与它**同口径、可直接比**；但**新测的 `dp`（纯增量）不能直接和它比**——差一个 `idle/核数`（2112 时 15.4 mW = 4.2%）。
4. **频率口径**（2026-11-28 确立）：内核显示满频、但辅助手段（`time_in_state` 驻留率 / IPC / 指令数 / `cpu-cycles`）发现实际已降频时，**只填「频率真满」的样本**。这些样本里能算平均就算平均，算不了就填峰值。
   - ⚠️ **`scaling_cur_freq` 会撒谎**：顶档推频后它会立刻报目标频率，但实测功耗 0.42–0.57 秒内纹丝不动（实际没切换）。**不能用它当频率判据**。
   - ⚠️ **`time_in_state` 在 4.2G 以上也会撒谎**：PMU `cpu-cycles` 实测显示 4608 目标档实际只有 4174 MHz（−9.4%），但 TIS 报 100%。
5. **算力口径**（两套，别混）：
   - 簇内：`cap_rel = f / f_max`（**纯频率比，不含 capacity**）
   - 跨簇：`cap_glob = capacity × f / f_max / CAP_REF`（CAP_REF = 1024）
   - 本文件 §3 的「算力」列用**跨簇口径**（`capacity × f/fmax`）
6. **单位**：`soc.yaml` 用 W，qpt 原始读数用 uW（÷1000）。`power_w` = 簇级，`single_core_power_w` = 单核级。
7. **`voltage_mv` 是标称值不是实测**：SCMI 表 `physical_voltage_measured=0`。**不据此反解 Cx**，只用于 §3 的展示与 `P=coeff·f·V²` 外推顶档。

## 4. [efi] 单核功耗与频率/算力的关系

**频率-功耗关系在簇内是超线性的**（电压随频率上升而上升，`P ∝ V²f`）：

| 簇 | 最低档 → 最高档 | 功耗倍数 | 频率倍数 | 超线性程度 |
|---|---|---:|---:|---|
| big | 384 → 3628.8 MHz | 19.9× | 9.45× | **2.1×** |
| prime | 768 → 4608 MHz | 20.3× | 6.0× | **3.4×** |

**prime 的超线性更陡**，因为它的电压从 544 mV 拉到 1044 mV（+92%），而 big 只从 488 拉到 928（+90%）——但 prime 的频率范围更窄，所以同样频率增幅下功耗涨得更凶。

**边际能效（Δ算力 / Δ功耗）在甜点前单调下降**：

| 段 | big eff | prime eff |
|---|---:|---:|
| 2496→2611 | 1.447 | — |
| 2611→2745 | **1.003** ← 甜点 | — |
| 2745→2899 | 0.675 | — |
| 3398→3648 | — | 1.216 |
| 3648→3763 | — | 1.157 |
| 3763→3859 | — | **1.021** ← 甜点 |
| 3859→3974 | — | 0.432 |

## 5. [ratio] 簇间换算

**跨簇单核功耗比 R = prime 单核功耗 ÷ big 单核功耗**（同频实测，11-27 晚至 11-28）：

| 频率 kHz | R（实测） | CV | 说明 |
| -------: | --------: | --: | ---- |
|  2112000 | **2.443** | 1.2% | 3 轮 × 60 样本，TIS 100% |
|  2227200 | **2.419** | 0.0% | 同上 |
|  3398400 | **1.804** | 2.8% | 同上 |

**趋势：高频时 R 下降 25%**（2.44 → 1.80）。这与 `soc.yaml` 的方向一致（2.395 / 2.543 / 1.923），但 soc 在 2112 以上**高估 R 约 5–6%**。

**历史「顶档 cost 比 2.50」已作废**——那个数是 prime 顶档被降频污染后的产物，不是真实同频比。

## 6. [limits] 边界与注意

- **prime 顶三档（4396.8 / 4512 / 4608）不推荐使用**：

  | 现象 | 数据 |
  |---|---|
  | 热态实际达不到 | 60°C 时请求 4608，PMU `cpu-cycles` 实测稳定在 **4339 MHz** |
  | 冷态满血只维持 1.15–1.25 秒 | 4608 满血 4.6057 GHz 仅存在于起速后 0.4–1.0 s；4512 较长（1.8–1.9 s） |
  | 电压跃升陡 | 968 → 1008 → 1044 mV，每档 +36~40 mV，而频率只 +2.5% |
  | 功耗非线性 | 4608 是 3859 的 **1.79 倍** |

  **这三个值怎么来的**：4396.8 / 4512 / 4608 都是 11-28 冷态实测（各 4 轮，50ms 频率窗口 + 2–5ms 功耗采样，CV ≤1.4%）。因为工具抓不到那 0.7 秒的满血期，同时用 SCMI 电压表 `P = 1053·f·V²` 交叉验证（偏差 −3.6% ~ +7.9%）。**功耗填高的目的**：让 EEM 自然避开这些档，而不是让它们看起来可用。

- **`scaling_cur_freq` 是不可靠的频率判据**（见 §2.4）：它会报满而实际未切换。
- **`time_in_state` 在 4.2G 以上不可信**：TIS 报 100% 时 PMU 实测只有 ~4.17 GHz。
- **`instructions` 不能分辨 4.2G 以上的频率**：4262→4339 频率差 2.5%，指令数只差 0.3%（IPC 补偿）。
- **绝对量级受 idle 基线漂移影响**：跨会话 idle 可漂移 30 mW；11-28 的复测已用同会话连测消除这个误差，但历史数据（v7/v8）仍有此问题。
- **温度敏感性**：+6 mW/°C（0.3%/°C），已用 C1 数据标定。
- **测量边界**（不影响配置可用性）：
  1. **qpt 绝对值未与电池对账**——EEM 只消费归一化形状 `(p−p₀)/(p_max−p₀)`，绝对刻度偏差被完全抵消，不影响甜点与跨簇落点
  2. **低频段（<2112）无跨簇同频实测**——883.2 是两簇唯一共享的低频档；该频段几乎不涉及单线程跨簇选核
  3. **1324800 单档偏高**——已用插值替代，前后两档（1228800 / 1440000）均正常

## 7. [check] 校验

**数据质量自检（11-28）**：

| 检查 | 方法 | 结果 |
|---|---|---|
| 频率真满 | `simpleperf cpu-cycles` 直接数时钟周期 | 3859 目标档实测 3838 MHz（−0.5%，准）；4608 档只有 4174（−9.4%，TIS 骗人） |
| EPSS 降压不缩水算力 | 同频 3 轮 `instructions` 计数 | CV < 1%（最高 3628 也稳定） |
| 跨簇比例稳定性 | 3 个同频点 × 60 样本 | CV ≤ 2.8% |
| 顶档冷态重复性 | 每档 4 轮 | 4396.8 CV 1.2% / 4512 CV 0.6% / 4608 CV 1.4% |
| 电压表形状 | `P=coeff·f·V²` 拟合 14 个实测点 | 偏差均值 +5.8%（中位 +7.2%，SD 3.5%） |
| 甜点一致性 | 峰值口径 vs 稳态口径 | big 都是 2745.6（不受口径影响）；prime 稳态口径下会变 4396.8，但那是数据倒挂假象 |

**交叉验证**：与极客湾 SPEC2026 反推的交叉点差 <0.3%（2.736 vs 2.742）；capacity 比值 0.727/0.683（极客湾）vs 0.744（本机 `cpu_capacity`）。

## 8. [sweetspot] 参考甜点

判据：`sweet_index` = 单核能效曲线最后一段满足 `Δcap_rel / Δpow_rel ≥ 1` 的档位下标（`src/chiri/energy_model.rs`）。

| 簇 | 甜点档 | 甜点 kHz | 占本簇峰值 | 边际能效 eff |
|---|---|---:|---:|---:|
| big | 21 / 28 | **2745600** | 75.7% | **1.003（压线）** |
| prime | 21 / 29 | **3859200** | 83.8% | **1.021** |

**⚠️ big 的甜点是整条链最脆的一环**：`2611→2745` 的 eff = 1.003，离判据线只差 0.3%。任何 1% 量级的 dp 修正都会让它掉回 2611。这个位置已经过 11-28 的实测复核（big 甜点区 8 档 + prime 3 档，同会话连测消除 idle 漂移），是目前能拿到的最准结论。

**真机若发现单线程性能不足**：先看 `eem_press_streak` 抗饥饿释放的触发率（触发 = 封顶确实压住了），再考虑引入 `sweet_bias` 档偏移，**不要直接改判据**（`agentsdocs/07-todos.md` 同口径）。

**改受控块后本文件必须同步重生成**，否则两处会漂移。
