## 4. 数据缺口

1. **`touch=1` vs `touch=0` 的功耗差无法产出**：`status.csv` 无 touch 列，两表无法按该维度对齐。只能给决策下限（1651200）。
2. **`touch=1` 行只在 big 簇**：little / prime 簇 touch=1 行数为 0，对比不覆盖这两个簇。
3. **`(85, 95)` 开区间内的 tick 行 = 0**：本包 `thermal_cap_pct` 只有 85 和 100 两个取值，「压制带内」样本为空，带内/带外的对照实际退化为 cap85 与 cap100 的对照。
4. **cap85 vs cap100 功耗差未做场景归一化**：窗口内的包构成与负载场景不同，−0.386 W 不能直接读作限幅带来的节省。
5. **devimp `batt_p` 与 status.csv 在 mobileqq 上不一致**（4.561 vs 4.473，n 299 vs 275），未追查原因；功耗结论请以 status.csv 为准。
6. **top 50 中有 3 秒无同秒 tick 匹配**（16:03:38、15:08:07、15:38:55，均为 bili / playback），该 3 秒的构成缺失；命中率 47/50。
7. **`fps` 列全时段非空行 = 0**：FAS 全程未接管，本包无帧率数据可用。
8. **批次 2（`x_0926-162818`）样本极小**（122 秒，mobileqq n=24 / kernelsu n=10 / bili n=87），且无 cap85 窗口，不参与横向对比。
9. **`daemon.log` 未被解析**：该文件为 fluent 本地化文本且存在编码问题，本文所有数字均来自 `main_*.log` 与 `status.csv`。
10. **`max_util` 双语义**：本文所有 util 数字取自 tick 行（CLG 语义 = 平滑前原始 util）。tuned（playback）行的 `max_util` 是平滑后决策负载，两者未混用。
