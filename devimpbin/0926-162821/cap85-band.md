# cap85 频段数据整理（`devimpbin/0926-162821`）

本文只做数据整理，不给结论。所有数字均来自 `devimpbin/0926-162821/` 下的
`x_0926-162614/status.csv`、`x_0926-162818/status.csv` 与
`x_devimp_0926-162614/main_*.log`、`x_devimp_0926-162818/main_*.log`（共 40 个 main 文件）。

统一口径说明（后文每个数字都按此执行）：

- `thermal_cap_pct`：status.csv 第 8 列（0 基列号）。
- `batt_power_w`：status.csv 第 17 列。功耗只用该列，不用 devimp 的 `batt_i`。
- tick 行 `cur_perf` = main 第 13 列，`max_util` = 第 10 列，`cur_freq_khz`（决策选频）= 第 15 列，
  `max_freq_khz`（scaling_max 上限）= 第 16 列，`thermal_cap_pct` = 第 21 列。
- snap 行 `cpu_cur_khz`（实际频率）= 第 36 列，格式 `policy0:频率;policy3:频率;policy7:频率`。
- 簇硬件上限：little = 2016000、big = 2803200、prime = 3187200 kHz。
- `max_util` 语义：CLG 行（`mode=default`）为**平滑前原始 util**；tuned 行（`mode=playback`）
  为平滑后决策负载。本文分桶统计只落在 `mode=default`（原因见第 4 节）。
- 逐秒配对：把 tick 行时间戳（含毫秒）截到整数秒，与**同秒** snap 行的 `cpu_cur_khz` 按簇配对；
  未配上的单独计数。

### 2.2 豁免带内（`cur_perf >= 0.95`）

- 豁免带内满足 `决策列(15) == 硬件上限` 的样本：**三个簇均为 0 条**（little 0/215、big 0/90、prime 0/92），
  故「豁免带 × 决策满档」的逐秒样本切片为空。
- 空的原因（列语义，必须分开看）：
  - 脚本的「满档」口径是**第 15 列 `cur_freq_khz`（决策选频）等于硬件上限**，该口径下窗口内确实全为 0
    （含全带参照：little 0/3918、big 0/3931、prime 0/2947）。
  - 满档现象体现在**第 16 列 `max_freq_khz`（scaling_max 上限）**：cap85 窗口内该列恒为硬件上限
    （little 2016000 / big 2803200 / prime 3187200），而第 15 列决策选频是变化的
    （样本见 1670400、1900800、1593600、1286400、1171200、1113600 等，并非恒为上限）。
  - 即：`决策选频(15)` 与 `scaling_max 上限(16)` 是两列不同语义，本文不合并统计。
- 带内 `max_util` 分桶与计数见 3.1；带内 28243 行的完整配对数据以 3.1 的分桶汇总呈现，不逐行罗列。

## 4. 数据缺口

1. **`max_freq_khz`(第 16 列) 满档的逐簇时长占比本轮未单独计算**。本文只确认了该列在 cap85 窗口内
   恒为硬件上限（样本层面），未按簇统计「该列 == 上限」的行数/占比。
2. **tick↔snap 同秒配对存在时点错位**：tick 行时间戳带毫秒，snap 为每秒一次，本文按整数秒匹配，
   同秒内两者不是同一时刻采样。样本中出现 `cap% > 100%` 的行（如 little dec=1113600 / actual=1555200
   -> 139.7%），即由此产生，配对口径有此局限。未配对行 69 条已单独计数，未纳入 cap% 统计。
3. **豁免带样本为空是列语义所致**，非数据缺失：`cur_perf` 在 `mode=playback` 行不落数值，
   而「决策满档」按第 15 列口径统计；满档证据在第 16 列（见 2.2）。两列不可混算。
4. **该包未采集的数据**：`mode=playback` 行的 `cur_perf`/`tgt_perf`（第 13/14 列）该包未采集（恒为 `-`），
   故 playback 行无法做豁免带判定；本文未用其它字段或其它包推断。
5. **显示层瑕疵**：生成 scratch（`tmp_cap85.txt`）时 Windows 代码页把「档」字写成了 `æ¡£`，
   仅影响 scratch 的显示，不影响任何数字（该 scratch 已在收尾时删除）。
