# ChiRi 调度改进方案（2026-10-11 归因合并定稿）——核查要点与可复用口径

> 来源：ChiRi 仓库内 AI 产出的计划类文档 `.cursor/plans/2026-10-11-调度改进方案.md`（715 行，定稿于 2026-10-11，从 `.cursor/docs/` 迁入）。本文件是该计划与其六路归因分析的结构化摘要，供后续会话快速接管；细节与逐条算式仍以仓库原文为准。

## 背景与目标

- 工作仓库：`/home/aibeto/code/ChiRi`（Android/SM8550 平台的 userspace sysfs 调频调度项目）。
- 目标：对 SM8550（board=kalama，model PHB110，ChiRi #3 Transition 相变 A02-04 / versionCode 30204，kernel 5.15.180）的调度侧省电空间做定量归因，并产出按「预期收益 × 回归风险」排序的改动清单。
- 数据输入：`devimpbin/1011-000909/`，8 批采集（1009-144818 ~ 1011-000901），`status.csv` 117994 行、44 列新 schema。
- 硬约束（用户派单时定的铁律）：**不做 A/B 对照实验**，只允许同版本同场景观察 / 离线重放 / 模型折算 / 构造性自检。

## 核心量化结论

- 整机能量盘子 **66.5 Wh**；其中 **硬地板**（调度层碰不到）= 屏幕本体 6.35 Wh + 息屏地板外围 4.38~8.14 Wh = **10.73~14.49 Wh（16.1%~21.8%）**。任何「降整机 X%」的承诺必须先扣掉这块。
- 调度侧现实可动：**1.6 ~ 5.0 Wh（2.5% ~ 7.6%），中枢 ≈3.3 Wh（5.0%）**；建议对外口径 **1.6 ~ 4.5 Wh（2.5% ~ 6.8%）**（上界截断，因 5.0 含 AMP 共线上界，不作承诺）。
- 合计口径必须是**逐项可加**（去重叠后仅 4 项）：亮屏 default 决策密度与尖峰削顶（P2/P3/P4 取 P2 区间为代表，不逐行相加）**0.93~2.88** + 息屏/scenemode **0.05~0.25** + daemon 自耗 **0.15~0.40** + playback/fas/akmode 三特调模式 **0.50~1.50**，即下界 `0.93+0.05+0.15+0.50=1.63`、上界 `2.88+0.25+0.40+1.50=5.03`。初版正文出现的底数「1.2 / 4.0」查无出处，属旧版残留，已删。
- 收益结构：约 57% 来自亮屏 default 的升频决策密度与尖峰削顶（P2），约 30% 来自三特调模式（P13），息屏路径仅占 3~5%，**不是主战场**。
- 去重叠依据：P2 与 P3 共享同一批秒数（窗口交集 C∩A=5260s、C∩D=5192s），P4 的 1851s 窗口完全落在 P2 并集窗口 17389s 内。

## 关键方法与裁决（可复用的分析手法）

- **DiD（双重差分）裁决**：t2（息屏路径）与 t3（scenemode 门槛）对同一现象给出冲突口径，用 `tmp_an200.py`（事件重建 + 息屏状态分层）、`tmp_an201.py`（进入/退出边界配对）、`tmp_an202.py`（段长×位置分层）、`tmp_an203.py`（DiD 判定）复算裁决，**采信 t3 的数字**。脚本须**从仓库根执行**（脚本内用仓库相对路径，在 `_tmp/` 里直接跑会得到空数据）。
- **按 mode 分化的系数**：原方案的 AMP=1.4833 是 **default 专属值**，不能套用其它模式；应按 mode 取（playback 0.792 / fas 0.417 / akmode 1.020），上界才用 1.0。GPU 偏系数 W/% 同样按 mode 分化（default 0.0878 / playback 0.0728 / akmode 0.0452 / fas 0.0193 且 R²=0.015 无意义）。
- **热点定位纠偏**：akmode 的 `cpu_dyn` 仅 0.721Wh（27.1%），CPU 侧现实可削 10~20% → 0.07~0.14Wh，且其 `tuned_profiles.yaml` 已配 `headroom=1.15 / perf_ceil=1.0`（天花板本就拉满）。结论：**akmode 的省电战场在 GPU，不在 CPU 调度**，CPU 侧只值 headroom 微调，主要交付物是「触档延后」而非电量。
- **能量账口径**：权威过滤为 `status.csv` 中 `charge=discharging` ∧ `0<batt_power_w<=20`；热态打折按亮屏 −0~10%、中枢 −4%、息屏 −0%。

## 跨环境借鉴的三条硬结论（2026-10-11 补充）

1. **天花板类改动已被全仓否决**：搜遍 `perf_ceil`/`headroom`，真天花板只剩 `module/config/normal/scenemode.yaml:15` 的 `0.12`（即 R2「天花板全拆」已落地）⇒ 改 tuned `headroom` 到 1.10/0.97（P9/P10）属于**直接回退 R2**，本轮不建议；P13 若走 `headroom`/`perf_ceil` 同样撞墙，只能走 R7 的「取点 / 到达速度 / 降权(uclamp)」三条。
2. **`agentsdocs/07-todos.md:53` 明写「不要往调阈值方向改」**，且「降后 N tick 禁止再抬」已被 2026-10-04 裁决否决 ⇒ P2/P4 正面落在这条边界上，置信度封在「中 / 中高」，采纳前必须先离线重放确认 up:down 朝收敛方向变化。
3. **新增 CR.1（CLG 反复重建）**：`src/.../cpu_load_governor.rs:1179/1257` 每次重建 `ClusterState`、清零 `up_wait`/`down_wait`/`steady_decay`；1011 包实测重建 710 次 vs 1009 包 722 次（**跨版本未改善**）。收益仅 0~0.02 Wh ⇒ 标为**可靠性项，不是电量项**，未并入合计。
