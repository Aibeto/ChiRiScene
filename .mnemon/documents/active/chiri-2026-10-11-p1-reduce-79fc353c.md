## P1 终版：取消二段式息屏（用户明确目标「息屏只有一个档」）

- **方法（用户裁定）**：doze 与 CLG 本是同一套算法、doze 只是换参数 ⇒ 取消二段式 = **删掉那 4 行息屏专用覆盖**（`perf_ceil .min(0.30)` / `perf_floor 0.0` / `smoothing_up 0.10` / `touch_boost false`），**基座仍取 `reduce`，不是换 default**（换基座会连带改 7 个无关字段）。息屏后 CLG = reduce 参数原样（`up_threshold 0.90` / `perf_ceil 1.00` / `perf_floor 0.05` / `smoothing_up 0.50` / `touch_boost true`）。
- **教训（用户反馈1推得）**：改参数叠加式设计的取消方式是「删叠加」，不是「换底层」。
- 连带 8 处：`src/chiri/mod.rs:3716-3733` 删 doze_cfg 构造（同款覆盖出现在 `:3326`/`:3728`/`:4226` 三组共 12 行）；`:3321-3329` FAS 失效分支、`:4222-4233` scenemode 关闭分支同口径删除；`:4359-4381` 饱和退出**保持现状**（退回 reduce，落地后与窗口态天然一致）；`src/chiri/config.rs:1808-1810` 缺省已是 3000（7e14783 改的），五机型 `module/config/{8550,8650,8475,8998,zumapro}/feature.yaml` `scene_mode_delay_secs: 300→3000`（缺省意图从未生效）；i18n `zh.ftl:109/110/111` 与 `en.ftl:109/110/111` 文案随语义改（key 保留）。回退 = 恢复 doze 段构造 + YAML 改回 300。
- **FAS 澄清**：FAS 活跃息屏走「保持接管」（`mod.rs:3714`）进不到 doze，本项只影响 FAS 失效路径；不涉及后台保留期省电。
- **代价 0.09~1.17 Wh（中枢 0.59）**：窗口 = 每次息屏 [0, min(段长,3000))，185 次息屏中 119 段长 <3000 s 永不进 scenemode；作用面仅 default 模式 13469 s / 2.6791 Wh / avgW 0.716。上界按 t2 ΔW 0.314 W，中枢按窗口内「有 0.30 上限(13193s, 0.713W) vs 无上限(276s, 0.871W)」直接观测，下界 DiD 折算。关键参照：窗口内「天花板咬住」组 avgW 0.702 ≈ 未咬住组 0.729 ⇒ 功耗主要由负载而非该天花板决定；咬住且上限 ≤0.32 的 6272 s 里 cpu_dyn 仅占整机 22.6%。

## 数字修正（二轮 GLM 5.3 Flash 审查抓到）

- **P2 对外区间 = 1.38 ~ 2.77 Wh**（10%~20% 两档、两端均含 AMP 1.4833 × 热态 4% 折扣；下界 = 9.71×10%×1.4833×0.96 = 1.38）。旧 0.93 是漏乘 AMP 的 `0.97×0.96` 残留；初版 2.88 上界未打折。两轮审查抓的是同一类错：**改数字必须从基数重跑完整算式，不能拿旧数字拼新句**。
- **三档净额（P1 代价 + P2 + P4）**：保守 **+0.36 Wh（+0.5%）** / 中枢 **+1.59 Wh（+2.4%）** / 乐观 **+3.08 Wh（+4.6%）**。旧「最保守净额转负（−0.09）」结论翻正，P1 功耗上接近零和，其首要价值是设计目标「息屏只有一个档」。

## 硬约束（2026-10-11 用户重申）

**任何模式下都必须保留「随时可到硬件最高频」的能力**。已核实 reduce 段无阻碍：`perf_ceil 1.00`、`headroom_factor 1.05`（放大非封顶）、`up_rate_limit 2`（只延迟）、`steady_decay_target_ratio 0.80`（下探取点非上限）。全仓 perf_ceil<1.0 真天花板只剩 `module/config/normal/scenemode.yaml:15` 的 0.12。
