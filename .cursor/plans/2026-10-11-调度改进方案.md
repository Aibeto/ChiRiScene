**方法**：以 `daemon.log` 的 `息屏触发事件` / `亮屏触发事件` 为权威息屏段边界（**不能用 `status.csv` 的 `screen_on` 连续行 —— CPU 睡眠时不落行，会把同一段切成多次**）；只统计 `charge=discharging` 且 `0<batt_power_w<=20`；生效上限由 `type=tick` 行在 `max_util≥0.95` 时的 `tgt_perf` 前向填充得到（覆盖率 100%）。脚本 `devimpbin/_tmp/tmp_dz9.py` / `tmp_dz10.py` / `tmp_dz11.py`。

#### P1.6 收益（非电量）与风险

- **非电量收益**：① 灭屏后**不再立即干涉**后台 sync / JobScheduler（0.30 的注释原文就是「突发时允许短暂借力」，本项把借力窗口从 0 扩到 3000 s）；② 息屏**只剩一个档**，那 4 行息屏专用覆盖（3 组共 12 行）整体消失；③ **消除非 scenemode 的息屏天花板**（0.30），**保留「随时可到硬件最高频」**，与硬口径 **R2** 一致；④ **CLG 重建应减少**（每次灭屏少一次构造 + `init_policies`）。
- **风险（中）**：① **窗口内功耗上升是确定的**（0.09~1.17 Wh）；② **窗口从 9904 s 扩到 13469 s**（delay 300→3000 的连带效应）；③ **119/185 次息屏永远不进 scenemode** —— 实机若抖动更频繁覆盖率可能更低，须复核；④ 本包无「窗口内无天花板运行」的对照口径，代价值是**结构化外推**。
- **已澄清、不算风险的两条**：
  - **FAS 息屏路径**：FAS 活跃时息屏走「保持接管」分支（`src/chiri/mod.rs:3714`），**本来就进不到 doze**；本节改动只影响 FAS **失效**后的那条（`:3320-3330`）。而且**息屏时捕不到帧，与「FAS 应用在后台」是同一种情况，算法本身一样**，不构成额外代价。
  - **饱和退出**：第 5 条保持退回 `reduce` 不变；第 1 条落地后窗口内也是 `reduce` 参数 ⇒ **两者天然一致**，不存在「退出后反而比窗口内更省」的错位（那是旧方案改走 `default` 才会有的问题）。
- **验证**：① 灭屏后不再出现 `perf_ceil≤0.32` 段（取 `max_util≥0.95` 的 tick，`tgt_perf` 应直接等于 `reduce` 的生效上限 1.00）；② `scheduler-doze-enable` / `scheduler-doze-restore` 文案**不再含 doze 语义**（key 仍在，打点仍会打）；③ `scene_enter` 次数按 3000 s 门槛应有的量级（本包按段长 ≥3000 s 推算约 **66 次**）；④ `[CLG] P\d 初始化` 行数应下降（现 2130 行 ⇒ 710 次重建）；⑤ 上线后同版本观察息屏前 3000 s 的 avgW 与 >1W 率方向（**不取差值判据**）。

## 5. 不做的事 / 证据不足

### 5.1 明确不做

| 项 | 理由 |
|---|---|
| **任何 A/B 对照实验** | 项目铁律 |
| **调 GPU**（读 `gpu_busy` 反过来压 CPU） | 越过 CPU 调频边界；且 GPU 归因区间宽（8.80 vs 11.28 Wh）、CPU/GPU 负载共线，收益归属不可分离 |
| **削特调模式性能**（playback / fas / akmode） | 会让游戏/视频帧率承压；且 R2 的天花板禁令使唯一手段（`headroom` / `perf_ceil`）作废，fps 遥测又不可用、风险无法量化 |
| **在 scenemode 的 0.12 之上再压**（如 0.08） | 0.12 相对 0.30 的边际已接近噪声（DiD = +0.0461 W）；再压会伤息屏后台任务，且本包无时延数据 |
| 单改 `down_fast_threshold`（只挑 P3 的一条参数） | 与稳态下探共用判定，须与 `down_rate_limit_ticks` / `steady_decay_target_ratio` 联合评估 |
| 单独调 `SCENEMODE_SAT_UTIL`（0.85/0.95/1.00） | 进入与退出共用常量，实测总驻留反降 28%（15298 s）。**P1 不改变这条**：P1 改的是**进入延迟**（`scene_mode_delay_secs`），不改变 `SCENEMODE_SAT_UTIL` 常量本身，也不改 `SCENEMODE_SAT_SECS` 与 `SCENEMODE_COOLDOWN` 的长度 |
| 动屏幕 6.35 Wh / 靠「压更狠」省电 | 前者是真空硬地板；后者：压制本身只花 1.43 Wh/39.8 h，压更狠只会掉帧而不会少触档（cap=60 段均 5.33 W **高于** cap=100 段 2.32 W） |
| 停写频 / 加长决策周期 | 实测 CLG 写频仅 **0.678 次/s**，而 status 的 `freq_trans` 2152/s 来自内核 tracepoint（schedutil 自调频），相差 ~3200×。消不掉，消掉也不省电 |
| 改 `Sched.params` / 调大 `devimp_aff_secs` / 降采样质量 | 前者计数与功率无因果（>1W 秒 migrations 1550/s **低于** ≤1W 秒 1776/s）；后两项是既有铁律 |
| 关 `clamp_heavy` / 收紧 `hysteresis_c` / 单独动 `batt_mid_temp_c` | 被钳样本 61~70% 落在 (0.95,1.0] 旧豁免带；38-40 ℃ 滞后带钉死率 12.6% **高于** 40-41(8.6%)，收紧无收益；43→44 会让 normalize 静默把硬档回滞降到 1.0 |

### 5.2 已知证据不足（不藏）

1. **P1 的代价是结构化外推不是实测**：本包**没有**「窗口内长期无 0.30 上限」的对照段；中枢口径的对照组只有 276 s，上界口径借用了「0.30 vs 0.12」的单价。
2. **无时延/流畅度数据**：息屏后台同步/推送时延**本包无法验证**；P1 恰好把借力窗口从 0 扩到 3000 s，实机必须复核。
3. **`fps` 列不可用**：117994 行中非空仅 2854 行且集中在两个批次；t1 亮屏 default 的 fps 全 0。
4. **线程级归因样本小**：aff.txt 的 `t` 行是字段级差分，full=1 帧仅 27/182。
5. **离线 tick 行数是下界**：`logger.rs:1477-1553` 的 tick 去重签名不含 `max_util`/`cur_perf`。
6. **`status.csv` 时间戳含假值**：某批给 00:00:00→23:59:59 跨全天，逐批跨度合计 42.68 h（含重复）⇒ **不可作墙钟分母**。
7. **`cpu_dyn_w` 是下界**：只含动态项、电压借自另一批次；负 resid 占 4.24% ⇒ 「CPU 动态只占 31%」是上界性质描述。
8. **屏幕 0.474 W 是差值估计**：±30% 不确定度（≈±1.9 Wh）。
9. **GPU 归因区间宽**：偏系数 8.80 Wh vs 分桶上界 11.28 Wh 差 2.5 Wh，分桶含共线；且 `gpu_busy%` 是占用率不是功率占比。
10. **modem 无法分离**；**息屏地板外围是混合地板**（区间 4.38~8.14 Wh）。
11. **`thermal_cap_pct` 是 perf 索引不是 hw 频率百分比**：0.85 档实为 little 1670400 / big 2457600 / prime 2726400；且 **cap=85 ≠ 已压制**（仅 6.6~13.2% 的秒真被咬住）。
12. **`@A` 失败帧计数是「帧次」不是「唯一次」**。总失败率 3.28%（e3/ESRCH 8596 属正常）。
13. **8 次 daemon 重启全部由 128MB 归档预算触发**，无崩溃；**cap 序列不可跨批次连读**。
14. **package 列语义**：息屏期是「息屏前最后前台」残值（launcher 占 51.7% 不代表 launcher 在跑）。
15. **息屏采样稀疏**：本包息屏 status 行 33184 行（9.22 h）而权威息屏墙钟更长，**CPU 睡眠时不落行**；所有息屏 Wh 都是 sample-equivalent，且**息屏段边界只能用 daemon 事件**。
16. **P1 的 delay=3000 使 119/185 次息屏永不进 scenemode**：这是本包抖动程度的产物，实机若抖动更频繁覆盖率会更低。
