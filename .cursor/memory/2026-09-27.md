## 审查修复三项（用户 review，2026-09-27）

### [1] `normalize` panic 修复（`src/chiri/config.rs`）—— 真 bug，已修
- 症状：`thermal_clamp_warn` 内 `v.clamp(lo, hi)` 在 `lo > hi` 时 **panic**。两处调用点传
  `lo = soft + 0.5` / `hi = hard - 0.5`，故 `hard - soft ∈ (0, 1)`（如 batt 44.9/45.0、cpu 94.9/95.0）
  即 `clamp(45.4, 44.5)`。原兜底判据是 `hard <= soft`（`hard = (soft + 4.0).min(65.0)`），
  差在 (0,1) 的开区间不兜底 → `Config::load` panic → 守护进程崩 → watchdog 重启 → 崩溃循环。
  yaml 是用户可改的，故这是**可达**故障而非理论。
- 修法（最小）：电池 + CPU 两侧兜底判据都改 `if hard < soft + 1.0`（电池仍 `+4.0.min(65.0)`，
  CPU 仍 `+10.0.min(100.0)`）；`thermal_clamp_warn` 再加一道 `hi < lo ⇒ hi = lo` 的兜底（合法区间下
  结果与直接 clamp 完全相同，行为零变化），并修正 `normalize` doc 与 line 1036/1049 那条
  「已保证硬限 >= 软限 + 4」的假注释（实为 `+1.0`，且原来根本不是这个判据）。CPU 侧确实同样有问题，已同改。
- 全调用点复核（`soft/mid/hard_perf_cap`、`free_above`、`tuned_thermal_floor`）：
  `0 <= hard_cap <= mid_cap <= soft_cap <= 1.0`、`tuned_floor >= hard_cap` 都在 clamp 前建立，
  `lo <= hi` 成立；mid 两处由新的 `>= soft+1.0` 保证。`tuned_thermal_floor` 的 `(hard_cap, 1.0)`
  在 `hard_cap` 已被前序钳进 `[0,1]` 后恒合法。
- **无测试模块**：`src/chiri/config.rs` 不含 `#[cfg(test)] mod tests`（全文件 grep 无 `#[test]`），
  按任务约束不新造测试框架，此处仅报告。
- 自证：`cargo check -p chiri --target aarch64-linux-android` → 见 `Checking chiri`、exit 0、0 warning。

### [3] `cpu_load_governor.rs` up-hold 与 `down_wait`（确认，未改行为）
- 判定：**off-by-a-tick 真实存在且可达**。「`down_wait` 已到 `down_rate_limit_ticks - 1` → 一次
  up-hold（残留不清）→ 一次真 down」会在第 N 个 down intent（而非第 N 个连续 down tick）写出降频，
  即比连续 N tick 早 1 tick。up-hold 分支本身既不累加 `up_wait` 也不清 `down_wait`（符合任务描述）。
- 原注释（~418 行）已写明「不累计 up_wait、**不清 down_wait**」的意图，但未点明这条 off-by-a-tick 后果。
  本次以 `[dir_stabilize_tick]` 标记扩写：说清 1-tick 提前、收益（噪声 tick 不抹降频进度）、
  up-hold 的「有频差方向」性质，以及生产 `down_rate_limit_ticks ∈ 1..10` 时该路径非空。
- 建议：**保持现状**。改成「up-hold 视为同向未推进」= 在 up-hold 里 `down_wait = 0`，
  代价是方向翻转更频繁（正是 P1-2 这轮修的东西），收益仅 1 tick 的降频延迟，不划算。
