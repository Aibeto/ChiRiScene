# git commit 确认闸门

2026-09-25 事故：用户说「为暂存的更改生成commit」，助手理解为「执行提交」直接 `git commit`，实际意图是「生成提交信息供确认」。提交是需要用户授权的动作，执行前必须确认。

## 硬规则

1. 「生成commit」「生成提交信息」这类表述**默认只出草稿**：给出信息、停在那里，不运行 `git commit`。
2. 只有用户对信息明确点头（「提交」「commit it」或对草稿的直接认可）才执行。
3. 用户没让提交时擅自提交 = 严重错误；即使事后 `git reset --soft HEAD~1` 可无损回退（改动原样回暂存区、工作区不动），也不能作为先斩后奏的依据。
4. 暂存区内容、提交拆分方式、是否包含未跟踪文件，同样属于用户决策，不代做。

## 流程

1. `git diff --staged`（无暂存则 `git diff`）+ `git status --porcelain` 分析改动。
2. 按约定式提交给出 type/scope/信息草稿（中文，与仓库历史风格一致），展示给用户。
3. 停下等确认。用户认可后才执行 `git commit`。

## 正反例

```text
[BAD] 用户：「为暂存的更改生成commit」→ 直接 git commit -m "..."，事后才解释
[GOOD] 用户：「为暂存的更改生成commit」→ 分析 diff、给出信息草稿、询问是否提交
```
