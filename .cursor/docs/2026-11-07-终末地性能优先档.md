# 终末地性能优先档（\`[perf_lock]\`）

> 日期：2026-11-07　｜　用户指令：为终末地（\`com.hypergryph.endfield\`）提供性能增强，忽略功耗开销，以「绝对流畅、绝对不卡不掉帧、尤其没有小卡顿」为主要目标。
> 结论：新增 FAS 单一开关 \`perf_lock\`（缺省关闭），在唯一写频下游 \`apply_freqs\` 强制满性能；终末地配置开启并收成单档 60fps。代码 9 文件、单测 4 条、离线契约 4 条，全部通过。

## 1. 先证明「只改配置不行」

FAS 的 perf 值（\`perf_index\`，0..1，越大越接近最高频）在运行期被十余条路径反复下调。配置面能抬高的是地板 \`perf_floor\`，但：

\`\`\`
src/scheduler/fas/controller.rs:304-310
let base = self.cfg.perf_floor;
let fps_bonus = ((self.current_target_fps - 60.0).max(0.0) * 0.004).min(0.25);
(base + fps_bonus).min(0.45)
\`\`\`

那个 \`.min(0.45)\` 是硬顶。\`perf_floor: 1.0\` 也只能得到 0.45，于是 PID 衰减、稳态衰减、post-jank 地板最后都夹回 0.45 附近。也就是说：**只要走配置，就锁不住频**。

如果逐条改这些路径（把 PID 增益归零、把 \`steady_decay_frame_threshold\` 调到天文数字、把 \`loading_perf_floor/ceiling\` 抬到 1.0、把 \`jank_cooldown_frames\` 设 0……）也能凑出类似效果，但要动六七个模块、彼此还有交叉约束（\`normalize()\` 会把 \`perf_init/perf_cold_boot/post_loading_perf/damped_perf_cap/app_switch_resume_perf\` 全部夹进 \`[perf_floor, perf_ceil]\`），任何一处漏掉就会在某个场景（加载、切后台回来、开环）掉一次频，而**「偶发掉一次频」正是微卡顿**。这类「靠参数巧合成立」的配置不是契约，下一个人改一个数就破了。

## 2. 设计：一个开关，一个收敛点

关键观察：FAS 所有下调最终都只是改 \`perf_index\` 这个内部变量，而**写频率只发生在一个函数**里 —— \`policy_mgmt.rs::apply_freqs\`。那么只要在这个函数里、在算出最终 \`effective_perf\` 之后强制拉满，所有上游路径都被一次性旁路，一条不用改。

\`\`\`
src/scheduler/fas/policy_mgmt.rs::apply_freqs
let locked = self.cfg.perf_lock;
let load_only = !locked && self.uses_load_control();   // 开环下探与锁频互斥
...
// util 软封顶块之后
if locked { self.perf_index = ceiling; effective_perf = ceiling; }
// thermal_cap 压顶之前
if let Some(cap) = thermal_cap { ... }
\`\`\`

三处顺序细节都是硬约束：

1. **必须在 util 软封顶之后**。软封顶用 200ms 滞后的 \`ema_fg_util\` 把 \`effective_perf\` 混向 \`[0.40,1.0]\`，是锁频最主要的对手；写在它前面会被立刻改掉。
2. **必须在 \`thermal_cap\` 之前**。内核/本模块的热降频是保护，用户要的是「不掉帧」，但烧机器不是选项；锁频只锁到本模块算出的上限，热钳制仍然压顶。
3. **\`load_only\` 要一起短路**。开环（帧源静默）时原逻辑把 perf 设为 \`max(core_utils)\`，可能远低于上限；锁频档下这等于自己制造锯齿，所以 \`load_only = !locked && uses_load_control()\`。

配套两处「不改也不掉频、但要改」的地方：\`adjust_target_for_util\`（util 长期 ≤0.55 时把目标帧率每秒降 0.1、最多降 3）与 \`apply_steady_decay\`（连续正常帧就按 0.004~0.022 的步长往下削）。它们在锁频档下不会影响写频，但会让内部状态漂移 —— 日志里 \`P:\` 显示 1.00 而 target 已经变成 57fps，判读会误以为掉帧。所以两处都在函数开头 \`if self.cfg.perf_lock { return; }\`。

## 4. 终末地配置与「单档」的必要性

\`\`\`yaml
fas_rules:
  perf_lock: true
  fps_gears: [60.0]
  fps_margin: 3.0
  per_app_profiles:
    com.hypergryph.endfield:
      target_fps: [60]
      fps_margin: 3.0
  core_temp_threshold: 0.0
\`\`\`

单档不是随手写的。\`evaluate_gear\` 的升档整段包在 \`if let Some(next) = self.next_gear()\` 里、降档整段包在 \`if let Some(prev) = self.prev_gear()\` 里；\`fps_gears\` 只有一个元素时 \`next_gear/prev_gear\` 恒返回 \`None\`，齿轮机整段不执行。这掐掉两条实测过的掉频来源（均来自 1107 包 sgame 的 FAS 现场）：

- **降档加速**：\`gear_state.rs:325\` 的 \`self.perf_index = (self.perf_index + boost_inc).min(0.90);\` —— 打的是「加速」，实际是把 perf 硬压到 0.90 并维持 \`downgrade_boost_duration\` 帧。1107 包出现 30 次。
- **原生档翻面**：\`detect_native_gear\` 判到 60fps 就降档，1 秒后又升回 120（sgame 实测「60 → 120」即时翻面）。齿轮机在锁频档下毫无意义，只有噪音。

注意 \`perf_lock\` 本身并不依赖单档：它把频率钉死，齿轮机即使触发也改不动频。单档的作用是**消掉状态机抖动带来的判读噪声与日志噪声**，以及避免降档加速把 \`perf_index\` 拉到 0.90 后又被强制拉回、在 \`current_freq\` 上留一次多余的 min→max 写。

## 5. 验证

\`\`\`
cargo fmt --all                                  → 干净
YUMI_SKIP_EBPF=1 cargo check -p chiri            → exit 0（13 条既有 dead-code 告警，与基线一致）
cargo test -p chiri --bin chiri -- perf_lock     → 4 passed / 0 failed
rustc --edition=2024 --test scripts/tests/fas_perf_tier_regression.rs → 4 passed
cargo test -p chiri --bin chiri                  → 278 passed / 3 failed / 1 ignored
\`\`\`

三条失败仍是 \`chiri::fas_manager::tests::{activate_same_pid_unknown_starttime_is_new_session_fail_closed, repeated_activate_same_pid_keeps_frame_session, same_package_pid_replacement_advances_generation}\`，依赖编译期嵌入的 \`fas.yaml\` 与真机 sysfs，HEAD 即失败，与本轮无关。

四条单测的断言口径值得记一下，它们是「锁频」的定义：

1. \`perf_lock_keeps_max_freq_under_util_cap_and_jank\`：人为把 \`perf_index\` 压到 0.30、挂 30 帧 jank 冷却、util 只给 0.10（三个下调条件同时满足）→ 断言 \`perf_index == 1.0\` 且 \`current_freq == 500\`（测试策略的 \`freq_max\`）。
2. \`perf_lock_bypasses_load_only_demand\`：帧源静默（开环）时不得按 util 下探。
3. \`perf_lock_freezes_target_fps_offset\`：util 长期低不得改目标帧率。
4. \`perf_lock_skips_steady_decay\`：连续正常帧不得削 perf。

第 1 条是核心：三个下调入口同时开火，写频仍是顶格。以后谁改 FAS 的降频逻辑，只要这条还过，锁频档就不会被悄悄破掉。

\`fas_perf_tier_regression.rs\` 是源码文本契约，防的是「配置被改回去」和「顺序被调乱」：\`endfield_runs_performance_first_tier\`（yaml 里 \`perf_lock\` 为真、\`fps_gears\` 单档）、\`perf_lock_defaults_off\`（\`fas_types.rs\` 缺省为 false）、\`lock_applies_before_thermal_cap\`（锁频语句的下标 < \`thermal_cap\` 的下标）、\`load_only_is_bypassed_under_lock\`。

## 6. 与既有契约的关系

- **热切换的 \`perf_init\` 重放**：不冲突。那条契约解决的是「接管间隙 \`current_perf\` 掉到 0 后从地板缓慢爬升」；锁频档下接管瞬间就写顶格，比任何种子都高。
- **\`effective_perf_floor()\` 的 0.45 硬顶**：没动。\`perf_lock\` 绕过它（写频只认 \`perf_ceil\`），改它会影响所有非锁频档的地板语义，属另一件事。将来若要做「半锁」（floor 0.8 保底、允许 PID 微调），才需要把它改成可配字段并同步 \`normalize()\` 的交叉约束段。
- **热**：\`core_temp_threshold: 0.0\` 保留（FAS 侧不降频），热量交内核 thermal；\`apply_freqs\` 里锁频写在 \`thermal_cap\` 之前，本模块若将来重开护栏也能压顶。内核侧若把 \`scaling_max_freq\` 压到目标以下，\`verify_prev_freq\` 会识别为 QoS 钳制：只按 300s 窗口告警、不重写（避免和 thermal 打架）。
- **GPU**：FAS 完全不碰 GPU（\`src/chiri/gpu.rs\` 的 \`GpuGuard\` 只服务 lab 的 contingency/babel）。本轮不锁 GPU，理由见下。

## 7. 未做项与理由

**GPU 锁频**。没有证据表明终末地是 GPU bound（全仓没有 \`com.hypergryph.endfield\` 本体的 devimp 日志，只有 \`arknights\`/skland），而风险是实的：8550 上读 GPU 节点会把 GPU 拉起（实测 +47% 功耗），锁最高频会显著抬 SoC 温度，反而可能诱发内核 thermal 去压 CPU。开锁判据写进 TODO：真机日志里 \`gpu_busy\` 长期 ≥95%、且 CPU 已在最高频仍掉帧。

**套用到 sgame / lolm / speedmobile**。1107 包证明 sgame 的三条掉频来源（开环锯齿 58 次、降档加速 30 次、原生档 60↔120 翻面）都会被 \`perf_lock\` 一并解决，但电竞是长时高负载场景，「忽略功耗」的代价比单机游戏大，需用户裁决。套用方式只是在该应用 yaml 加一行 \`perf_lock: true\`（\`fps_gears\` 是否收单档按机型刷新率定）。

## 8. 真机复核判据

拿到下一份含终末地的日志后，按顺序看这五条：

1. \`daemon.log\` 出现 \`fas-perf-lock\` —— 配置被读到。
2. \`fas-tick-log\`（每 30 帧一条）的 \`P:\` 全程 1.00，\`snap\` 行三簇 \`cur_freq_khz == max_freq_khz\` 的比例 >99%。
3. \`fas-gear-switch\` / \`fas-downgrade-boost\` / \`fas-native-gear-detected\` 零条 —— 齿轮机确实被单档关掉。
4. \`fas-loop-open\`（帧源静默）期间的 tick 行频率不掉 —— 这是本档最直接的收益，原逻辑此时按 \`max(core_utils)\` 下探。
5. \`qos_clamped\` 告警：若内核 thermal 持续把上限压到目标以下，说明这台机器压不住满频，需要回退（把 \`core_temp_threshold\` 恢复成 40 之类，让 FAS 自己先降）。

## 9. 跨平台影响面

\`perf_lock\` 落在 \`config/normal\` 与 \`src/scheduler/fas\` 两层，都不绑 SoC：\`fas_types.rs\` 的字段、\`policy_mgmt.rs\` 的收敛点、i18n 键位对所有机型同一份代码。任何 SoC 只要配了 \`fas.yaml\` 白名单 + 应用 yaml，加一行 \`perf_lock: true\` 就能得到同一语义。速度表差异由 \`PolicyController::find_nearest_freq\` 吸收（\`ratio=1.0\` 时取该簇硬件最高档），不需要为不同平台各写一份。
