## 1. EEM 功耗模型审计（任务 ③）

### 1.1 先证伪「EEM 抬高频率」

`src/chiri/cpu_load_governor.rs:774-787` 的 flush：

```
ratio_freq = cluster.find_floor_freq(write_perf)      // 比例路径
eem_target = eem_target_freq(core_utils)              // EEM 路径（触摸窗口内直接 None）
target_freq = ratio_freq.min(eem_target)
```

EEM 的输出只作为**上限的下界约束**参与 `min`。它不可能把频率抬到比例路径之上，
所以「EEM 让功耗变高」不可能是通过「抬高频率」发生的。真正的两条机制性缺陷在下面。

### 1.2 缺陷一：k 取 `ceil(Σutil)`，和注释的物理口径相反（P0）

`eem_target_freq` 里 `k` 是「用几颗核去承接这份需求」：

- 需求：`demand = max(Σ_i util_i×cap_i, busiest×k)`（`energy_model.rs:349-355`）
- 供给：`supply(f,k) = cap(f)×k`（`energy_model.rs:82`）
- 够用判据：`cap(f) ≥ max(Σ/k, busiest)`

取 **k = 忙核数 m** 时，`Σ/m` = 均载 ≤ busiest，Σ 项自动失效，判据收敛成
**`cap(f) ≥ busiest`** —— 这正是「整簇共享一个频率域，每颗核拿到的频率都得够自己用」的物理判据，
也与比例路径用 max_util 作基准同源。

旧实现是 `k = (occupied.ceil() as usize).max(1)`（`occupied = Σ clamp(util)`）。
当 m > ceil(Σ) 时它把均载放大 m/ceil(Σ) 倍，**均匀轻载被当成重载**：

| 场景（big 簇 6 核） | Σ | 旧 k | 旧判据 | 新 k | 新判据 |
|---|---|---|---|---|---|
| 2 核各 50% | 1.00 | 1 | cap ≥ 1.00（顶档） | 2 | cap ≥ 0.50（中档） |
| 6 核各 16.7% | 1.00 | 1 | cap ≥ 1.00（顶档） | 6 | cap ≥ 0.167（低档） |
| 1 核 85% + 3 核 10% | 1.15 | 2 | cap ≥ 0.575 | 4 | cap ≥ 0.85（busiest 接管） |

右两列就是「EEM 明明开着、甜点封顶却形同虚设」的机制：`gear_for_demand` 被喂进一个
虚高的需求，选出的档位越过甜点，`capped=false`，`eem_cap_suspended` 也不会挂起——
表面看 EEM 在工作（日志里 eem 段有目标），实际下发的是顶档。

> 注：源码 :946-947 的注释本来就写着「供给按**忙核数**算…否则 6 核各 50% 会被当成 1 核吃 3 倍算力」，
> 是注释描述的正确口径没落地，不是设计分歧。

**修法**（`cpu_load_governor.rs:963-987`）：忙核 = `affected_cpus` 里 util > `EEM_BUSY_UTIL`(0.02) 的核数，
再 `clamp(1, curve.cores())`。2% 是 eBPF 采样的噪声地板；取 0 会把所有在线核算忙，取 10% 会把
「4 核各 5%」判成 0 核。Σ 项保留在 `demand_with_core_floor` 里（m 核时自动失效，但保住
hotplug/容量缺失时的退化路径）。

**受益面**：所有带 `[frontier_policy]` 的 SoC（39/40）与所有走 EEM 的模式，同一处改动；
sm8750/sm8650/sm8550 的曲线表都不用动。

### 1.3 缺陷二：EEM 规划池不看 cgroup cpuset，每轮规划出「必然被摘」的窗口（P0）

- 触发条件：`module/config/sm8550/feature.yaml` 的 `normal_fg_exclude_little: true`（2026-10-01 起开），
  `affinity.rs:1103-1119` 每轮把 top-app/foreground 收窄到 big∪prime。
- EEM 侧：`placement::decide` 的候选池来自 `energy_model::online_clusters()`，**只看在线核，不看 cpuset**。
- 后果（本包实测）：place ok 6,513 帧里 **clipped=true 2,493（38.3%）**、eff⊊dst 2,404（36.9%）；
  被摘 4,295 核次中**小核占 86.1%**（核 0/1/2 被摘率 79.0/88.3/93.7%，核 3-7 仅 2.2~14.1%）；
  59 个 (pid,簇) 对在 60 s 内被摘 ≥3 次（单对最多 37 次）。
- 修法：新增 `AffinityManager::eem_allowed_cpus()`（`affinity.rs:2449-2486`）——
  `top-app ∩ foreground` 的 cpuset，再与在线位图求交；`eem_place_round` 用它过滤 `online_clusters()`
  （簇内一颗允许核都没有就整簇剔除）。变化时才打 `affinity-eem-allowed` 一条 INFO，不刷屏。
- 代价：每 2 s 两次小文件读（cpuset.cpus）。收益：不再产生「写成功但被摘」的假动作、
  不再用假窗口更新 `eem_window` 触发下一拍重规划。

### 1.4 附带的模型一致性发现（未改，记 TODO）

`energy_model::best_placement` 的文档说「都不够时返回供给最大的」，实现 `(false,false)`
走的是**最便宜**分支。当前所有调用点都带了 `supply >= demand` 后置闸，故不产生错误迁移，
但文档与实现不符，容易在下次改动时埋雷。

## 2. 快速切应用卡顿（任务 ②）

### 2.1 升频速率闸排错位置：`up_wait` 白等（P0，已修）

源码原顺序（`cpu_load_governor.rs` 旧 :682-705）：

```
if up_wait < up_rate_limit_ticks { decision = "up_wait"; return; }   // 速率闸
...
is_high_load / is_significant_jump                                // 判据，永远到不了
```

⇒ 注释承诺的「显著跳变立即升频」从未生效。本包 8 会话 1,900,788 tick 实测：

- default `up` 499,644 / `up_wait` **220,174（30.6%）**；
- up_wait run 长：len1 57,948 / len2 12,580 / **len3 42,723**；
- 首个 up_wait → 真 up：**中位 478 ms、p90 487 ms**（= 3×160 ms），其中 53% 是等满 3 拍；
- 另有 37.9k run（33%）在 hold/down 终止 = 纯白等。
- playback/boost/reduce 全是 len1（40/160/160 ms）——**只有 default 的 up_rate=4 吃 3 拍**。

**修法**：判据前置，闸门改成 `if !is_significant_jump && up_wait < up_rate_limit_ticks`；
且显著跳变时直接 `current_perf = target_perf`（写的是**上限**，抬上限不强制频率跳变，
schedutil 在 ceiling 内按需取频，所以「一次给足」几乎不额外耗电）。
稳态无跳变时逐位不变。

验证列（下轮）：`decision` 里 up_wait 占比 30.6% → <18%、len3 占比 37% → <5%、
up 总次数增幅 ≤30%。

### 2.2 剩下两个卡顿源（本轮只取证，未改）

1. **@S 同步块墙钟偏慢**（`src/chiri/mod.rs:3129-3168`）：aff 快照在**主控制循环内同步构建**，
   8 会话 3,669 条 warn（阈值 50 ms），p50 59.3 ms / p90 108.5 / p99 595.8 / **max 10,292.9 ms**；
   成本 68.9% 在 `tid_stat`（443 次/帧 × 0.06 ms），线性 `13.1 ms + 61.8 µs×tids`。
   warn 在换包 ±5 s 聚集 9.8%（随机 3.7%）——正好压在「切应用」这个最需要节拍稳定的时刻。
   计划：20 ms 墙钟预算闸（超预算停止采样，帧头标 partial）+ `devimp_aff_secs` 1→2。
2. **换模式时 CLG 重建强制写 `perf_init`**：`apply_mode_takeover → reload_config/init_policies`
   把 `current_perf` 重置到 `perf_init` 并**立即写频**（default 0.35 ⇒ big ~1 GHz）。
   切应用时若跨模式（playback→default），上限在开应用那一刻被砸到地板再爬坡。
   计划：接管时用 `scaling_max_freq` 反算当前 perf 作为种子（读失败退回 perf_init）。

### 2.3 WindowProbe 超时：不影响节拍，影响规则命中

`src/monitor/window_visibility.rs:554` 的 `dumpsys -t 1 window` 单段预算 800 ms；
取消闭包传的是 `&|| false`（:191），所以日志里的 "cancelled or timed out" **100% 是超时**。
本包 74 条/8 会话（bluetooth 21、incallui 15、QQ 12…），失败后退避 5 s，不覆盖 LAST_ACTIVITY。
⇒ 表现为「切前台瞬间规则晚 1~5 s 生效」，不是掉帧源。`incallui` 14 h 归属经 cgroup 交叉验证
是真值（top-app），不是探针粘住。

## 3. 腾讯视频适配（任务 ①）

### 3.1 为什么不能「整包加 playback」

特调模式（`TunedGovernor`，akmode/playback/sweet 共用）**完全没有触摸升频**：
`grep -n touch src/chiri/tuned.rs` 零命中；触摸事件只喂 CLG（`mod.rs:3522-3526`）。
腾讯视频已观测样本的触摸密度 **28.1%**（同期 B 站 0.03%），且 playback 参数组用
`util_smoothing 0.25`（为长稳态视频调的），会把滚动/输入尖峰滤平 ⇒ 整包特调 = 关掉跟手。

而现有证据只有 81.1 s、两次约 40 s 的**详情页**会话（`devimpbin/_x1030/tencent-video.md`：
activity 全程 `.kmm.VideoDetailKmmActivityBk`、无 fps 数据、81 样本 4.81 W）。

### 3.2 落地：`activity-first` 标志位（零爆炸半径）

- `src/common.rs`：`SpecialTunedEntry` 新增 `activity_first: bool`；解析改 `splitn(4, ':')`，
  第四段是逗号分隔标志位（未知标志告警并忽略，旧条目三字段解析结果逐位不变）。
- `src/main.rs`：导出快照对带标志位的条目追加第四段。
- `src/monitor/app_detect.rs`：把 activity 查表提到特调早退之前；特调块改为
  `if !special_yields_to_activity(entry.activity_first, activity_mode.is_some()) { return fallback }`。
  纯函数 `special_yields_to_activity` 单独可测（本机 x86 无法跑 `is_chiri_soc` 分支）。
- `src/chiri/special_tuned.yaml`：`com.tencent.qqlive:playback:playback:activity-first`。
- `module/rules.yaml`：三条已观测 activity 拉回 default ——
  `.kmm.VideoDetailKmmActivityBk`（1,437 tick）、`.ona.activity.HotStartSplashActivity`（80 tick）、
  `.ona.activity.SplashHomeActivity`（29 tick）。

⇒ 播放页（activity 名未观测到）走包名回退 playback；详情/启动页走 CLG（有触摸升频）。
这两个文件都在 `module/config/normal`，与 SoC 解绑 ⇒ 单点改动全机型受益。

### 3.3 下轮验证判据

播放页 `mode=playback` 且 fps 无 >52 ms 长尾；详情页 `mode=default`；该包 Wh 占比下降或持平。
若拿到播放器 activity 名，改成显式键并删掉 `activity-first` 条目。

### 3.4 顺带修正的文档口径

`app_detect.rs` 文档写的优先级（FAS > Activity > 特调白名单）与实现不符——实现是特调白名单早退，
所以 bili 的两条 activity 规则（`rules.yaml:45-46`，映射 default）**写而不生效**：
本包 `.MainActivityV2` 49,654 tick + `BiliMainSearchActivity` 13,933 tick 全走 playback。
本轮只改文档描述，不改 bili 行为（现状对视频 App 反而合理），裁决进 07-todos。
