### 1.2 归因

1. **>1W 的两大来源不是"某个后台在跑"，而是"息屏刚发生"与"上限没压住"**：
   - 时间维度：82.7% 的高功率能量落在段内前 300s（68.2% 的秒数），avgW 0.687 vs 0.511。
   - 上限维度：见第二节——高负载秒里 41.3% 处于 doze 0.30 档、11.5% 处于"无 0.30 天花板"档，只有 47.4% 处于 scenemode 0.12 档。
2. **应用侧确有并发**：mobileqq 单进程 Σutil/帧 从 25.3 升到 53.3（+28），该秒线程总数从 65.6 升到 125.0（+59 线程），符合"消息/保活线程批量唤醒"的形态；配合 com.tencent.mm:push、OkHttp/NtHttp 线程（线程级明细见下）——但**这一波带来的 CPU 动态功率有限**：>1W 段 dyn 只占 19.2%（0.2615/1.3649 Wh）。
3. **>1W 的 80.8% 是 resid（屏幕/modem/GPU/静态漏电）**：status 的 cpu_dyn_w 是"能效表折算、只含动态项、是 CPU 功耗**下界**"（`src/logger.rs:424-425`）。>1W 段 gpu_busy 只有 0.27%（很低），psi_cpu 23.89（偏高）→ 高功率秒的 resid 主要由**已唤醒的外围（modem/显示/漏电）＋ 低频下的高漏电**构成，而不是 CPU 动态。
4. 因此"息屏 >1W"的可操作抓手是**压低上限、缩短高功率时间窗**，不是"揪出某个耗电 app"。

## 第二节 87.6% 息屏 CLG 激活必要吗？doze perf_ceil 0.30 与逐秒 tick/写频矛盾吗？doze 期 tick 决策分布？

### 2.1 证据

**(a) CLG 是否"逐秒 tick + 写频"——不成立**

- `src/chiri/cpu_load_governor.rs:378` `let tick_interval = Duration::from_secs(1);`、`:386` `recv_timeout(tick_interval)`：**有负载包就决策 + flush，超时才每 1s flush 一次**（`:376` 注释："空闲空转从 ~6 次/s 降到 1 次"）。
- `src/chiri/cpu_load_governor.rs:142-165` `write_freq`：`:143` 同值直接 return；`:153` 死区 gate `if (freq.abs_diff(current_freq) as f32) < deadzone_band { return; }`；`:157-164` 方向翻摆 + dwell 未到 return。缺省 `write_dwell_ms=320`、`write_deadzone=0.03`（`src/chiri/config.rs:364-369`；8550 `feature.yaml` 的 reduce/default/boost 均未覆盖 → 走缺省）。
- 实测：息屏 default 秒 23796，相邻 tick 的 **上限（cur_freq_khz）变化 16132 次 → 0.678 次/s**（分簇 little 9.90% / big 4.89% / prime 3.06% 的相邻 tick 变化率，tmp_an115/tmp_an84）。
- 同一窗口 status `freq_trans` mean 2152.2/s → **比值约 3200×**。`freq_trans` 的来源是 eBPF tracepoint `power/cpu_frequency`（`src/monitor/cpu_monitor.rs:99-109`），统计**内核 cpufreq 事件**（schedutil 自己调频），不是 ChiRi 写频。
- 结论：**"CLG 逐秒写频"是读数误判**，不需要"停写频"。

- C 档高负载秒的 tgt_perf 里 little 出现 1.00（16%），正是 reduce 的 1.00 生效的直接指纹。

**(e) scenemode 的真实覆盖率（daemon.log，去 U+2068/U+2069 后按 (时间,文本) 去重）**

- 8 批 daemon.log 时间范围首尾相接无重叠（05:15:05 → … → 2026-10-11 00:09:00），Scheduler 事件 1708 条，去重前后均 1708（重复率 0.0%）。

- 状态时长：**有效驻留 25 段合计 21136s＝5.87h**（被 OUT 或**下一次亮屏**终止；期间亮屏 326 次）。落到息屏 default 秒：scene 8734 秒 / 1.1351 Wh / **0.468 W**；post 2504 / 0.3894 / 0.560 W；other 12558 / 2.6209 / **0.751 W**。

- 修正既有简报："scenemode 0.12 基本没生效"**不成立**：息屏 default 秒中 A 档（≤0.135）占 10330/23199＝44.5%，其中 **8676 秒在 scene 生效窗内**；高负载秒里 A 档的 5719/5808 也在 scene 窗内。

### 2.2 归因

1. **87.6% CLG 激活是设计必然**（非特调息屏一律交 CLG；playback/fas 走 keep 分支），要改的是上限而不是开关。CLG 本身不是功耗来源：写频 0.678 次/s，且 clg=1 段 avg 0.627 W 低于 clg=0 的播放段 0.652 W。
2. **0.30 不是"矛盾"，是"两档共存"**：scenemode（0.12）与 doze（0.30）在同一段息屏里交替生效，形成 A/B 两档。B 档（0.30）虽然秒数少（4821 vs 5808 的高负载秒），却贡献 1.0457 Wh（A 档仅 0.7526 Wh）。
3. **问题是 0.30 档太宽**：匹配 (位置 × psi) 后 A 档 avgW 0.466 W、B 档 0.781 W，ΔW=+0.314 W，>1W 率 5.9% vs 23.0%（tmp_an118）——这是同一负载形态（同位置、同 PSI）下的同一性对照，不是负载选择效应。
4. **"天花板丢失"是退出路径的缺陷**：饱和退出把 CLG 换成 reduce(1.00)，掩盖了 0.30，且直到亮屏才会被 doze 分支重置。
5. tick 决策 up 占比高（71.92%）**不等于 doze 没压住**——up 是"抬向 ceiling"，在 0.30 档下 71.9% 的 up 抬到的是 0.30 而非满频；但 up 占比在 A/B 档之间无区分度（A 档 max_util 均值 0.77、B 档 0.74），说明它也不是改进抓手。

### 2.4 折算收益与不确定性

**匹配反事实（tmp_an118）**：以同 (段内位置 × psi 档) 匹配 A 档（0.12）与 B 档（0.30）：
- 匹配子集 A n=5808 avgW=0.466 W，>1W 5.9%；B n=4821 avgW=**0.781 W**，>1W 23.0%；ΔW=+0.314 W。

- 占息屏 default 能量 11.86%、占息屏全量 **10.33%**、占整机放电 **0.74%**。

**折算收益区间**：
- 目标 1（perf_ceil 0.30→0.20）：若按比例只实现 A/B 差距的 1/3~2/3 → **0.14 ~ 0.28 Wh**（息屏 4.76 Wh 的 2.9%~5.9%）。
- 目标 2（退出回 doze）：C 档全部 0.3496 Wh × 匹配内可达比例 → **0.03 ~ 0.07 Wh**。
- 目标 3（delay 300→120s）：仅在段内前 300s 的 82.7% 高功率能量上提前生效，且 scenemode 进入还需过 `SCENEMODE_SAT_UTIL` 门槛与 60s 免锁预判 → **0.05 ~ 0.15 Wh**（不确定性最大）。
- **合计保守 0.15 ~ 0.35 Wh，乐观上限 0.49 Wh**（对应息屏 4.76 → 4.27~4.61 Wh，目标档位约 4.3 Wh）。

**不确定性（必须随结论一起读）**
1. 全部为**观察性匹配对照**，非 A/B 实验（遵守铁律）。残余混淆：scenemode 只在息屏 ≥300s 且负载低于门槛时进入，B 档秒因此在时间/负载分布上与 A 档不同；已用 (位置 × psi) 分层匹配缓解，但无法完全消除。
2. `avgW` 里 CPU 动态只占 26.1%，**降 perf_ceil 的节流空间受 resid 下限约束**：A 档 avgW 0.466 W 里仍有大量 resid，故"压到 A 档均值"是**乐观上界**，真实收益会低于 0.49 Wh。
3. `doze_cfg.perf_ceil` 是硬编码 0.30（三处），抽出配置项属于代码改动，需复核 `mod.rs:3323-3329`/`:3723-3732`/`:4223-4233` 三处一致性。
4. 回归风险：`src/chiri/mod.rs:3726-3727` 注释明确 0.30 是为"后台任务（sync/JobScheduler）突发时允许短暂借力，但压住口袋发热"——降到 0.20 需实测后台同步/消息推送时延（本包无时延数据，**证据不足**）。
5. smax 是 scaling_max 读回上限，不等于实际频率；实际频率需看 snap 行 `cpu_cur_khz`（`src/chiri/mod.rs:556-557`：tick 的 cur_freq_khz 是"我们写了多少"，snap 的 cpu_cur_khz 是"内核实际是多少"）。

## 第三节 freq_trans 2969/s、migrations 3555/s 是后台唤醒还是 CLG 自身？能否消掉？

### 3.1 证据

**(a) 计数语义更正**

- 简报数值 2969/3555/8230 是 `status.csv` 的 **2s 原始增量**（相邻行三元组完全相同占 51.23%；相邻行间隔中位 1.001s，1.000s 出现 42226 次）。每秒值为其一半：息屏 default **freq_trans 2152 / migrations 1799 / wakeups 4008 次/秒（mean）**；亮屏对照 4128 / 4268 / 8253 次/秒。
- 息屏是亮屏的 **37%~52%**，并非简报所述"与亮屏同量级"。

**(b) 来源归属（status.csv 分 mode/state）**

| 分组 | n | avgW | wakeups/s | migrations/s | freq_trans/s |
|---|---|---|---|---|---|
| 息屏 default 全部 | 23796 | 0.627 | 4008 | 1799 | 2152 |
| 息屏 default / scene | 8734 | 0.468 | 4387 | 2304 | 2933 |
| 息屏 default / post | 2504 | 0.560 | 4664 | 1941 | 1966 |
| 息屏 default / other | 12558 | 0.751 | 3614 | 1420 | 1645 |
| 息屏 default / >1.0W | 3191 | 1.368 | 4225 | 1548 | 2112 |
| 息屏 default / ≤1.0W | 20605 | 0.512 | 3975 | 1838 | 2158 |
| 息屏 playback（**CLG 已释放**） | 3359 | 0.652 | 3603 | 1371 | 1292 |
| 息屏 fas（CLG 已释放） | 12 | 1.974 | 5052 | 1196 | **15** |

- CLG 自身写频 0.678 次/s vs freq_trans 2152 次/s → **freq_trans 与 CLG 写频相差约 3200 倍**，其来源是内核 cpufreq 事件（schedutil 按 util 自行调频），不是 ChiRi 写频。
- `freq_trans` 与 `migrations` 在同秒上强相关：r(freq_trans,migrations)=**0.934**、r(freq_trans,wakeups)=0.501、r(wakeups,migrations)=0.429（tmp_an75）→ **同一次唤醒/迁移突发同时推高内核调频次数**，即 freq_trans 是"唤醒→跑一下→schedutil 调频"的伴随量。
- playback（CLG 释放）仍有 1292 次/s freq_trans（>1W 的 370 秒为 1558 次/s），且 3359 秒里 **>1W 占 370 秒**——说明这些计数与 CLG 是否接管无关。
- **scene 档反而计数最高**（freq_trans 2933/s、migrations 2304/s > other 的 1645/1420）：因为 scenemode 把上限压到 0.12 后，同样负载下 schedutil 需要更频繁地微调频率。这进一步说明这些计数是"压上限的下游产物"，不是功耗来源（scene 档 avgW 反而最低 0.468 W）。

**(c) 与高功率的关系**

>1W 秒的 migrations 1550/s **低于** ≤1W 秒的 1776/s；freq_trans 2048 vs 2044 几乎相同；wakeups 4230 vs 3918（+8%）。**计数高低不预测功率高低。**

**(d) 能否"消掉"**

- 迁移量级由内核调度决定；ChiRi 侧可动的是 `Sched.params`（`module/config/8550/feature.yaml:187-188`，`sched_migration_cost_ns: 200000` 由内核默认 500000 降低、`sched_nr_migrate: 27`），当前设置**是加大迁移倾向**（"调度器更愿意跨核均衡"）。息屏下这一倾向贡献的迁移量与高功率无关（见 (c)）。
- 息屏空闲核多，唤醒后任务在多核间铺开本身会导致迁移计数偏高，这是 8 核 8550 的常态，不是异常。
- 写循环：`src/chiri/cpu_load_governor.rs:386` 已是 `recv_timeout(1s)` 的"有包才决策 + 超时 flush"，不是"每 1s 空转决策"。**没有可省的写频/tick 开销。**

### 3.2 归因

1. 息屏 freq_trans / migrations / wakeups **不是 CLG 自身产物**，而是内核调度与 schedutil 的伴随量；CLG 的实际写频只有 0.678 次/s。
2. 三者与息屏高功率**无因果关系**（>1W 秒的迁移反而更少）。
3. 因此简报设想的"延长决策周期 / 停写频 / 关 CLG 只留 tuned 能消掉 2969/s、3555/s"**不成立**：这些量消不掉，且消掉也不省电。

### 3.3 可操作参数改动

| 文件 | 参数 | 现值 | 建议 | 结论 |
|---|---|---|---|---|
| — | — | — | **不改** | 无可得收益；改 `Sched.params` 或 `write_dwell_ms/write_deadzone` 都会以调度延迟/频率跟随换不确定的功耗收益 |

（唯一相关的小项：`write_dwell_ms`/`write_deadzone` 缺省 320ms / 0.03 未被 8550 覆盖。若要把 0.678 次/s 再压一半，可试 `write_deadzone` 0.03→0.05，但收益不可测——实测 0.678 次/s 本身已很低，故列为**不推荐**。）

### 3.4 折算收益与不确定性

- **本项折算收益 ≈ 0 Wh（无可测收益）**。这不是"证据不足"，而是三个计数与功率的对照（>1W vs ≤1W 的 mig/ft 无差异；playback 段 CLG 释放仍有同量级计数）已经否定了因果方向。
- 不确定性：`wakeups/migrations/freq_trans` 是 2s 增量采样，跨采样边界会有 ±1 计数抖动；但分组均值差（1550 vs 1776/s）远大于抖动。

### 4.3 证据不足与不确定性（明示）

1. **线程级归因证据不足**：aff.txt 的 `t` 行是字段级差分（`# t 行级差分：任一槽变化才落行`），只有 `full=1` 刷新帧（首帧 + 每 30 帧）自包含；实测 full=1 帧仅 27/182（hi/lo 合计）。因此"哪条线程在 >1W 秒里跑"只有 full 帧样本（tmp_an99：DefaultDispatch / thread_general_ / libra-active-re 等 mobileqq 线程 Σutil/帧显著更高），**样本量小、只在部分批次有帧，不足以下强结论**。进程级结论（p 行每帧全量）是可靠的。
2. **aff 帧覆盖率**：8 批各 1 个 aff 文件，帧数 1913~14716；对齐到息屏放电秒且同秒功率有效的帧只有 5435（hi 713 / lo 4722）。
3. **package 列语义**：息屏期 package 是"息屏前最后前台"残值（`app_detect` 息屏不更新），launcher 占 51.7% 不代表 launcher 在跑。
4. **scenemode 进出只有 daemon.log**：`main_*.log` 中 `scene_*` event 数＝0，退出原因只有"饱和"一种记录；无法区分"被饱和打回"与"其他原因退出"（18/25 有配对记录）。
5. **反事实的残余混淆**：A 档（scenemode 0.12）只在息屏 ≥300s、负载低于门槛、且不在 300s 冷却时生效；B 档（doze 0.30）主要在 other 状态。已按 (段内位置 × psi) 分层匹配，但仍非随机化。
6. **cpu_dyn_w 是下界**：能效表折算、只含动态项，故"CPU 动态只占 26%"是上界性质的描述；降上限的实际节流空间受 resid 支配，乐观上界会被打折。
7. **无时延/流畅度数据**：改进项 #1、#3 的主要回归风险（后台同步/推送时延、锁屏后台卡顿）在本数据包内**无法验证**，必须实机复核后才能上线。
8. **计数跨采样抖动**：status 计数是 2s 增量，跨采样边界 ±1；分组差远大于抖动，不影响结论方向。
