# 2026-10-31 日志 ERROR 取证与负载源兜底

> 起因：2026-10-30 用户追问「你有没有注意到日志中的 error」。此前四轮只解析 `main_*.log` / `aff_*.log`，
> 从未按 `[LEVEL]` 统计过 `daemon.log`。本轮把 1025–1030 全部日志包的守护进程日志逐条分级，
> 定位到两类**功能性失效**（不是噪声）并落地修复。

## 1. 底盘与方法

- 输入：`devimpbin/*/x_*/daemon.log`，1025–1030 共 65 个文件，按 md5 去重后 **58 个**；
  批次口径仍是按目录 basename 去重后的 **29 批**（sm8550 19 / sm8750 7 / sm8250 3）。
- 行格式：`[ts] [LEVEL] [module] [tag] msg`；按行首正则分级，未解析行 62,639 条几乎全是
  `screen-detect` 的 TRACE（无 LEVEL 段），**panic = 0**。
- 级别总量（58 个唯一文件）：INFO 82,379 / WARN 25,713 / **ERROR 446** / DEBUG 133,237。
- SoC 分布：sm8550 33 个文件、sm8750 22 个、sm8250 3 个。

## 3. 根因

### 3.1 sm8250 / kernel 4.19：eBPF ringbuf 不存在 → 负载源永久缺失

- `src/monitor/cpu_monitor.rs` 的 `Ebpf::load(include_bytes!(...))`（debug :100 / release :105）在
  kernel 4.19.157-perf+ 上失败：`BPF_MAP_TYPE_RINGBUF` 需要内核 **≥ 5.8**。
- `src/monitor/mod.rs:378-401` 的 `spawn_guarded("cpu_monitor_ebpf", …)` 拿到 Err 后只打一条
  `monitor-cpu-crashed`，**线程结束、不 panic、不 exit、不重试**；daemon 继续活着，但
  `DaemonEvent::SystemLoadUpdate` 再也不会发出。
- 后果链：CLG/tuned 的看门狗按「N 秒无负载事件」判定负载源失效并 release CPU 控制权 →
  68 分钟内 release 26 次 → **该机型等于完全没有 ChiRi 调频**（只剩 scenemode/默认调速器）。
  这是「能跑但不生效」的静默失效：daemon 活着、日志只有 ERROR 级别的一条，很容易被漏掉。

### 3.2 FAS 开环通知过激：每次翻转沿都发用户可见通知

- 判据：`src/scheduler/fas/controller.rs:15` `FRAME_FEEDBACK_STALE = 500ms`；超时即开环。
- 实测：417 次进入开环、178 次 `closed-loop restored`；配对时长**中位 1 s、p90 7 s**；
  207 条 `[fas] open-loop entered: … posting ChiRi-FAS warning`。
- 抽样全是「静默 1–3 s 后 AppDetect 已切到 launcher / FAS 实例去激活」——即退游、加载、切后台的瞬态。
  唯一一条 14551 s 的「长开环」是配对假象（中间已去激活，恢复行没配到同一次进入）。
- 危害不在 CPU，而在**用户可见噪声**：每次退游弹一条「ChiRi-FAS」告警，久而久之用户会关掉通知权限，
  真正需要告警的长开环反而看不见。

## 5. 修复

### 5.1 Fix 1：eBPF 不可用时的 procfs 负载源（`src/monitor/cpu_monitor.rs`）

新增 `[proc-stat-fallback]` 段，**不改 eBPF 主路径**：

- `read_proc_stat_core_times()` + `parse_cpu_times_line()`：逐核累计 jiffies；汇总行 `"cpu  …"`
  必须跳过（坑：按 `split_whitespace` 取首项会把汇总行解析成 cpu id 100）。
  忙 = user+nice+system+irq+softirq+steal，闲 = idle+iowait（guest 已含在 user，不重计）。
- `update_core_utils(last, current, out)`：两拍差分 `busy/total`，clamp(0,1)；
  `total_delta == 0`（同一 jiffie 内重复采样 / 该核本拍缺失）**沿用上一拍**，避免把利用率抖成 0 触发降频；
  核数变少（热插拔下线）时截断向量，旧核数据不得残留在尾部继续参与需求计算。
- `fg_thread_max_util()`：按 TID 读 `/proc/<pid>/task/<tid>/stat` 的 utime+stime 差分，
  `USER_HZ = 100`（Android 恒定），500ms 节流；首帧只建基线。
- `start_proc_stat_fallback(tx, rx_pid, ak_active, sample_ms_normal)`：**节拍与 eBPF 路径完全一致**
  （特调 40ms / 常规 `sample_ms_normal`），每拍发 `SystemLoadUpdate{core_utils, foreground_max_util}`；
  不伪造 `BpfStats`（procfs 无等价来源，留空优于填 0）；前台切换清 fg 基线；
  `/proc/stat` 连续失败 > 50 拍（≈8s）返回 Err，交回看门狗走 release —— 宁可不接管，
  也不发一串全 0 把频率压到底。
- 接线（`src/monitor/mod.rs`）：`start_cpu_loop` 返回 Err 时先 `warn!(monitor-cpu-ebpf-unavailable)`
  再起兜底；兜底也失败才 `error!(monitor-cpu-crashed)`。
- i18n：`monitor-cpu-ebpf-unavailable` / `cpu-monitor-proc-fallback-started` /
  `cpu-monitor-proc-stat-read-failed`，中英对称。

### 5.2 Fix 2：FAS 开环通知改为「持续时长」触发（`src/chiri/fas_manager.rs`）

- `OPEN_LOOP_NOTIFY_AFTER = 10s`：进入开环只记 INFO；**持续 10s** 才发一次用户通知；
  恢复时记 INFO 并带开环时长（ms）。PID 替换 / 去激活两处一并清 `open_loop_since/notified`。
- 判据依据就是 §3.2 的分布：中位 1s、p90 7s 的瞬态不该打扰用户；真的坏满 10s 的仍然会通知。
- controller 侧 `error!(fas-loop-open)` 保留（「开环 = 功能性失效」的错误标记本身没错），
  本次只改**用户可见**的那一层。

## 6. 验证

- `cargo fmt --all` 干净；`YUMI_SKIP_EBPF=1 cargo check -p chiri` exit 0（13 条既有 dead-code 告警）。
- 新增 6 条单元测试 `monitor::cpu_monitor::proc_stat_parse_tests`（汇总行跳过、忙/闲口径、
  comm 含空格括号、截断行、零增量保持、新核扩容）→ **6 passed**。
- `cargo test -p chiri --bin chiri`：**266 passed / 3 failed / 1 ignored**。3 条失败全在 `fas_manager::tests`
  （`activate_same_pid_unknown_starttime_is_new_session_fail_closed` :588、
  `repeated_activate_same_pid_keeps_frame_session` :683、
  `same_package_pid_replacement_advances_generation` :694），均卡在
  `assert!(manager.activate("game", 100))`。
  **判为既有环境依赖失败、非本次引入**：`activate` 首步是
  `fas_whitelist_entry(pkg).and_then(fas_app_config)`，而白名单是
  `include_dir!` 编译期嵌入的 `module/config/normal/fas.yaml`（21 行，只有真实包名，
  无 `game` 条目）⇒ 宿主机上 activate 必返回 false；即便进了白名单，
  `controller.load_policies` 还需要真机 sysfs 的 cpufreq 节点。这三条测试只能在真机上通过。

## 7. 残留与后续

1. **`[selfcost] @S` 22,397 条**：只有 devimp 诊断开时出现，但 50ms 阈值被打了这么多次说明
   @S 帧构建本身偏贵。下一轮可做「@S 分块计时」，先定位是 `/proc/<pid>/task/*` 扫描还是
   uclamp/掩码回读，再决定砍哪块；不影响生产（诊断关时无此路径）。
2. **`sched_migration_cost_ns` / `sched_nr_migrate` 在零售 GKI 上不存在**（`kernel/sched/core.c:96`
   `sysctl_sched_nr_migrate` + `debug.c:324` 只挂 debugfs）：ChiRi 的「迁移成本微调」在零售机是空转，
   每次 boot 刷 38 条 WARN。应改为「探测一次、缺失即静默并标记不可用」，而不是每 boot 重试。
3. **3 条 FAS 单测**需注入桩（白名单 + policy loader）或标注 `#[ignore]`，否则宿主机永远红。
4. sm8250 的 procfs 兜底**尚未真机验证**：本次只做了离线路由与解析单测，还需一次 4.19 真机日志
   确认 `monitor-cpu-ebpf-unavailable` 出现、CLG 看门狗不再 release、`status.csv` 的 CPU 列有值。
